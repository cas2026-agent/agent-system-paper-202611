总览

智能体系统的层次，以及六篇论文各自的位置

怎么读这张图。一个智能体任务从最上层开始：测试环境给出目标和初始观察，智能体主循环据此工作，最后把动作交回环境。主循环每一轮做两件事，一是把对话上下文作为 LLM request 发给大模型推理服务，拿回模型的回复；二是按回复里的指令向工具沙箱发出命令，拿回执行结果。这两条往返交替进行，一个任务往往要几十轮，每一轮的上下文都比上一轮更长。推理服务运行在 GPU 集群上，沙箱运行在 CPU 主机和存储上，GPU 的耗电最终汇总为数据中心的电力需求。左侧的搜索策略和右侧的强化学习训练都建立在主循环之上：前者在一个任务里尝试多条路线、走错就退回，后者从相同的起点批量运行大量任务来训练模型。

AgentBoard 位于最上层。它回答“大模型当智能体用时能力如何”，关心的是测试环境如何设计、得分如何计算，下面的推理服务和沙箱如何实现不在它的范围内。为了比较模型本身，它用固定的简单写法驱动所有模型，在部分可观测、需要多轮交互的环境里按步计算进度率。

The Cost of Dynamic Reasoning 的范围最大，是图中红色虚线围出的阶梯形区域：从智能体主循环发出调用，到推理引擎在 GPU 上执行，再到数据中心的功率。它不修改其中任何组件，而是沿着这条链路测量智能体负载的开销：一个 request（智能体的一个完整任务）调用多少次模型，时间花在推理还是工具上，GPU 是否闲置，占多少显存，多花计算能换来多少准确率，最后才把单次能耗推算到大规模使用量。

LLMServingSim 2.0 覆盖推理服务这一列和下面的 GPU 硬件，是图中青色虚线围出的区域。硬件正在变得异构（TPU、PIM、CXL 内存），部署也在拆分（prefill 与 decode 分开、缓存分层共享），这些组合很难逐个在真机上试。它在 CPU 上模拟 request 从路由、组批到硬件执行的整个过程，同时给出吞吐、延迟、显存和功耗，用来回答“换一种硬件或部署，服务性能会怎样”。它只考虑彼此独立的 request，不涉及智能体。

AgentServeSim 位于推理服务这一列，建在 LLMServingSim 2.0 之上。推理引擎要管理显存里的 KV 缓存、实例内的等待队列和多个实例之间的分配，因此要做三个决定：工具间隙里这个 program 的 KV 缓存留不留、下一个 turn 在队列里排第几、派到哪台机器。它把这三处做成可替换的策略，并用 CPU 上的模拟器代替真实 GPU 来评估效果，再让大模型在模拟器里自动改写策略。

DeltaBox 位于沙箱内部。搜索策略需要随时退回历史节点，强化学习训练需要从一个准备好的状态开出很多沙箱，两者都要求快速保存和恢复沙箱里的文件和进程。DeltaBox 修改了沙箱的客户机内核：文件用可在运行中加层的 overlayfs，进程用冻结的 fork 模板，使保存和恢复都在毫秒级完成。

Crab 在图中出现在两处。一处是智能体与推理服务之间的代理，它截获 LLM request，从而知道一轮何时结束、模型何时在思考；另一处是宿主机上的存档调度和内核观察，它用 eBPF 看清每一轮在沙箱里实际改了什么，决定这一轮存不存、存多少，并统一安排一台机器上所有沙箱的存档任务。底层的保存和恢复直接使用现成的 CRIU 和 ZFS。

AgentBoard: An Analytical Evaluation Board of Multi-turn LLM Agents

AgentBoard：多轮 LLM 智能体的分析式评测板

Chang Ma、Junlei Zhang、Zhihao Zhu、Cheng Yang、Yujiu Yang、Yaohui Jin、Zhenzhong Lan、Lingpeng Kong、Junxian He，香港大学、浙江大学、上海交通大学、清华大学、西湖大学、香港科技大学

深度学习自然语言处理大模型评测智能体基准
背景

领域定位

深度学习，自然语言处理
大语言模型的能力评测：MMLU、GSM8K、HumanEval
把大模型当智能体来评测：AgentBench、GAIA、MINT
多轮交互、部分可观测、按步计分：AgentBoard

MMLU、GSM8K 这类基准一次给出完整题目，模型一次作答，测的是知识和单步推理。智能体评测关心的是另一种能力：在一个会对动作作出反应的环境里连续做几十个决定，边做边收集信息，记住已经知道的事，发现走错后改正。这种能力只有在多轮交互中才会暴露出来，单轮问答测不到。

AgentBoard 的贡献在测量方法上，它没有训练新模型。它提供一个基准（4 类场景、9 种任务、1013 个测试样本），一个在每一步都给分的进度指标，以及一套把运行记录拆开分析的开源工具。

背景

基本概念

LLM 智能体
大模型读入环境的文字描述，输出一个文字动作（例如 open fridge 1），环境执行后用文字返回结果，循环往复直到完成任务或用完步数。
多轮交互
一个样本需要多次“观察、行动”的往返。每一步的决定会改变后续能看到的信息，早期的错误会累积。
部分可观测
智能体一开始看不到全部状态，比如不知道哪个柜子里有鸡蛋，必须主动去看。这迫使它探索并记住探索结果。
POMDP
部分可观测马尔可夫决策过程，是上面这种交互的数学写法：给定目标 g，智能体根据目标和历史观察选动作，环境转移到新状态并返回新的观察。读懂后文不需要它的公式。
成功率
在限定步数内完整达成目标的样本比例，每个样本只有 0 和 1 两种结果。
进度率
本文提出的指标，每一步给出 0 到 1 之间的分数，表示到这一步为止离目标有多近。
Grounding
把想法落实成环境能执行的动作。grounding 准确率是模型输出的动作中合法动作所占的比例，反映模型是否守格式、是否用对动作名。
Act 与 ReAct
两种提示方式。Act 只让模型输出动作；ReAct 让模型先写一段推理再输出动作，推理文字会进入后续的上下文。
主线

问题、方案、验证、发现

问题

现有基准要么任务种类单一，要么大部分是单轮题，要么信息一开始就全给了。而且几乎都只报最终成功率，在难任务上大家都接近 0，比不出高下。

方案

挑选并改造 9 种需要多轮、大多部分可观测的纯文本任务；给每个样本标注子目标或匹配规则；每一步计算进度率，取历史最高值。

验证

8 种任务各 60 条运行记录，由 4 人在不看自动分数的情况下打分。进度率和人工分的相关系数在所有任务上都超过 0.95。

发现

GPT-4 平均进度率 70.0%，大幅领先。能否持续多轮推进是强弱分水岭，而这依赖 grounding、世界知识和自我纠错等基础能力。

九种任务大多来自已有研究，改造围绕三件事：统一成纯文字的输入输出，让所有文本模型都能参评，比如 BabyAI 原本是图像观察和数字动作；补齐或重标子目标，比如 ScienceWorld 原有子目标稀疏且权重不均；改进报错信息，让模型犯错后有机会纠正，比如 WebShop 越界和点错对象时的反馈。另有两处修补具体漏洞。Jericho 原游戏要 50 到 300 步，超出模型的上下文能力，于是改写目标，限制在 15 个子目标内。Tool-Query 的问题刻意设计成凭记忆答不出来，即使答案碰巧正确，没有查库也判错。

所有模型用相同的智能体写法

评测要比较的是模型，如果给不同模型配上复杂程度不同的规划、反思或记忆模块，分数差异就分不清来自模型还是来自框架。所以全部采用图左的简单结构：模型拿到目标、当前观察和之前的全部观察与动作，生成下一个动作；提示词如图右，只要求输出动作（Act），外加一个示范例子。历史超过上下文长度时只保留最近若干轮，交互得以进行到步数上限，上下文较短的模型不会因提前终止而被额外扣分。

方法

进度率怎么算

§2.2

进度率要解决的问题是：样本没做完时，怎样给出一个能比较的部分分。不同任务的状态形式不同，所以有两种算法，二者都输出 0 到 1 的分数，最后都取历史最大值。

subgoal：数里程碑（AlfWorld 等）

中间状态难以直接和目标比较的任务用这种算法。人工把目标拆成 K 个有先后顺序的子目标，每个子目标对应环境文字里的一段可检查内容，用正则表达式判断是否达成。分数等于已达成子目标的比例。

rt = max0≤i≤t ( 1/K × Σk f(si, gk) )，f ∈ {0, 1}

match：比较当前状态和目标状态（PDDL 等）

状态可以逐项比较的任务用这种算法。比如目标是“a 在 b 上，b 在桌上”，当前是“a 在桌上，b 在桌上”，两个条件满足一个，匹配分 0.5。表格操作按单元格比较，网页任务按网址和页面内容比较。

rt = max0≤i≤t f(si, g)，f ∈ [0, 1]

上表就是这个指标相对成功率多出来的信息。取最大值的用意在于容忍探索：智能体经常要走回头路，比如为了找东西离开厨房，这时当前状态和目标的距离会暂时变远，直接用当前状态打分会惩罚探索。取最大值记录的是“最远推进到了哪里”。代价是分数不会下降，智能体后来破坏了已完成的部分也看不出来。

为了让子目标标得出来，每个目标只允许对应一种子目标顺序，约 5% 的原题因此被改写。这个约束只限制里程碑的顺序，绕路完成同样能拿满分。它也意味着进度率最适合目标明确、路径相对固定的任务。页面末尾的附录用一个完整样本演示了这个计算过程。

验证实验：进度率可信吗

进度率是人为定义的分数，只有它和人对“做到哪了”的判断一致，才能拿它比较模型。后面所有结果都以此为前提。

结论

结论

GPT-4 在所有任务和所有子能力上都领先，开放模型中 Llama3 和 DeepSeek LLM 最好。强弱智能体的分界线在于能否在多轮交互中持续推进，大多数开放模型在几步之后就停滞。持续推进的能力建立在 grounding、世界知识和根据反馈自我纠正等基础能力之上。代码数据和智能体交互数据都能在不增加参数的情况下明显改善这些能力。

方法上，进度率让评测在成功率接近零的区间仍然有分辨率，难易分组、按步曲线和子能力拆解把一个总分变成了可以定位问题的诊断信息。具体名次会随新模型过时，这套测法的价值更持久。

局限

局限与讨论

进度率依赖人工标注的子目标。任务越复杂，标注的人力成本越高；用大模型自动标注是自然的方向，但当时的模型在这些任务上表现不佳，标注不可靠。评测全部在模拟环境中进行，是为了保证结果可复现；真实网站内容随时变化，在真实环境中操作也有安全风险，这两点都还没有解决。

统一的 Act 写法让比较公平，但分数反映的是模型自身的能力，不代表配上更好的规划、记忆或反思模块后能达到的水平，排行榜应理解为基础能力排名。

背景

基本概念

智能体沙箱
隔离执行智能体动作的容器或轻量虚拟机。本文的沙箱里常驻一个智能体进程，所以沙箱状态包括文件系统和这个进程的内存。
检查点与恢复
把某一时刻的完整状态保存下来，之后能回到这个状态。对智能体而言就是回滚。
overlayfs
Linux 的叠层文件系统。下面是只读的 lower 层，上面是可写的 upper 层，程序看到的是叠加结果；修改文件时先把它从下层复制到上层（copy-up）。原生实现的层在挂载时固定，运行中不能增删。
写时复制
多方共用一份数据，有人要改时才把被改的部分复制出来。fork、reflink、copy-up 都基于这个思路。
XFS reflink
文件级写时复制。复制文件时只增加对数据块的引用，写入时才按 4 KB 的块分配新空间。
fork
Linux 创建子进程的系统调用，只复制页表，内存页由父子进程写时复制共享，所以耗时和进程占用的内存大小基本无关。
CRIU
把运行中的进程完整保存成镜像文件、之后再恢复出来的工具。lazy-pages 模式下恢复时按需读回内存页。
Firecracker
AWS 开源的轻量虚拟机，常用于 serverless 和智能体沙箱。它的快照包含内存和设备状态，不包含磁盘。
E2B、CubeSandbox
两个面向智能体的沙箱产品。E2B 靠暂停整台虚拟机做快照；CubeSandbox 用 reflink 卷加内存脏页跟踪做写时复制快照，但需要定制的宿主机内核。
主线

问题、洞见、机制、效果

问题

编程智能体改的是真实的操作系统状态，改对话历史撤销不了。树搜索不停回退，昂贵的恢复反复出现在等待路径上，而现有方案保存和恢复都要复制整个状态。

洞见

相邻两次存档之间只多了几个文件、改了少量内存页，只需保存这部分变化。文件系统和进程内存被当作一对按变化保存的状态，称为 DeltaState。

机制

DeltaFS 让 overlayfs 能在运行中插入新的可写层；DeltaCR 用 fork 出来并冻结的进程当模板，恢复时再 fork 一份，只复制页表。两者在相同时刻成对保存。

效果

存档约 10.83 毫秒，与大模型推理重叠，智能体不用等；恢复约 1.86 毫秒。SWE-bench 搜索中花在沙箱上的时间占比从 23% 到 48% 降到 1% 到 2%。

问题

文件和进程必须一起回滚

§2.2、§2.4

只回滚文件

进程内存里的对话历史和工具输出还记着那些已经不存在的磁盘修改。

只回滚进程

进程回到了过去，却在另一条分支留下的文件上继续干活。

两种错位都会让一个搜索节点每次展开的结果不一样，树搜索赖以成立的确定性就没了。进程状态里装的是大模型的对话历史、工具的输出、打开的文件描述符；如果回滚时丢掉进程、只恢复文件，就只能从头重新执行之前的所有命令来重建它，代价随搜索深度线性增长。所以一个存档必须是“文件状态加内存状态”这一对，并且两者对应相同的时刻。

据此，设计目标有四个：文件与进程联合保存和恢复，耗时在毫秒级；保存时复制的数据量只和实际改动多少有关，和工作目录大小无关；回到任意历史存档的时间是常数；对智能体透明，不改它的代码、不重启、不丢上下文。

这个想法之所以能落地，是因为 Linux 里已经有两个现成的“变化”表示。overlayfs 的每一层本来就只记录相对下层的改动，冻结当前可写层、在上面再放一层，就等于存了一个文件增量。fork 出的子进程和父进程靠写时复制共享内存，冻结住的子进程就是父进程那一刻内存的快照，只占后来被改动的那些页。缺的是两样东西：overlayfs 不允许运行中加层，fork 出来的进程也不总是能安全地被冻结和再次 fork。DeltaFS 和 DeltaCR 分别补的就是这两处。

文件这一半的难处在于规模和频率的组合。仓库有数十万个文件，智能体每一步通常只动其中几个：改一个源文件里的几行，或者 pip install 往 site-packages 里新增一批文件。存档如果按“目录有多大”付出代价，在搜索的频率下就承受不起；它应该只按“这一步改了多少”付出代价。回滚也一样，跳回十步之前的节点不应该比跳回一步之前更慢。

现有的文件工具都在某一项上不达标，它们的共同做法是复制，并且只管文件、丢掉进程内存。复制目录的成本与目录大小成正比。git stash 或分支只管版本库跟踪的文件，装进 site-packages 的依赖、构建产物、被 .gitignore 忽略的文件通常都不在它的范围内，而这些恰恰是 pip install 和编译改动的地方。Docker commit 把容器的改动打包成镜像层，回滚要用新镜像重启容器，恢复需要 1 到 10 秒。Btrfs、ZFS 和 LVM 快照是块级写时复制，速度不差，但要把沙箱的存储整体换成这些文件系统，并且快照以整个卷为单位。

overlayfs 是 Linux 的叠层文件系统，Docker 容器的文件系统就建立在它上面。它把一个只读的下层（lower，可以有多层）和一个可写的上层（upper）叠成一个统一的视图交给程序。程序以为自己在读写一个普通目录，实际上所有修改都只落在上层，下层永远不变。

从上表可以看出，上层里装的恰好是“相对于下层的全部改动”：改过的文件、新文件、删除标记，没有改动的文件一个都不在里面。这正是存档需要的增量。如果在某一刻把当前上层冻结成只读，再在它上面放一个新的空上层，被冻结的那一层就是“到这一刻为止这一步的改动”，相当于做了一次存档，而且不复制任何未改动的数据。回滚则是把上面几层拿掉：被拿掉的层里的修改、新文件、删除标记一起消失，下层原来的文件自动重新可见，被删的文件也回来了。存档和回滚都只是改变“哪些层叠在一起”，与仓库里有多少文件无关。

第一行是表面上的限制，后面几行是真正动手改层时才会暴露的问题，它们都源于原生 overlayfs 默认“层在挂载后不会变”。内核为了速度缓存了很多“这个文件在哪一层”的信息：打开的文件句柄、目录项缓存、正在进行的读操作手里的层数组。一旦允许运行中换层，这些缓存全都可能过期。最危险的是已打开的文件。举个例子，智能体在第 3 步打开一个日志文件不断追加，第 3 步结束时做了存档，旧上层被冻结。如果不处理，第 4 步的追加仍然顺着文件句柄写进已冻结的那一层，存档被悄悄改掉，日后回滚到第 3 步时，看到的却是包含第 4 步内容的文件。DeltaFS 用一个全局计数器 checkpoint_gen 解决：每存档一次加一，每个文件记住自己最后一次定位时的代号，写入路径上两者一致就直接写，不一致就按新的层组合重新找到位置，必要时先 copy-up 到新上层再写。这个检查只在写入时做，读和没变过的文件不受影响，所以叫“惰性切换”。

写放大的问题则来自 copy-up 的粒度。智能体典型的编辑是改 12 到 65 KB 文件中的几行，原生 copy-up 每次都复制整个文件；更糟的是，这个文件在后续每一步再被改动，都要从下层再完整复制一份到新的上层，存档越多，这个文件的副本越多。reflink 让 copy-up 变成“新建一个文件，引用原文件的所有数据块”，只有真正改动的 4 KB 块才分配新空间。降级旧上层时用改名而不是复制，文件的块引用关系原样保留，于是一个连续很多次存档都没改过的块在磁盘上始终只有一份。实测中不开 reflink 时写入量随文件大小线性增长，开了以后几乎是常数。

还有一个问题文中没有讨论：每次存档都会多出一个下层，查找文件时要从上往下逐层找，层数越多查找路径越长，而 Linux 内核对 overlayfs 的下层数量设有上限（OVL_MAX_STACK，为 500）。一次 30 轮的搜索影响不大，但更长的搜索或训练需要把不再访问的层合并或回收，论文的垃圾回收只针对进程镜像，对文件层如何回收没有说明。

存档时，CRIU 让智能体暂停约 11 毫秒拍一张内存照片，写进内存盘；DeltaFS 在这个暂停的瞬间把当前可写层改成只读并放上新层。两件事看到的是相同的冻结时刻，所以文件和内存对得上。拍完照后，智能体在主循环的安全位置 fork 一次，父进程继续干活，子进程立刻把自己冻结，成为这次存档的模板。如果 CRIU 拍照失败，刚才的加层操作会被撤销并报错，不会留下文件和内存不匹配的半成品。

存档对智能体几乎没有代价，是因为它发生在智能体等待大模型回复的时候：一次回复要几秒，暂停只有十来毫秒。读档则没有这样的掩护，搜索必须等它完成才能继续，所以 DeltaBox 把读档压到只剩“换层”和“fork”两个动作。读档后的进程从存档那一刻的下一条指令继续执行，察觉不到自己被回滚过。

DeltaFS：运行中可以加层的 overlayfs

Figure 4、§4.1

左图是传统 overlayfs：沙箱镜像在最底下，中间是只读层，上面是可写层，程序看到的 a、b、c 三个文件是各层叠加的结果。右图是 DeltaFS：存档时原来的可写层被冻结成只读的 Step-1 层，上面放一个新的可写层 Step-2，之后的改动都落在新层里。存档就是加一层，回滚就是去掉上面若干层，耗时与文件多少无关。右上角红色的 checkpoint_gen 是每存档一次加一的计数器。

一次换层按这样的顺序进行：用户态先把当前上层目录改名，作为新的只读下层；再建一个空目录作为新上层；然后调用 ioctl。内核解析新的层配置，为每个目录建一个私有挂载，组成新的层数组，在自旋锁保护下原子地替换旧数组，把 checkpoint_gen 加一，并把缓存的目录项标记为需要重新验证。被降级的旧上层放在所有下层的最上面，存档前已经 copy-up 过的文件因此仍能被找到；旧数组等两次存档之后、确认没有读操作还在使用时才释放。整个过程不搬动任何文件数据，DeltaFS 的这部分改动约 565 行 C。回滚走的是相同的 ioctl，只是把层组合换成目标存档记录的那一组。

Figure 5、§4.2

虚线左边是存档，右边是读档。存档时 GSD 一边让 CRIU 在后台生成镜像链，一边通过管道请求活跃的智能体 fork 出模板放入模板池。读档时先用 ioctl 换层，再查模板池：命中（Hit）就从模板 fork 出新的智能体，没命中（Miss）就用 CRIU 从镜像恢复。

快路径快在 fork 只复制页表、不复制内存内容，占几百 MB 和占几 MB 的进程 fork 起来差不多快。fork 在主循环的安全位置进行，此时没有进行中的系统调用和写了一半的文件，并且只复制调用线程，避开了多线程程序 fork 后可能出现的死锁。CRIU 镜像是兜底：模板占内存，模板池有上限，被淘汰的模板仍有镜像可用，只是慢一点，不会出错。镜像本身的清理要考虑搜索算法，MCTS 随时可能重新选中很久没碰过的节点，按“最近没用”删除会导致恢复失败、重选、再失败的循环，所以只清理搜索已经判定不会再访问的节点。

fork 之后子进程第一次写某一页时才真正复制，每次几微秒，Python 智能体恢复后第一轮会写很多页。GSD 在另一个 CPU 核上把子进程的可写页挨个读一字节再写回，提前把复制做完；来不及处理的页照常复制，最坏也不比不预热差。另一个问题来自大模型 SDK，它们在后台开着 HTTP 连接池和线程池，带着这些线程 fork 会导致半开的连接、错乱的连接池状态和永久死锁。DeltaBox 把 SDK 和网络连接全部移到单独的 NPD 进程，智能体只通过定长管道消息与它通信，模板里便不再有危险的线程。

系统

其他设计与实现

搜索框架常靠跑测试给节点打分，测试会留下 __pycache__ 一类的临时文件。DeltaBox 在跑测试前存档、读完结果后无条件回滚，测试便不会污染沙箱。

存档是按进程而非按虚拟机做的，一台虚拟机里可以放多个智能体各自独立回滚，整机快照做不到这一点。每台 Firecracker 虚拟机运行带 DeltaFS 模块的定制 Linux 6.8 内核，宿主机通过 virtio-vsock 与 GSD 通信。DeltaFS 的 ioctl 约 565 行 C，DeltaCR 约 1200 行 Python。LangGraph 自带的存档只保存图的逻辑状态，撤销不了已执行的命令，DeltaBox 提供了适配器，让图状态存档时同时触发沙箱存档。

列名的读法
每个方案都要同时恢复进程和文件，列名写成“进程怎么恢复 + 文件怎么恢复”。
replay+cp
文件用 cp，即 Python 的 shutil.copytree 把整个仓库目录复制一份；进程用 replay，即不保存内存，读档时重新启动智能体、加载代码索引，把录下来的动作按顺序再执行一遍，把内存状态重新算出来。
FC-Diff+dm
进程用 Firecracker 虚拟机的增量快照（Diff），存档时只保存自上次以来变脏的内存页，保存的是整台虚拟机的内存；文件用 dm-snapshot，即 Linux device-mapper 提供的块设备写时复制快照。
CRIU+cp
进程用 CRIU 把智能体进程的内存写成镜像，读档时从镜像恢复；文件同样用 copytree 复制目录。
E2B (diff)
自己部署的开源 E2B，暂停整台虚拟机，保存变脏的内存页和磁盘块，读档时恢复虚拟机。它本身就同时覆盖进程和文件。
DeltaBox
进程用 DeltaCR（CRIU 镜像加 fork 模板），文件用 DeltaFS（overlayfs 换层）。

表注里的特殊口径。有三处数字的含义和其他格子不同，读表时要注意。第一，replay+cp 只在每条轨迹开头复制一次原始仓库，之后的节点都不再复制，表里的 ck 是这一次复制的耗时；它的读档在重放时直接使用录好的大模型回复，不计大模型的时间，所以 28 秒全部是重启程序、重新执行命令本身的开销，算是下限。第二，FC-Diff+dm 的存档平均值里包含每条轨迹开头一次完整的虚拟机快照，会把平均值抬高一些。第三，DeltaBox 的存档只计调用到返回的时间，后台进行的 CRIU 写镜像不计入，因为它与大模型推理同时进行，不让搜索等待。

结论

结论

智能体相邻两个状态非常相似，DeltaBox 据此放弃整体复制，改为按变化保存和恢复。它没有发明新的存储格式，而是把 Linux 里本来就以“变化”为单位工作的两个机制，overlayfs 的层和 fork 的写时复制，改造成可以频繁、安全使用的存档原语：DeltaFS 让层能在运行中增删，DeltaCR 让冻结的进程能作为模板反复 fork，并用 CRIU 镜像兜底。

结果是存档对智能体没有可见的等待，读档约 1.86 毫秒，SWE-bench 搜索中沙箱开销从 E2B 的 23% 到 48% 降到 1% 到 2%，强化学习训练中 GPU 几乎不再等沙箱。

局限

局限与讨论

网络操作无法回滚，智能体已经发出去的外部请求，比如调用第三方 API、推送代码，撤销不了。Crab 用 eBPF 判断该在什么粒度存档，与 DeltaBox 优化存档机制本身的思路互补。

存档没有可见等待的前提是大模型回复足够慢，能把十来毫秒的暂停盖住；推理很快或连续多步都是不调用大模型的工具操作时，这部分开销会露出来。fork 快路径对智能体程序也有要求：要在安全位置 fork，智能体进程宜为单线程，大模型 SDK 必须交给 NPD，“对智能体透明”背后有这些工程前提。DeltaFS 是修改过的内核模块，虚拟机镜像要用定制内核。端到端实验重放的是事先录好的搜索轨迹，测的是沙箱开销降低了多少，同样时间内能多搜索多少节点、解题率能否提高，是由此推出的结论，没有直接测量。

背景

领域定位

大模型推理服务的性能模拟
硬件级模拟器：LLMCompass、ADOR、ASTRA-sim
系统级模拟器：Vidur、APEX、TokenSim、LLMServingSim

新的推理服务硬件和部署方式在真机上很难逐个试：要有设备，要搭大规模环境，连粗略比较几种方案都要投入大量工程。模拟器因此成为早期探索的主要工具。现有的两类模拟器各缺一块。硬件级模拟器算得细，但只看固定的算子执行，没有 request 到达、组批变化和缓存复用。系统级模拟器有服务层，但前缀缓存、prefill 与 decode 分开部署、异构设备这些近年的主流手段支持有限。

LLMServingSim 2.0 的目标是把这两部分放进一个循环里模拟。它的上一版只支持单个实例，也没有混合专家模型和前缀缓存，2.0 在此基础上扩展到多实例、异构设备和这些服务技术。

背景

基本概念

prefill 与 decode
prefill 一次处理全部输入，主要吃算力。decode 逐个生成 token，每步都要读 KV 缓存，主要受内存带宽、容量和缓存位置限制。两个阶段需要的硬件不同，这是后面拆分部署和 PIM 的出发点。
KV 缓存
模型为已处理的每个 token 存下的中间结果，随输出变长而增长，占显存。
前缀缓存
新 request 开头和已缓存内容相同时，复用这部分 KV 缓存，跳过 prefill。
混合专家模型（MoE）
每层有多个专家子网络，每个 token 只激活其中几个。相对地，每个 token 都走全部参数的模型叫 dense 模型。
PIM
processing-in-memory，内存芯片里带计算单元，数据不用搬到加速器上就能做部分运算。CXL 是一种可以外接大容量内存池的互连。
TTFT、TPOT、ITL、TPS
第一个 token 的等待时间；平均每个输出 token 的时间；相邻 token 的间隔；每秒生成的 token 数。前三个针对单个 request，TPS 针对整个系统。
TP、PP、DP、EP
四种把模型放到多个设备上的方式：张量并行切分每层的张量，流水线并行按层切分，数据并行多放几份副本各接各的 request，专家并行把 MoE 的专家分到不同设备。
主线

问题、方法、验证、用途

问题

服务系统的性能不再单独由硬件或软件决定，而取决于两者运行时的互相影响。现有模拟器无法把异构硬件和拆分部署放在一个运行时框架里模拟。

方法

把服务决策和硬件行为放进一个循环：组批、放置、插入数据搬运，由 ASTRA-sim 算出耗时，结果再影响下一轮决策。硬件用算子级 profile 描述。

验证

和 RTX A6000、H100、TPU 上的真实 vLLM 对比吞吐、延迟、显存、功耗，摘要给出的平均误差是 0.95%，模拟耗时约 10 分钟。

用途

评估手头没有的硬件和部署。案例是给 GPU 加上 PIM，只在模拟器中进行：decode 阶段吞吐提高到 1.43 倍，每 token 能耗降低 14.8%。

近年的两个趋势让这条路径更复杂。一是异构：一个集群里可能有不同代的 GPU、TPU、NPU、PIM 和 CXL 设备，算力、带宽、容量和功耗各不相同。二是拆分：把原本放在一起的部分分开，每种分法都带来新的数据搬运。

System Simulator 算耗时

§IV-D

假设分析

给 GPU 加 PIM 值得吗

Fig. 10§VII-C

这是模拟器的目标用法：评估没有实物的硬件。三种系统都跑 Llama 3.1-8B 和单块 RTX A6000，只有内存不同。两个 PIM 系统把主内存换成 256 个通道、每通道 1 GB 的 HBM2。负载也按 PIM 定制：256 个 request，正好一个通道一个，每个输入 128、输出 512 token。SBI 是 NeuPIMs 提出的子 batch 交替执行。

这个实验没有真机对照，图中数字全部是模拟结果。

(a) 吞吐

前 25 秒以 prefill 为主，收益有限，因为 PIM 主要加速 decode。prefill 结束后，GPU+PIM 的吞吐是 GPU 的 1.43 倍。1.43 倍只是 decode 段的值：从图上估读，全部 request 完成的时间从约 53 秒缩短到约 46 秒，整体只快约 15%。输出更短的负载，收益还会更小，这是本页的推断。

SBI 反而和纯 GPU 差不多。它把 batch 切开，提高了硬件利用率，却让 GPU 实际看到的 batch 变小。只有持续维持 256 以上的超大 batch 时才有效，也就是 26 到 35 秒那段。

(b) 能耗

GPU+PIM 总能耗最低，每 token 能耗降低 14.8%。原因在于跑得更快：恒定功率的部件（CPU、其他）随时间缩短而少耗能，内存能耗只略有增加。SBI 没有提速，多出的 PIM 又要耗能，所以比纯 GPU 还略高。

折线可以用总能耗验算：约 37 kJ 除以 256×512 = 131072 个输出 token，约 0.28 J，和图一致。这说明指标只数输出 token。

这个案例说明模拟器能揭示单看硬件参数看不到的结果：提高硬件利用率的 SBI 没有带来收益，因为它和组批发生了相互作用。不过 PIM 的结论依赖两点假设。负载是配合 PIM 选的（decode 占比高，request 数等于通道数），PIM 的算子数据也没有和实物对过。所以 1.43 倍和 14.8% 应读作“这个设定下的模拟结果”，不宜读作 PIM 的一般收益。

结论

结论

LLMServingSim 2.0 把服务决策和硬件行为放进一个循环：每轮按当前状态组 batch、放置算子、自动插入搬运和同步，再由改造过的 ASTRA-sim 算出耗时和资源，结果决定下一轮。硬件以算子级 profile 接入，因此可以覆盖 GPU、TPU，以及通过外部模拟器接入 PIM。

在 GPU 真机上，全程聚合的吞吐、延迟、显存和能耗误差都在 1.6% 以内，逐时刻吞吐误差 3% 到 5%。相比已有模拟器，它在更多部署上可以运行，且各项指标更均衡；代价是单次模拟要 5 到 10 分钟。它的主要贡献是提供一个公开的共同底座，AgentServeSim 就是一个现成的例子。

局限

局限与讨论

支持的范围明显大于验证过的范围。Table I 里打勾的功能，有几项没有和真机对比过：Fig. 5 每一行只有一种 GPU，所以 Fig. 4(a) 中 H100 配 A100 的异构分离没有验证；CXL 内存池和注意力卸载只有模拟；TPU 只验证了单实例 dense；功耗和显存只在 RTX A6000 上对比过。异构恰恰是这篇论文的主打，在真机上却只能分别验证每种硬件。

负载也比较温和：300 个聊天 request，几十秒跑完，前缀命中率最高约 26%。长上下文、显存持续紧张、智能体这种高度重合的请求，都不在实验范围内。换到这些场景时，误差需要重新确认。此外，模拟器的精度建立在 profile 上，每增加一种模型和设备的组合都要重新 profile 一次；没有实物时，结果的可信度只能和外部硬件模拟器一样。

背景

领域定位

大模型推理服务引擎：vLLM（组批、KV 缓存管理、前缀缓存）
请求级服务模拟器：Vidur、APEX、LLMServingSim
有状态请求链、因果释放：Frontier
program 级、KV 保留与调度可编程：AgentServeSim

推理服务研究有两条线。一条是为智能体设计新的服务策略：InferCept 和 Continuum 研究工具调用间隙里 KV 缓存怎么留，Autellix 按 program 而不是按 request 排队，SMetric 按会话分配机器。另一条是模拟器：用真机上测出的算子耗时，在 CPU 上推算服务性能，省掉昂贵的 GPU 实验。两条线此前没有接上，现有模拟器表达不了前一条线里的那些策略。

背景

基本概念

program
一次智能体任务的完整执行：调用大模型、等工具、再调用大模型，如此交替。论文也把它叫 job，比如解决一个 SWE-bench 问题就是一个 program。
turn
program 中的一次大模型调用（论文也叫 call）。后一个 turn 的输入包含前面所有 turn 的内容。
tool gap
两个 turn 之间等待工具执行的时间。
KV 缓存
模型为已处理的每个 token 存下的中间结果，生成后续 token 时复用。它存在显存里，是推理服务最紧张的资源。
前缀缓存
新输入开头和已缓存的内容相同时，直接复用这部分 KV 缓存，跳过计算。
prefill 与 decode
prefill 一次性处理输入，计算量大；decode 逐个生成输出 token。KV 缓存被丢掉后，下一个 turn 要把整段上下文重新 prefill。
JCT
job completion time，一个 program 从到达到最后一个 turn 完成的总时长，是本文的主要指标。
TP
张量并行度，TP2 表示模型切分到 2 块 GPU 上运行。
主线

问题、抽象、验证、应用

问题

智能体的完成时间取决于推理引擎的三个决定：KV 缓存留不留、下一个 turn 派到哪台机器、和其他 program 谁先执行。在真机上逐个试太贵，现有模拟器又以单个 request 为单位，表达不了它们。

抽象

把 program 看作操作系统里的进程：下一个 turn 何时出现由模拟本身算出来；三个决定做成可替换的策略代码。

验证

让模拟器和真实 vLLM 运行相同的策略和负载，比较完成时间。20 组对照的平均 JCT 误差，在 B200 上不超过 5.5%，在显存紧张的 RTX PRO 6000 上不超过 5.2%。

应用

每个模拟点约 1 个 CPU 核时，真机要占两块 GPU 跑 3 到 6 小时。于是可以大量比较策略组合，并让大模型自动改写策略代码。

§1、§2

请求级模拟

每个 request 的到达时间从记录里读出。request 结束时，KV 缓存立即释放，或按固定规则当普通缓存。

program 级模拟

下一个 turn 的到达时间由模拟算出。KV 缓存归 program 所有，去留由策略决定。

差别在到达时间。下面的例子说明为什么不能照抄录下的时间戳（数字是示意）。一个 turn 执行 2 秒，之后工具运行 5 秒：

策略排队等待完成时刻下一个 turn 到达时刻
录制轨迹时用的策略 A1 s3 s8 s
想评估的策略 B10 s12 s17 s

策略 B 下，下一个 turn 应该在第 17 秒到达，这又改变了那一刻的队列和 KV 池状态。如果按录下的第 8 秒重放，策略本该改变的东西就被固定死了，测不出换一种策略会怎样。KV 缓存也有类似问题：请求级模拟器在 request 结束时就决定了缓存的命运，而对智能体来说，tool gap 本身就是要做决定的时刻。最接近的 Frontier 已经能按完成时间释放下一个 request，但把它固定派到上一个所在的实例，缓存保留也交给引擎自带的前缀缓存，这两处都不能替换成别的策略。

架构：在原模拟器上加一层 program 层

Figure 1

下方大框是 LLMServingSim 2.0 原来就有的部分：服务实例里的设备、性能模型、KV 缓存管理器、组批调度器和执行图生成器，由 ASTRA-sim 算出计算、通信和访存的耗时。它们模拟的是引擎机制。

§3 的三个定义：模拟器为什么需要它们

模拟器要回答的问题是“换一种策略，JCT 会怎样变”。这要求它做到三件事：算出下一个 turn 何时到达，让策略能看到跨 turn 的历史，并规定策略能决定什么。下面三个面板一一对应。

定义

到达时间由模拟算出

式 (2)
下一个 turn 的到达时刻 = 这个 turn 的完成时刻 + 这个 turn 之后的工具耗时

工具耗时、token 数这些属于任务本身的内容从记录里读取，所有策略相同。完成时刻包含排队和执行，随策略变化。两者相加，就把前面例子里的 8 秒和 17 秒都算对了。这个公式就是 program 层的动力来源，到达时间不再是输入，而是运行结果。

结论

结论

AgentServeSim 把模拟的单位从 request 换成了 program，下一个 turn 何时到达、缓存在不在，都是模拟执行的结果，不再照抄录下的数据。它把 KV 回收、队列排序和实例选择做成可替换的策略，和 vLLM 执行相同的策略代码。20 组对照中平均 JCT 误差不超过 5.5%。

模拟器把评估一个策略的成本从数小时的双卡 GPU 时间降到约一个 CPU 核时，使系统地比较策略、让大模型自动搜索策略成为可能。比较的结果说明排队对 JCT 的影响大于保留，两者必须配合设计。

局限

局限与讨论

验证只用了一个服务实例，routing 尚未与真实系统对照；模型只有 Llama-3.1 的两个规模，负载两类，策略组合只验证了固定 TTL 加 PLAS 一种。换成混合专家模型、更长的上下文或 prefill 与 decode 分开部署的架构，准确度需要重新确认。演化出的策略针对特定的负载和硬件，本来就不追求通用。

策略扫描和搜索的结果都只来自模拟器，收益（0.5%、2.8%、5%）和拥堵时单个 program 7% 到 11% 的模拟误差在量级上接近，更适合看作模拟器能充当搜索评分器的可行性演示。长期价值更大的是那层接口，它让 InferCept、Continuum、Autellix 等系统中分散的策略可以放在一起组合比较。

结论

结论

智能体的成本可以拆成三个相乘的因素：调用次数成倍增加，每次调用的输入随历史累积而变长，调用之间夹着让 GPU 空等的工具时间。前缀缓存和并发处理能缓解后两个因素。一块 GPU 能撑的 QPS 仍只有聊天的几分之一，而测试时扩展本身面临收益递减，继续堆计算换来的准确率越来越少。

据此，智能体设计应从堆计算转向考虑成本的推理。可行的方向包括：量化、蒸馏，按角色混用大小模型；按任务难度动态分配计算；在推理系统上采用分层 KV 缓存与缓存压缩、利用智能体输出格式固定的特点做推测解码、把 prefill 和 decode 分开部署以减少互相干扰。

局限

局限与讨论

业界对智能体还没有公认的服务质量标准，分析没有、也难以针对某个具体的延迟目标，它描绘的是不同配置下准确率和成本的取舍。实验规模也不大：每种配置 50 道题，A100 40GB，vLLM 0.6.6，最大 70B 模型。

换成新的硬件、推理引擎和更大的模型，绝对数字会变，但准确率收益递减、尾部延迟上升、工具执行时 GPU 闲置、前缀缓存对智能体特别重要这些规律与具体硬件关系不大，参考价值更持久。

问题、洞见、设计、效果

问题

只保存对话或文件的轻量恢复便宜但常常恢复错；每轮保存整个沙箱的做法正确但太贵，多个沙箱挤在一台机器上时更扛不住。

根源

智能体框架看得到工具调用，看不到它对操作系统的实际影响；操作系统看得到状态变化，却不知道哪一轮结束了、哪些变化值得保存。结果是超过 75% 的轮次其实什么都不用存。

设计

把智能体当黑盒，在每一轮结束时观察它在操作系统里留下的实际变化，据此决定这一轮存什么；存档与等待大模型回复并行；一台机器上所有沙箱的存档任务统一排队调度。

效果

恢复正确率从只保存对话时的 8% 提到 100%；最多 87% 的轮次完全跳过存档；每个任务注入一次崩溃，总耗时仍只比不出故障、不做存档时多 1.9% 以内。

设计

架构：宿主机上的透明运行时

Figure 5

中间是三个沙箱，分别跑着 Claude Code、SWE-agent 和 Codex。黄色是 Crab 的组件：用户态的 Coordinator 架在智能体和LLM API 之间，所有 LLM request 和回复都经过它；内核里的 Inspector eBPF 程序观察每个沙箱的系统调用，用户态的 Inspector 守护进程汇总结果；右侧的 C/R Engine 包含调度器、执行存档的 Worker 和管理版本的 Manager，底层调用 CRIU 和 ZFS。智能体和 CRIU、ZFS 都不需要修改。

组件放在宿主机上有它的道理。如果每个沙箱配一个旁路进程，它只能看到自己的沙箱，无法协调整台机器上的存档流量；如果只在内核里做，能看到操作系统的变化，却不知道一轮何时结束、大模型何时在思考，也就没法把存档藏进等待时间。只有宿主机上的运行时既能拿到轮次的语义（通过拦截 LLM request），又能看到所有沙箱的内核事件。

设计

一轮结束时发生了什么

Figure 6、§5.1

横轴是时间，每一行是一个参与者：智能体与沙箱、Coordinator、调度器、Worker、Manager、Inspector、大模型服务。第 i 轮的工具执行完，智能体向大模型发 LLM request，Coordinator 拦下（1）并立刻转发（2），这个 LLM request 的出现就标志着第 i 轮结束。随后它问 Inspector 这一轮改了什么（3），决定跳过还是存文件、存进程或两者都存，把任务交给 C/R Engine（4），调度器安排 Worker 去做（5）。这些都发生在大模型思考的那几秒里。

大模型的回复回来时，Coordinator 再次拦下（6）。如果第 i 轮的存档已经完成，回复立刻交给智能体，第 i+1 轮开始（7）；如果还没完成，就扣住回复，等存档做完再放行。这道闸门保证任何一轮开始前，上一轮的状态都已经安全落盘，同时把存档的等待只暴露在它超过大模型思考时间的那部分。若回复已到而存档未完成，Coordinator 还会把这个任务提升为高优先级，让调度器先处理已经卡住智能体的存档。

设计

Inspector：判断这一轮改了什么

Figure 7、§5.2

四行各是一个文件或进程从上次存档（灰色箭头）到本次查询（黄色箭头）的经历，橙色长条是它的存在期，斜线块是被修改的时段。第一行在上次存档后被创建，但查询前就消失了，判定为没变；后三行在查询时仍然存在、新建或被改过，判定为有变化。

这就是“净变化”的含义：只看从上次存档到现在，最后留下了什么。shell 每执行一条命令都会派生短命的子进程，很多工具也会写临时文件再删掉，如果把这些都算作变化，几乎每一轮都得存档。文件方面，eBPF 挂在系统调用入口和出口，记录沙箱内进程的创建、删除、改名和写入，标准输出这类特殊句柄除外，守护进程据此计算净变化。进程方面，用 cgroup 判断沙箱里是否有进程新增或退出，对一直活着的进程，读它的软脏页标记看有没有写过内存。每次存档完成后把记录和标记清零，作为下次比较的起点。

设计

C/R Engine：调度、执行、版本

Figure 8、§5.3

左图横轴是轮次，FS 行和 Proc 行标出哪些轮存了文件、哪些轮存了进程。第 0 轮两者都存，得到恢复点 C0=(P0, F0)；第 1 轮只改了文件，新的恢复点是 C1=(P0, F1)，进程部分沿用第 0 轮的；第 2 轮什么都没改，不产生新恢复点。由于每次存档可能只覆盖一半状态，单个存档文件本身不能用来恢复，Manager 把“最近的进程镜像加最近的文件快照”组合成一个版本，形成类似 git 的版本历史，可以回到其中任意一个。右图是一次存档的生命周期：排队、写入、组合版本、成功；任何一步出错或被打断就标为失败，绝不会被当作恢复点使用。

调度器用两个先进先出队列。新任务进普通队列，因为它的耗时还能被大模型思考时间盖住；一旦对应的回复已经回来，任务被提升到高优先级队列，Worker 总是先处理高优先级的。每个任务迟早会因回复到达而被提升，或者在此之前已经完成，不会饿死。这样，有限的磁盘带宽优先用在已经让智能体等着的存档上。文件快照用 ZFS，进程存档用 runc 调用 CRIU，Worker 的数量设成刚好跑满磁盘带宽。

设计

两种部署方式下的恢复

Figure 9、§6

智能体在沙箱外时，沙箱可能在一条命令执行到一半时崩溃。存档只在轮次边界进行，恢复出来的沙箱里没有这条命令的痕迹，而外面的智能体正等着它的结果。Coordinator 在转发每条命令前先记日志，恢复后发现有未完成的命令就重新执行，智能体只看到命令正常返回。

智能体在沙箱内时问题更微妙。智能体进程每一轮都会改自己的内存，如果把它当普通进程跟踪，几乎每轮都要做昂贵的进程存档，所以 Crab 不跟踪智能体进程本身。代价是恢复时智能体的内存可能比文件旧。图中最新的恢复点是 C4=(P2, F3)，智能体的记忆停在第 2 轮，文件已到第 3 轮。第 3 轮执行的是 echo "b" >> foo，如果让智能体照常继续，它会再追加一次，文件变成 “abb”。Coordinator 缓存了所有 LLM request 和回复，恢复后智能体重发第 3 轮的 LLM request时，Coordinator 认出这是重复的 LLM request，直接从缓存返回当时的回复，而不真正去执行动作，直到智能体的进度追上文件状态，foo 的内容保持正确的 “ab”。

结论

结论

智能体沙箱里积累的操作系统状态，现有的检查点机制要么抓不全，要么抓得太多。原因在于智能体框架和操作系统各自只掌握一半信息。Crab 的做法是站在两者之间：从LLM request 里得到“一轮结束了”的信号，从内核里得到“这一轮实际留下了什么”的信号，二者结合，只在需要时以需要的粒度存档，把存档藏进大模型思考的时间，并在整台机器的范围内调度存档流量。

结果是在 Terminal-Bench 和 SWE-bench 上恢复正确率从 8% 提到 100%，最多 87% 的轮次免于存档，每个任务崩溃一次时总耗时仍在理想情况的 1.9% 以内。更一般地，对一个看不透内部逻辑的程序，它在操作系统里留下的可见痕迹可以作为轻量的语义信号，同样的思路可用于沙箱的调度、资源隔离和安全审计。

局限

局限与讨论

实验按录好的轨迹确定性重放，并只挑选了能顺利完成的任务。这样做能干净地衡量存档本身的开销和正确性，但没有覆盖真实运行中模型随机性、任务失败等情况；主动回滚、推测执行两个案例也是在录好的轨迹上模拟出来的，智能体实际学会使用回滚工具后的效果还需要真实运行来验证。Inspector 的准确率是在 iFlow-cli 的 2,063 个轮次上人工标注得到的，其他智能体和任务类型上是否同样零漏报，没有单独报告。

Crab 判断的是“状态有没有变”，进程一旦变了仍要做完整的 CRIU 存档，这一部分的耗时（接近一秒）和内存大小成正比，也是长尾延迟的来源；大模型推理变快时，能掩藏它的时间会缩短。智能体在沙箱内时不跟踪智能体自身，恢复依赖缓存的大模型回复做快进，这要求智能体在相同输入下会重发相同的 LLM request。系统依赖宿主机上的 ZFS、CRIU 和 eBPF，实验只使用了 runc 容器，在 Firecracker 这类轻量虚拟机沙箱上的表现没有评估。
