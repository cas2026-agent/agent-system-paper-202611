背景

智能体为什么要频繁回滚

Figure 1

纵轴是 SWE-bench 的通过率。左图橙色是一条路走到底的智能体，蓝色是用蒙特卡洛树搜索（MCTS）的智能体，三个模型都提高了 4.7 到 6.7 个百分点；右图橙色是原始模型，蓝色是强化学习训练后的模型，提高了 19.2 到 29.4 个百分点。搜索和训练是目前提升编程智能体最有效的两条路，而两者都要求能快速地保存和恢复沙箱的完整状态（文件和进程）[[abstract-cr]]。

两种需求的形态不同。树搜索是纵向的，要随时回到任意一个历史节点；Best-of-N 是横向的，要把初始沙箱快速复制 N 份[[two-axes]]。强化学习训练每一步都要从一个准备好的状态开出几十到上百个沙箱，现在靠新建 Docker 容器或从虚拟机快照恢复，单次就要几百毫秒到几秒[[rl]]。保存和恢复的次数随搜索深度、分支数和训练步数成倍增长，单次开销哪怕只有一秒，总量也会压过模型推理本身。

背景

基本概念

智能体沙箱
隔离执行智能体动作的容器或轻量虚拟机。本文的沙箱里常驻一个智能体进程，所以沙箱状态包括文件系统和这个进程的内存。
检查点与恢复
把某一时刻的完整状态保存下来，之后能回到这个状态。对智能体而言就是回滚。
overlayfs
Linux 的叠层文件系统。下面是只读的 lower 层，上面是可写的 upper 层，程序看到的是叠加结果；修改文件时先把它从下层复制到上层（copy-up）。原生实现的层在挂载时固定，运行中不能增删。
写时复制
多方共用一份数据，有人要改时才把被改的部分复制出来。fork、reflink、copy-up 都基于这个思路。
XFS reflink
文件级写时复制。复制文件时只增加对数据块的引用，写入时才按 4 KB 的块分配新空间。
fork
Linux 创建子进程的系统调用，只复制页表，内存页由父子进程写时复制共享，所以耗时和进程占用的内存大小基本无关。
CRIU
把运行中的进程完整保存成镜像文件、之后再恢复出来的工具。lazy-pages 模式下恢复时按需读回内存页。
Firecracker
AWS 开源的轻量虚拟机，常用于 serverless 和智能体沙箱。它的快照包含内存和设备状态，不包含磁盘。
E2B、CubeSandbox
两个面向智能体的沙箱产品。E2B 靠暂停整台虚拟机做快照；CubeSandbox 用 reflink 卷加内存脏页跟踪做写时复制快照，但需要定制的宿主机内核。
主线

问题、洞见、机制、效果

问题

编程智能体改的是真实的操作系统状态，改对话历史撤销不了[[real-os]]。树搜索不停回退，昂贵的恢复反复出现在等待路径上[[critical-path]]，而现有方案保存和恢复都要复制整个状态[[challenge2]]。

洞见

相邻两次存档之间只多了几个文件、改了少量内存页，只需保存这部分变化[[insight]]。文件系统和进程内存被当作一对按变化保存的状态，称为 DeltaState。

机制

DeltaFS 让 overlayfs 能在运行中插入新的可写层[[ioctl]]；DeltaCR 用 fork 出来并冻结的进程当模板，恢复时再 fork 一份，只复制页表[[fork-fast]]。两者在相同时刻成对保存。

效果

存档约 10.83 毫秒，与大模型推理重叠，智能体不用等；恢复约 1.86 毫秒。SWE-bench 搜索中花在沙箱上的时间占比从 23% 到 48% 降到 1% 到 2%[[e2e]]。

问题

文件和进程必须一起回滚

§2.2、§2.4

只回滚文件

进程内存里的对话历史和工具输出还记着那些已经不存在的磁盘修改。

只回滚进程

进程回到了过去，却在另一条分支留下的文件上继续干活。

两种错位都会让一个搜索节点每次展开的结果不一样[[coupling]]，树搜索赖以成立的确定性就没了。进程状态里装的是大模型的对话历史、工具的输出、打开的文件描述符；如果回滚时丢掉进程、只恢复文件，就只能从头重新执行之前的所有命令来重建它，代价随搜索深度线性增长。所以一个存档必须是“文件状态加内存状态”这一对，并且两者对应相同的时刻。

据此，设计目标有四个：文件与进程联合保存和恢复，耗时在毫秒级；保存时复制的数据量只和实际改动多少有关，和工作目录大小无关；回到任意历史存档的时间是常数；对智能体透明，不改它的代码、不重启、不丢上下文。

现有方案可以分成三类。前四行只管文件，进程内存直接丢弃，回滚后要重启进程并重放命令。Firecracker 和 E2B 以整台虚拟机为单位做快照，内核、系统守护进程的内存都被一起保存，粒度太粗，耗时随虚拟机内存增长；Firecracker 的快照还不含磁盘，文件系统要另外处理。DSec 不能回到任意历史点，只能重放日志里缓存的输出。最接近需求的是 CubeSandbox，五十到六十多毫秒，文件和进程都覆盖，但它要求更换宿主机内核，在云上部署门槛很高。

表里没有一种方法同时做到按进程粒度、文件与内存联合、毫秒级，这就是 DeltaBox 要填的位置。CubeSandbox 的数字是厂商公布的。

洞见

只保存相邻两次存档之间的变化

Figure 2

图从左往右是时间。上排每个方框是一个时刻的沙箱，绿色格子代表内存状态，黄色格子代表文件状态；下排是每次存档（deltaCheckpoint）真正保存的内容，只有这一步新改动的那几个格子。最右边智能体决定回到 Step-1，读档（deltaRestore）丢掉 Step-1 之后的改动，用到 Step-1 为止的变化拼出当时的状态。

这个想法之所以能落地，是因为 Linux 里已经有两个现成的“变化”表示。overlayfs 的每一层本来就只记录相对下层的改动，冻结当前可写层、在上面再放一层，就等于存了一个文件增量。fork 出的子进程和父进程靠写时复制共享内存，冻结住的子进程就是父进程那一刻内存的快照，只占后来被改动的那些页。缺的是两样东西：overlayfs 不允许运行中加层，fork 出来的进程也不总是能安全地被冻结和再次 fork。DeltaFS 和 DeltaCR 分别补的就是这两处。

文件状态的存档要满足什么

§1、§2.2、§2.3
要求来自智能体的哪种行为
耗时和空间不随工作目录变大而增长工作目录是整个克隆下来的仓库，动辄数十万个文件[[workdir]]
新增、修改、删除都能撤销每次编辑源码、pip install、改配置都在改文件，rm 会删文件
每次存档在毫秒级MCTS 每展开一个节点就存一次，一次搜索几十上百次
回到任意历史节点的时间是常数树搜索会跳回很早的分支，回退深度不固定
不卸载、不重启智能体进程一直开着文件，甚至把文件映射进内存
与内存快照对应相同时刻文件和进程必须成对回滚，否则两者错位

文件这一半的难处在于规模和频率的组合。仓库有数十万个文件，智能体每一步通常只动其中几个：改一个源文件里的几行，或者 pip install 往 site-packages 里新增一批文件。存档如果按“目录有多大”付出代价，在搜索的频率下就承受不起；它应该只按“这一步改了多少”付出代价。回滚也一样，跳回十步之前的节点不应该比跳回一步之前更慢。

现有的文件工具都在某一项上不达标，它们的共同做法是复制[[challenge1]]，并且只管文件、丢掉进程内存[[fs-tools]]。复制目录的成本与目录大小成正比。git stash 或分支只管版本库跟踪的文件，装进 site-packages 的依赖、构建产物、被 .gitignore 忽略的文件通常都不在它的范围内，而这些恰恰是 pip install 和编译改动的地方。Docker commit 把容器的改动打包成镜像层，回滚要用新镜像重启容器，恢复需要 1 到 10 秒。Btrfs、ZFS 和 LVM 快照是块级写时复制，速度不差，但要把沙箱的存储整体换成这些文件系统[[storage-stacks]]，并且快照以整个卷为单位。

overlayfs 为什么天然是增量

Figure 4(a)
程序的操作overlayfs 的处理可写层里留下什么
读文件从上往下逐层查找，用找到的第一个什么都不留
第一次改下层的文件先把整个文件复制到可写层（copy-up），再改副本改过的文件
新建文件直接写在可写层新文件
删除下层的文件在可写层放一个同名的“删除标记”（whiteout），遮住下层文件删除标记

overlayfs 是 Linux 的叠层文件系统，Docker 容器的文件系统就建立在它上面。它把一个只读的下层（lower，可以有多层）和一个可写的上层（upper）叠成一个统一的视图交给程序。程序以为自己在读写一个普通目录，实际上所有修改都只落在上层，下层永远不变。

从上表可以看出，上层里装的恰好是“相对于下层的全部改动”：改过的文件、新文件、删除标记，没有改动的文件一个都不在里面。这正是存档需要的增量。如果在某一刻把当前上层冻结成只读，再在它上面放一个新的空上层，被冻结的那一层就是“到这一刻为止这一步的改动”，相当于做了一次存档，而且不复制任何未改动的数据。回滚则是把上面几层拿掉：被拿掉的层里的修改、新文件、删除标记一起消失，下层原来的文件自动重新可见，被删的文件也回来了。存档和回滚都只是改变“哪些层叠在一起”，与仓库里有多少文件无关。

第一行是表面上的限制，后面几行是真正动手改层时才会暴露的问题，它们都源于原生 overlayfs 默认“层在挂载后不会变”。内核为了速度缓存了很多“这个文件在哪一层”的信息：打开的文件句柄、目录项缓存、正在进行的读操作手里的层数组。一旦允许运行中换层，这些缓存全都可能过期。最危险的是已打开的文件。举个例子，智能体在第 3 步打开一个日志文件不断追加，第 3 步结束时做了存档，旧上层被冻结。如果不处理，第 4 步的追加仍然顺着文件句柄写进已冻结的那一层，存档被悄悄改掉，日后回滚到第 3 步时，看到的却是包含第 4 步内容的文件。DeltaFS 用一个全局计数器 checkpoint_gen 解决：每存档一次加一，每个文件记住自己最后一次定位时的代号，写入路径上两者一致就直接写，不一致就按新的层组合重新找到位置，必要时先 copy-up 到新上层再写。这个检查只在写入时做，读和没变过的文件不受影响，所以叫“惰性切换”。

写放大的问题则来自 copy-up 的粒度。智能体典型的编辑是改 12 到 65 KB 文件中的几行，原生 copy-up 每次都复制整个文件；更糟的是，这个文件在后续每一步再被改动，都要从下层再完整复制一份到新的上层，存档越多，这个文件的副本越多。reflink 让 copy-up 变成“新建一个文件，引用原文件的所有数据块”，只有真正改动的 4 KB 块才分配新空间。降级旧上层时用改名而不是复制，文件的块引用关系原样保留，于是一个连续很多次存档都没改过的块在磁盘上始终只有一份。实测中不开 reflink 时写入量随文件大小线性增长，开了以后几乎是常数。

还有一个问题文中没有讨论：每次存档都会多出一个下层，查找文件时要从上往下逐层找，层数越多查找路径越长，而 Linux 内核对 overlayfs 的下层数量设有上限（OVL_MAX_STACK，为 500）。一次 30 轮的搜索影响不大，但更长的搜索或训练需要把不再访问的层合并或回收，论文的垃圾回收只针对进程镜像，对文件层如何回收没有说明。

存档时，CRIU 让智能体暂停约 11 毫秒拍一张内存照片，写进内存盘；DeltaFS 在这个暂停的瞬间把当前可写层改成只读并放上新层。两件事看到的是相同的冻结时刻，所以文件和内存对得上。拍完照后，智能体在主循环的安全位置 fork 一次，父进程继续干活，子进程立刻把自己冻结，成为这次存档的模板。如果 CRIU 拍照失败，刚才的加层操作会被撤销并报错，不会留下文件和内存不匹配的半成品。

存档对智能体几乎没有代价，是因为它发生在智能体等待大模型回复的时候：一次回复要几秒，暂停只有十来毫秒[[sigstop]]。读档则没有这样的掩护，搜索必须等它完成才能继续，所以 DeltaBox 把读档压到只剩“换层”和“fork”两个动作。读档后的进程从存档那一刻的下一条指令继续执行，察觉不到自己被回滚过。

系统

DeltaFS：运行中可以加层的 overlayfs

Figure 4、§4.1

左图是传统 overlayfs：沙箱镜像在最底下，中间是只读层，上面是可写层，程序看到的 a、b、c 三个文件是各层叠加的结果。右图是 DeltaFS：存档时原来的可写层被冻结成只读的 Step-1 层，上面放一个新的可写层 Step-2，之后的改动都落在新层里。存档就是加一层，回滚就是去掉上面若干层，耗时与文件多少无关。右上角红色的 checkpoint_gen 是每存档一次加一的计数器。

一次换层按这样的顺序进行：用户态先把当前上层目录改名，作为新的只读下层；再建一个空目录作为新上层；然后调用 ioctl。内核解析新的层配置，为每个目录建一个私有挂载，组成新的层数组，在自旋锁保护下原子地替换旧数组，把 checkpoint_gen 加一，并把缓存的目录项标记为需要重新验证。被降级的旧上层放在所有下层的最上面，存档前已经 copy-up 过的文件因此仍能被找到；旧数组等两次存档之后、确认没有读操作还在使用时才释放。整个过程不搬动任何文件数据，DeltaFS 的这部分改动约 565 行 C。回滚走的是相同的 ioctl，只是把层组合换成目标存档记录的那一组。

DeltaCR：恢复时间与进程大小无关

Figure 5、§4.2

虚线左边是存档，右边是读档。存档时 GSD 一边让 CRIU 在后台生成镜像链，一边通过管道请求活跃的智能体 fork 出模板放入模板池。读档时先用 ioctl 换层，再查模板池：命中（Hit）就从模板 fork 出新的智能体，没命中（Miss）就用 CRIU 从镜像恢复。

快路径快在 fork 只复制页表、不复制内存内容[[fork-fast]]，占几百 MB 和占几 MB 的进程 fork 起来差不多快。fork 在主循环的安全位置进行，此时没有进行中的系统调用和写了一半的文件，并且只复制调用线程，避开了多线程程序 fork 后可能出现的死锁。CRIU 镜像是兜底：模板占内存，模板池有上限，被淘汰的模板仍有镜像可用，只是慢一点，不会出错[[evict]]。镜像本身的清理要考虑搜索算法，MCTS 随时可能重新选中很久没碰过的节点，按“最近没用”删除会导致恢复失败、重选、再失败的循环，所以只清理搜索已经判定不会再访问的节点。

fork 之后子进程第一次写某一页时才真正复制，每次几微秒，Python 智能体恢复后第一轮会写很多页。GSD 在另一个 CPU 核上把子进程的可写页挨个读一字节再写回，提前把复制做完；来不及处理的页照常复制，最坏也不比不预热差[[async-warm]]。另一个问题来自大模型 SDK，它们在后台开着 HTTP 连接池和线程池，带着这些线程 fork 会导致半开的连接、错乱的连接池状态和永久死锁[[npd]]。DeltaBox 把 SDK 和网络连接全部移到单独的 NPD 进程，智能体只通过定长管道消息与它通信，模板里便不再有危险的线程。

系统

其他设计与实现

搜索框架常靠跑测试给节点打分，测试会留下 __pycache__ 一类的临时文件。DeltaBox 在跑测试前存档、读完结果后无条件回滚[[test-iso]]，测试便不会污染沙箱。

存档是按进程而非按虚拟机做的，一台虚拟机里可以放多个智能体各自独立回滚，整机快照做不到这一点。每台 Firecracker 虚拟机运行带 DeltaFS 模块的定制 Linux 6.8 内核，宿主机通过 virtio-vsock 与 GSD 通信。DeltaFS 的 ioctl 约 565 行 C，DeltaCR 约 1200 行 Python。LangGraph 自带的存档只保存图的逻辑状态，撤销不了已执行的命令，DeltaBox 提供了适配器，让图状态存档时同时触发沙箱存档。

实验的整体逻辑

实验围绕两个用途展开，先看 MCTS 搜索（沙箱要频繁回滚），再看强化学习（沙箱要一次开出很多），然后拆开 DeltaBox 看开销来自哪里。所有方案都同时保存文件和进程，否则 MCTS 的回滚结果不确定，比较没有意义。

表在测什么。用 Qwen3-Coder-30B 在 SWE-bench Verified 上跑 MCTS 搜索，把搜索过程录下来，再在五种方案上重放。搜索过程中每调用一次存档或读档，算一个“事件”。表里的每个数是这类事件的平均“阻塞时间”，单位是毫秒，即从调用开始到调用返回、搜索能够继续的这段时间。ck 是 checkpoint，即存档；rs 是 restore，即读档。读档比存档更要紧：读档不返回，下一轮 MCTS 就无法开始[[t2-critical]]。

列名的读法
每个方案都要同时恢复进程和文件，列名写成“进程怎么恢复 + 文件怎么恢复”[[t2-naming]]。
replay+cp
文件用 cp，即 Python 的 shutil.copytree 把整个仓库目录复制一份；进程用 replay，即不保存内存，读档时重新启动智能体、加载代码索引，把录下来的动作按顺序再执行一遍，把内存状态重新算出来。
FC-Diff+dm
进程用 Firecracker 虚拟机的增量快照（Diff），存档时只保存自上次以来变脏的内存页，保存的是整台虚拟机的内存；文件用 dm-snapshot，即 Linux device-mapper 提供的块设备写时复制快照。
CRIU+cp
进程用 CRIU 把智能体进程的内存写成镜像，读档时从镜像恢复；文件同样用 copytree 复制目录。
E2B (diff)
自己部署的开源 E2B，暂停整台虚拟机，保存变脏的内存页和磁盘块，读档时恢复虚拟机。它本身就同时覆盖进程和文件。
DeltaBox
进程用 DeltaCR（CRIU 镜像加 fork 模板），文件用 DeltaFS（overlayfs 换层）。

四行负载和最后一行。SWE-bench 的任务按项目特点分成四类：Django 智能体进程占内存大；SymPy 以读文件为主；科学计算类（Astropy、Matplotlib、scikit-learn、Xarray）大量使用 NumPy，内存状态重；工具类小项目（pylint、requests、pytest）最轻。四类分别有 4、4、10、6 条搜索轨迹，每条重放两次[[t2-weights]]。最后一行把所有事件放在一起求平均，没有对四行简单平均，所以事件最多的科学计算类对它影响最大。

表注里的特殊口径。有三处数字的含义和其他格子不同，读表时要注意。第一，replay+cp 只在每条轨迹开头复制一次原始仓库，之后的节点都不再复制，表里的 ck 是这一次复制的耗时；它的读档在重放时直接使用录好的大模型回复，不计大模型的时间[[t2-replay]]，所以 28 秒全部是重启程序、重新执行命令本身的开销，算是下限。第二，FC-Diff+dm 的存档平均值里包含每条轨迹开头一次完整的虚拟机快照[[t2-fc]]，会把平均值抬高一些。第三，DeltaBox 的存档只计调用到返回的时间，后台进行的 CRIU 写镜像不计入[[t2-async]]，因为它与大模型推理同时进行，不让搜索等待。

从表里能读出什么。横着看每个方案的两列，可以看出它把成本放在哪一头：replay+cp 存档便宜、读档极贵；FC-Diff+dm 存档 0.5 到 0.7 秒，读档要沿着祖先链合并增量，约 3 秒；CRIU+cp 两头都在几百毫秒；E2B 两头都在 0.5 到 1 秒；DeltaBox 两头都在毫秒级。竖着看每一列在四类负载间的变化，可以看出它对什么敏感：E2B 的读档在四类负载上都是 790 到 952 毫秒，几乎不变，因为它每次都暂停和恢复整台虚拟机，和智能体进程大小关系不大；CRIU+cp 的读档在进程最大的 Django 上最慢（1116 毫秒），在工具类小项目上最快（427 毫秒），因为 CRIU 要把内存从镜像里读回来；DeltaBox 也是 Django 最慢、小项目最快，但只在 1.46 到 2.23 毫秒之间，它读档的主要开销是 fork 复制页表，页表大小随进程内存增长[[fork-rss]]，所以仍有轻微差别。

结论

结论

智能体相邻两个状态非常相似，DeltaBox 据此放弃整体复制，改为按变化保存和恢复[[conclusion]]。它没有发明新的存储格式，而是把 Linux 里本来就以“变化”为单位工作的两个机制，overlayfs 的层和 fork 的写时复制，改造成可以频繁、安全使用的存档原语：DeltaFS 让层能在运行中增删，DeltaCR 让冻结的进程能作为模板反复 fork，并用 CRIU 镜像兜底。

结果是存档对智能体没有可见的等待，读档约 1.86 毫秒，SWE-bench 搜索中沙箱开销从 E2B 的 23% 到 48% 降到 1% 到 2%，强化学习训练中 GPU 几乎不再等沙箱。

局限

局限与讨论

网络操作无法回滚[[no-net]]，智能体已经发出去的外部请求，比如调用第三方 API、推送代码，撤销不了。Crab 用 eBPF 判断该在什么粒度存档，与 DeltaBox 优化存档机制本身的思路互补[[crab]]。

存档没有可见等待的前提是大模型回复足够慢，能把十来毫秒的暂停盖住；推理很快或连续多步都是不调用大模型的工具操作时，这部分开销会露出来。fork 快路径对智能体程序也有要求：要在安全位置 fork，智能体进程宜为单线程，大模型 SDK 必须交给 NPD，“对智能体透明”背后有这些工程前提。DeltaFS 是修改过的内核模块，虚拟机镜像要用定制内核。端到端实验重放的是事先录好的搜索轨迹，测的是沙箱开销降低了多少，同样时间内能多搜索多少节点、解题率能否提高，是由此推出的结论，没有直接测量。
