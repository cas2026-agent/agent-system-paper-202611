背景

领域定位

§1、§2.2
智能体负载的系统研究
能力基准：SWE-bench、WebArena、OSWorld，只记任务是否完成
智能体服务系统：各自只在一到三种应用上评估
测量研究：在一套固定的部署上记录轨迹和开销
十个应用、可替换的部署、加上生产轨迹：AgentSysBench

智能体把一次用户请求变成一段长时间的执行：反复调用模型、调用工具、操作环境、更新状态。现有的服务系统沿用为普通推理设计的假设，而这类负载的时间、开销和瓶颈到底出在哪里，还没有系统的刻画[[abs-gap]]。

论文指出已有工作的三处空缺：智能体服务系统只研究少数几个应用，而且彼此的工具、模型和编排假设不兼容[[gap-three]]；能力基准只看任务是否完成，几乎不记录系统层面的信息[[gap-cap]]；已有的测量研究都固定在一套部署上，没有把硬件分配和组件放置当作变量。

背景

两个模型：负载 W 与服务系统 S

§2.1、§2.2

论文把测到的系统行为记作 Y = Φ(W, S)，即负载和服务系统共同作用的结果。一个应用，配一个慢模型就显得受模型限制，配一个慢沙箱就显得受工具限制，上下文很大时受状态限制，远程部署时受网络限制[[interaction]]。所以只控制负载、不控制部署，测到的瓶颈可能来自部署；反过来，只换部署、不换负载，优化可能只对那一种配置有效。

符号含义例子
W = ⟨R, T, M, O⟩智能体负载：一个应用产生的执行的分布
R请求分布：场景、难度、输入大小短文档问答、分钟级的网页任务、数小时的研究任务
T工具与环境沙箱、浏览器、向量数据库、搜索服务
M模型选择与推理策略DeepSeek-V4-Pro 还是 V4-Flash
O编排结构固定流水线、ReAct 循环、规划者与执行者
S = ⟨H, C, A⟩服务系统
H硬件资源GPU、CPU 核数、内存、网络带宽
C每个组件怎么服务SGLang 还是 vLLM，batch 大小
A部署架构组件放在一台机器上还是分开、走网络

论文中的 request、session、execution 有层级关系：一次用户请求（request）引发一次智能体执行（execution），执行沿途记下的事件构成一条执行轨迹；生产环境中一个会话（session）可以包含多次用户请求，中间还有人在思考和确认。

主线

问题、工具、六个发现、四个设计探索

问题

智能体负载的延迟、资源和成本花在哪里，服务系统应该照顾哪些部分。

工具

十个应用、可替换的部署栈、按组件计量的统一埋点，再配上三个线上应用的一天生产轨迹。

六个发现

前三个来自受控实验：执行重且非模型部分常占主导、跨组件的异构、瓶颈会转移。后三个来自生产轨迹：长时间闲置但状态仍在、控制面开销、跨请求的重复。

设计探索

按任务拆分服务、按通信量放置组件、闲置时卸载沙箱、缓存工具结果，每项都是单独的原型验证。

实验规模：受控实验共 4641 次请求、64924 次模型调用、118274 次工具调用；生产轨迹是一天内的 178799 个会话[[scale]]。论文强调生产轨迹是对受控实验的补充，不用来验证受控实验的结论[[prod-compl]]，因为受控实验按合成的到达过程逐个跑完任务，看不到用户的思考时间、闲置时仍占着状态的会话和不同用户之间的重复请求[[prod-need]]。

工具

部署栈与埋点

Fig. 2§3.2、§3.3、§3.5

每个组件放在一个 Docker 容器里：负载生成器（负责 R 和到达过程）、编排器（O）、模型服务（M）、沙箱和向量数据库（T）。设计原则是因素隔离，改一个因素时其余尽量保持不变[[isolation]]，例如把 SGLang 换成 vLLM 而工具路径不动，或把一个本地函数调用改成远程服务来研究拆分。

能改源码的应用（RAG、HuggingGPT、DeepResearch、Mini-SWE、WebAgent）直接加注解记录；不能改的第三方应用通过模型和工具代理、沙箱钩子来记录[[blackbox]]。两条路径写出相同格式的逐操作记录，资源曲线由 cAdvisor、DCGM 和 Prometheus 采集。

默认部署：除 RAG 外，每个应用跑在一台 GPU 服务器上。只有 Mini-SWE 用 SGLang 自己部署 DeepSeek-V4-Pro，其余应用调用阿里云百炼的模型 API[[default]]。RAG 跑在一台 8 张 4090D 的服务器上。

发现一：执行重、有状态，非模型部分常占主导

从五个方面衡量一次智能体执行有多重：端到端延迟和时间构成（Fig. 3、Fig. 4）、token（Fig. 5）、需要保留的状态（Fig. 6）、数据搬运（Fig. 7）和按量计费的成本（Fig. 8）。这些实验都是一个请求接一个请求地顺序执行。

实验

延迟有多长，时间花在哪里

Fig. 3Fig. 4§4.1

Fig. 3每个请求的端到端延迟

注意三段纵轴的单位不同：RAG 以秒计（约 5 到 6.5 秒），中间八个以分钟计、对数刻度，Pi-AutoR 以小时计（中位数接近 4 小时）。普通聊天请求在一秒上下，这里多数应用的中位数在几分钟。

Fig. 4时间按组件拆分

蓝色是模型推理，其余都是非模型部分。GUIAgent 的桌面沙箱占总时间 70% 以上，Pi-AutoR 有 90% 花在实验运行上[[gui70]]；RAG 的向量数据库约占一半。论文据此说十个应用中有五个由工具和环境主导或共同主导。

两点推论。第一，单次请求要跑几分钟到几小时，中途机器或网络出故障的可能性随之变大，失败后整体重跑代价很高，需要轻量的检查点和恢复[[fault]]。第二，在非模型部分占一半以上的应用里，只优化模型推理，整体延迟能改善的上限有限。

本页说明：除 Mini-SWE 和 RAG 外，模型都通过百炼 API 调用，所以 Fig. 4 里的“LLM”时间包含了网络往返和服务商一侧的排队，不是本地 GPU 上的纯推理时间。模型这一块的占比因此取决于这家 API 当时的速度，这也正是后面“瓶颈会转移”一节要说明的现象。

实验

token：上下文累积，前缀缓存命中率相差悬殊

Fig. 5§4.2

纵轴是对数刻度，每个会话的 token 分成三类：命中前缀缓存的输入、未命中的输入、输出。ReAct 类应用每一轮都把完整的历史、工具日志和系统提示再发一遍，输入量随轮数近似平方增长，比 RAG 多出几个数量级。

命中率的差别来自应用怎样组织上下文。系统提示固定、历史只追加的 Claude Code 命中率最高到 99%；每一轮都重新组织或重新检索上下文的 DeepResearch，前缀复用降到 1% 甚至更低[[prefix99]]。前者的大部分输入都可以复用，前提是缓存能一直留着，这就引出下一块：状态有多大。

实验

状态分三类，大小和处理方式都不同

Fig. 6§4.3
性能状态（a）
丢掉不影响正确性、但要花时间重算的东西，主要是 KV 缓存。一个用 DeepSeek-V4 的 Claude Code 会话最多占 11 GB 显存[[kv11]]，平均 2.2 GB。
正确性状态（c）
丢了执行就出错的东西：DeepResearch 每个会话自己的向量数据库（中位数 7.4 MB，最大超过 49 MB）、Codex 改过的文件和装好的依赖，以及已经对外产生的副作用，例如发出的邮件。
活跃工作集（b）
命令运行时沙箱占用的内存。中位数约 0.8 GB，编译和跑单元测试时单个会话峰值到 28 GB[[peak28]]。这部分是暂时的，不一定需要放进检查点。

典型值和峰值相差三十多倍，所以检查点应选在安静的时刻做：在智能体等模型生成结果、沙箱没有命令在跑的间隙存档，就不会把编译时的暂时峰值当成要保存的状态[[quiescent]]。反过来，沙箱执行很久的工具时，可以把这个会话的 KV 缓存换出显存。

实验

数据搬运：每个会话几十 MB

Fig. 7§4.4

每组柱子左边是组件收到的数据量，右边是发出的。三个来源：GUIAgent 每一步都要传一张高分辨率的桌面截图，单步数据量最大；DeepResearch 的 embedding 服务输出 1024 维的 FP32 向量，一个请求传输的序列化向量超过 20 MB[[embed20]]；上下文越积越长，GUIAgent 一个会话来回传的文本超过 10 MB。组件拆开部署后，这些数据的序列化和网络传输会占用带宽和 CPU，后面的放置实验会直接测到这一点。

实验

按量计费的成本构成

Fig. 8§4.5

按公有云价格估算：模型 API 分缓存读取、prefill、decode 计价，沙箱按 E2B，网页搜索按 Firecrawl。工具重的应用里非模型费用占主导，Pi-AutoR 的沙箱费用超过 99%，因为它的科学计算容器带 GPU[[cost99]]。原因是闲置：沙箱和检索环境分配给会话后，即使会话在等模型推理，也一直在计费。论文由此提出，像无服务器冷启动优化那样，在闲置时暂停、存档、再恢复容器。

发现二：组件、任务、单次调用三个层次的异构

非模型部分不能当成一个整体来优化，因为它内部差异很大。论文从粗到细看三层（Fig. 9 到 Fig. 12），再用三个对照实验说明异构怎样造成干扰（Fig. 13）。

实验

任务层：一个组件上的不同任务相差 32 倍

Fig. 9Fig. 10§5.1、§5.2

Fig. 9DeepResearch 各任务的平均耗时

P1、P2 是规划，W1 到 W4 是写作的各步，S1 是总结，Emb-D 和 Emb-Q 是给文档和查询做 embedding。W2（写检索计划）和 W4（写章节）调用的是相同的模型，W4 却慢 6.43 倍[[w4]]；Emb-D 比 Emb-Q 慢 32 倍。

Fig. 10各任务的输入输出规模

差距来自输入输出的规模，与组件本身无关[[driver]]：W4 的平均输入是 W2 的 26 倍、输出是 16 倍；Emb-D 的数据量是 Emb-Q 的 325 倍。每个任务内部的点也散得很开，这就是下一层的异构。

组件层面的差异更直观：GPU 上的模型、吃内存的向量数据库、吃 CPU 的沙箱、依赖网络的搜索。HuggingGPT 一个应用里调用的模型，计算量就从 16.8 到 6032 GFLOP 不等。

发现三：瓶颈随负载和部署转移

瓶颈指占端到端延迟最大的组件。论文逐个改变 W 的四个因素和 S 的三个因素，说明瓶颈的位置取决于应用在什么条件下被服务，不是应用本身固定的属性[[emergent]]。

实验

部署三因素：硬件、组件服务方式、部署架构

§6.2
改变的因素实验瓶颈怎样移动
硬件 HCodex 跑十个要编译代码的 TerminalBench 任务，沙箱分配 8 到 96 个 CPU 核（Fig. 19）核数越多沙箱越快，瓶颈可以从沙箱执行转到模型推理
组件服务方式 CGUIAgent 的模型用 SGLang 服务，batch 从 1 调到 4batch 为 1 时每 token 7 ms，桌面交互是瓶颈；batch 为 4 时 30 ms，模型推理慢 4 倍，变成瓶颈[[batch]]
部署架构 ARAG 的模型、embedding、向量数据库放一台机器或分到三台同机时网络可忽略，向量数据库占 47%；分开且并发为 10 时网络拥塞，传输占 67.5%

论文的结论是静态的 profile 和固定的资源分配跟不上这种转移，需要按请求在线调整。这一节的七个实验也说明了前面 Fig. 4 应该怎样读：那张图是默认部署下的一张快照，换一个模型速度或者沙箱配额，某个应用就可能从“工具主导”变成“模型主导”。

生产轨迹：三个线上应用的 24 小时

编程智能体 35037 个会话、基于搜索的问答智能体 141376 个会话、类 Openclaw 的办公智能体 2386 个会话。这些轨迹揭示了受控实验看不到的三个现象（发现四到六）。

发现四

会话大部分时间在等待，状态却一直占着

Fig. 20§7.1

(a) 是每个编程智能体会话中，模型和工具执行的时间占会话总时长的比例。中位数只有 20%，七成会话的执行时间不到一半[[idle20]]。(b) 是闲置间隔的长度：从几秒（等工具结果、等用户批准）到几小时（隔夜），大多在 1 到 10 分钟之间；短于 10 秒的只占 14%。

闲置期间沙箱、终端上下文、KV 缓存和对话历史都还要留着，因为会话随时可能继续。只有“运行中”和“已结束”两种状态不够用：当作运行中会白占内存和磁盘，当作已结束又丢了可恢复的状态。论文建议增加一个“等待中”状态[[waiting]]，让服务层把正确性状态存档到持久层，KV 缓存则按预计的复用价值决定留下、迁移还是丢弃。

发现五

控制面开销：上下文、辅助调用、缓存过期

Fig. 21§7.2

智能体框架（harness）负责拼装提示、管理上下文、驱动和监控工具调用，这些是多步执行必需的，但带来了目标任务之外的额外开销，论文称之为 agent control-plane tax，分三种。

占上下文。Fig. 21 是一个生产会话的输入构成。第 1 步时系统消息（角色定义、工具和技能描述、记忆等）占 99.7%；之后历史（模型的推理、工具调用和工具输出）迅速增长，最终占 84.3%。到第 261 步，模型只输出 151 个 token 决定下一步动作，却要先处理 166721 个上下文 token[[step261]]。

发现五

上下文压缩本身也很贵

Fig. 22§7.2

生产中的智能体用压缩（compaction）控制上下文增长：让模型把当前上下文总结成更短的版本。35037 个会话中有 3170 次压缩，99% 的压缩把上下文缩短了 70% 以上[[compact]]，说明大部分上下文可以压缩，不必原样重放。

辅助计算。每次压缩平均读入 176K token、生成 5K token，平均耗时 156 秒，p99 为 775 秒[[compact-lat]]。除压缩外，安全检查、循环检测等辅助调用在这批会话里又多出 2684 次模型调用、650 万输入 token。

发现五

缓存过期造成的重复 prefill

Fig. 23§7.2

这个部署里缓存条目的存活时间（TTL）是 5 分钟，过期后下一次调用要重新 prefill 整个前缀。而发现四里大多数闲置间隔在 1 到 10 分钟，正好跨过这条线，固定 TTL 和人的节奏对不上[[ttl]]。59.4% 的会话至少遇到一次过期。按 Claude Opus 4.6 的价格（缓存读取、写入缓存、普通输入、输出分别为每百万 0.5、6.25、5、25 美元）估算，过期造成的缓存写入占全部缓存写入 token 的 55.9%，占总费用的 31.5%[[evict]]。

论文给出的方向：工具接口要为智能体设计（固定的 schema 标识、限制大小的观察、增量更新、按需取回完整内容的句柄）；上下文分层存放，冷的观察不进提示；KV 缓存的保留、卸载和预取由框架和模型服务协调，依据会话是否在等待、预计何时回来。

发现六

不同用户之间大量重复的工具调用

Fig. 24§7.3

问答智能体每个请求先做一次网页搜索：373678 次搜索，平均 1.349 秒，中位数占会话延迟的 35%。27% 的不同查询在 24 小时内重复出现，这些查询贡献了全部搜索调用的 67.3%[[recur]]。办公智能体 4389 次 URL 抓取中，24% 的不同 URL 重复出现，贡献了 64% 的抓取。单个会话内看不到这种重复，要在多个智能体共用的工具服务那一层做缓存。

设计探索：四个原型分别对应四个发现

四项都是单独的原型，不组成一个完整系统[[poc]]。每项在一个应用上与不区分负载特点的做法比较，资源总量相同。

结论

结论

AgentSysBench 把智能体负载拆成请求、工具、模型、编排四个因素，把服务系统拆成硬件、组件服务方式、部署架构三个因素，用十个应用和可替换的部署分别控制它们，再用三个线上应用的一天轨迹补上受控实验看不到的部分。

结论的主线是模型推理不再是成本的主要来源：延迟、内存和费用有很大一部分落在工具、环境和长期存在的会话状态上，而且哪一部分占主导随请求、模型和部署变化。因此服务系统要同时管理模型、工具、状态和通信。四个原型各自验证了一个方向：按任务拆分、按通信放置、闲置时卸载、跨请求缓存。

局限

局限与讨论

本页说明：以下是本页的分析。第一，除 Mini-SWE 和 RAG 外，模型都走商业 API，受控实验里的“LLM 时间”包含了服务商的排队和网络，十个应用之间的时间构成比较受这一点影响。第二，六个发现中前三个是在单机、顺序执行下测的，并发主要出现在干扰实验和设计探索里；多个会话同时争抢 GPU 和沙箱时的表现，还没有成体系的测量。第三，生产轨迹来自三个未具名的线上应用，只有一天，部署细节（模型、硬件、TTL 以外的缓存策略）没有公开。第四，四个设计探索都是在一个应用上的原型，对照组是简单的共享或分离部署，没有和已有的智能体服务系统比较；论文的定位也是说明这些发现可以落地，而不是给出完整方案。
