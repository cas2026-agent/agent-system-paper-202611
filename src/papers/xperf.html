智能体应用部署得越来越多，就需要知道背后的推理服务系统在这类负载下表现如何、瓶颈在哪里。已有工具各缺一块：能力评测关心智能体把任务完成得好不好，不关心服务系统[[eval-harness]]；性能测试的请求是从数据集采样或按分布合成的，彼此独立，表达不了一个用户请求展开成许多相互依赖的调用；AA-AgentPerf 只用私有的编程智能体轨迹，也不公开[[aa]]。

问题

一个请求跑两遍，负载就不一样

Fig. 3§2.3

智能体下一步做什么（调哪个工具、要不要停）由模型的输出决定，而输出有随机性，小的差异一路累积，最后生成的执行图完全不同[[exec-graph]]。即使固定随机种子，批处理推理中的浮点误差也会让输出分叉[[fp]]。

用 gpt-oss-120b 跑两遍 mini-SWE-agent，请求和到达时间都相同。(a) 每个点代表一个请求，两个坐标是它在两次运行中的模型调用数，平均相差 12.9 次，是平均调用数的 76%[[var76]]。(b) 在两小时的观察窗口里，两次运行中排队的调用数走势明显分开，第二次的累计排队时间少了 65%[[q65]]，平均延迟低 25%，P95 低 30%。负载本身差这么多，就无法分辨测到的变化来自系统优化还是来自负载。

本页说明：§1 写的是两次运行的调用数平均相差 70%，§2.3 写的是 76%，两处不一致。

背景

执行图与系统分层

Fig. 1Fig. 2§2.1、§2.2

Fig. 1两种应用的执行图

一个用户请求在智能体内部展开成一张由模型调用和工具调用组成的有向无环图（执行图）。mini-SWE-agent 是模型和工具交替的链，模型决定调用哪个工具、何时停止；Open Deep Research 中模型决定并行开出多少路搜索。

Fig. 2应用层与服务层

提示的拼装和输出的解析都在应用层，服务层看到的只是一个个普通的模型调用。服务层由一个或多个引擎组成，KV 缓存不够时调度器让多余的调用排队；多引擎时由路由器按负载和前缀缓存的位置分派。XPerf 测的是服务层，工具和应用逻辑所在的主机不在范围内[[host]]。

方法：记录、建图、合成负载、重放

思路是先在真实应用上录下一份轨迹，以后每次测试都重放这份轨迹，负载就固定了（Fig. 4）。难点在于：重放时服务系统已经换了，调用的发出时间不能照抄录制时的时间，而要按依赖关系重新推算。

方法

整体流程与轨迹记录

Fig. 4§3.2、§3.3

模型调用：在 OpenAI、Anthropic 等客户端库里插一层包装，记录每次调用输入和输出的 token ID、起止时间、属于哪个用户请求，不用改应用代码。工具调用没有统一接口：LangChain、LangGraph 里的工具同样自动包装，自己写的应用在每个工具上加一行注解；若两次调用之间超过 20 ms 没有任何已记录的调用完成，就提示那里可能有漏掉注解的代码。编排函数：把调用组织成链或图的函数（如 LangChain 的 Runnable）也记下起止时间，每条记录都带父节点编号，留作下一步建图用。

方法

从时间跨度树推出依赖

Fig. 6§3.4

为什么要建图。如果按录制时的时刻把每个调用发出去，换一个更快的引擎后，一个调用提前结束，依赖它的调用却仍按原时刻发出，负载就不真实了[[why-graph]]。所以要知道每个调用依赖哪些调用，前驱全部完成才发出。

怎么建。按父子关系把记录连成一棵树（b）：叶子是模型或工具调用，内部节点是编排函数，根是整个用户请求。自底向上合并：在一个父节点下，一个子节点结束后另一个才开始，就认为后者依赖前者，并只保留直接依赖[[dep]]；连接时从前一个子图中没有后继的调用，连到后一个子图中没有前驱的调用（c）。

只看时间先后而不看树会产生假依赖。LATS 并行跑多个独立任务，若两个任务的模型调用几乎同时结束，一个任务的工具调用会被误认为依赖另一个任务的模型调用[[false-dep]]；有了树，不同任务的调用挂在不同的内部节点下，就不会混在一起。实验中每个请求最多约 1000 次调用，建一张图不到 200 ms。

方法

合成新负载与重放规则

§3.5、§3.6、§4
层次怎样重放为什么
单次模型调用模式一：发送录下的输入 token ID，让引擎忽略结束符，生成长度设为录制时的输出长度[[mode1]]。模式二：进一步强制引擎逐 token 输出录下的内容（修改了 vLLM，用一个特殊角色的消息把 token ID 传进去，每步覆盖采样结果）输入相同才能保持前缀缓存的命中；输出长度相同才能保持 decode 的工作量。MoE 和稀疏注意力模型的计算取决于具体 token，所以需要模式二[[moe]]
执行图一个节点的前驱全部完成后才执行；工具节点按录下的时长睡眠工具默认被视为与服务负载无关，因为通常跑在另一台机器上[[tool-indep]]
整个负载按到达时间逐个启动执行图；用固定大小的缓冲区边加载边释放内存只取决于并发请求数，与负载总量无关

换一种负载不用重新录。录好的一批执行图可以配不同的到达方式：照录制时的时刻、按泊松过程的在线服务、开始时一次发出指定数量的离线批处理、保持固定并发数，或用户自己给出每个请求的到达时间。采集的指标有两类：从引擎的 /metrics 接口每秒读取运行和排队的调用数、KV 缓存占用、前缀命中率、token 吞吐；用 CUPTI 每 20 ms 读取 Tensor Core、SM 和显存带宽的利用率。

测量

请求延迟：长尾来自停不下来的智能体

Fig. 8§5.4

请求率低于饱和点。各应用的平均延迟相差很大，而且多数是长尾，P95 最高是 P50 的 6.60 倍[[tail]]。长尾主要来自没有进展却一直在调用模型和工具、不肯停下来的智能体[[noprogress]]。两个例外：DeerFlow 严格限制搜索轮数；MagenticOne 有一个负责监督的智能体，发现停滞就终止。深度研究类的最低延迟也很高，至少要做完一轮研究、写一份长报告。

测量

延迟构成：负载低时是 decode，负载高时是排队

Fig. 9§5.4

纵轴是端到端延迟除以 critical path 上的输出 token 数，按排队、prefill、decode、工具拆分。未饱和时 decode 占 60% 到 98%[[decode]]，prefill 很小，只有提示最长（平均 38.8K token）的 DeerFlow 接近 23%，其余平均 4%。请求率升高，排队占比随之增长，在测试的最高请求率下最多占 69%[[queue69]]。

测量

服务系统指标：前缀缓存在负载升高时被冲掉

Fig. 10§5.5

每列一个应用，横轴是请求率，六行依次为：正在运行的调用数、排队的调用数、KV 缓存占用、前缀命中率、输入 token 吞吐、输出 token 吞吐。前两行一起给出饱和点：运行数到达上限后不再增加，多出的请求开始排队，例如 mini-SWE-agent 在每分钟 4.5 个请求时开始排队。饱和时多数应用的 KV 缓存接近占满；DeerFlow 只到 75% 左右，因为它每次调用约 40K token，而总容量约 213K token，剩下的空间放不下下一个调用。

提示的写法决定能不能复用

低负载时多数应用命中率在 41% 到 91%。ODR 只有 14%，因为输入大多是互不相关的搜索结果。DeerFlow 在所有请求率下都低于 1%：它把时间戳放在系统提示的开头，每次调用的前缀都不同[[timestamp]]；去掉时间戳后低负载时能到 30% 左右。

负载升高后缓存被反复冲掉

其余应用的命中率在请求率超过某个值后骤降。原因是服务系统把每次调用当作独立的，KV 缓存紧张时，会把某个请求在工具调用期间暂时没人用的上下文淘汰掉，而下一次调用马上又要用[[thrash]]。mini-SWE-agent 从 91% 掉到 4% 以下[[swe91]]；降下来后的稳定值约等于系统提示占输入的比例，因为系统提示在各请求之间共用。

被冲掉的缓存要重算，于是输入吞吐不升反降（mini-SWE-agent 最多降 12%），也拖累 decode：请求率从每分钟 3.38 个升到 4.5 个时，运行中的调用数增加 83%，输出吞吐只增加 11%[[run83]]。

测量

GPU 指标印证缓存被冲掉

Fig. 11§5.5

命中率骤降的应用，接近饱和时显存带宽利用率反而下降。例如 CUGA 的请求率从每分钟 14.4 个升到 16.8 个，Tensor Core 利用率升高 55%，显存带宽利用率下降 16%。decode 主要消耗带宽，重算 prefill 主要消耗算力，所以 Tensor Core 利用率的上升并不代表效率提高，而是在重复计算[[wasted]]。

测量

多引擎扩展：路由要保住缓存的局部性

Fig. 14§5.7

mini-SWE-agent，固定并发，引擎从 1 个扩到 4 个，分布在两台服务器上，比较 vLLM-Router 的两种路由。轮转路由把一个请求的各次调用轮流发到不同引擎，前缀缓存的局部性被破坏，2 个和 4 个引擎只达到单引擎峰值吞吐的 1.41 倍和 2.26 倍[[rr]]；按前缀缓存路由时几乎把一个请求的调用都发到一个引擎上，达到 1.88 倍和 3.61 倍[[ca]]。

测量

调试：不固定负载会得出错误结论

Fig. 15§5.8

比较两种调度：主流引擎用的按调用先来先服务，以及按请求先来先服务（先到的用户请求的所有调用整体优先）。用相同随机种子录三份 mini-SWE-agent 轨迹，每份在两种策略下各重放一次。在每份轨迹上，按请求调度持平或略好，不超过 8%[[fcfs8]]。但三份轨迹之间差得更多：100 个并发时，轨迹 2 在两种策略下的延迟都比另两份低 720 到 910 秒，因为它的长请求少（输出超过 40K token 的只有 4.5%，另两份为 12% 和 13.5%）。如果在不同的运行上测两种策略，就可能大大高估按请求调度的收益[[mislead]]。

开销

§5.9

录制时，OpenTelemetry 让端到端延迟增加 0.1%[[overhead]]，收集轨迹的后端占用不到 5% 的 CPU 核和 2 GB 内存；平均每个请求的轨迹 4.6 MB，DeerFlow 最大的达 27.46 MB。重放时采集指标让每步 decode 增加不到 0.1%，GPU 采样每 20 ms 一次，只占 16 KB/s 的 PCIe 带宽。

结论

结论

XPerf 用“录制、建图、重放”解决智能体负载不可复现的问题：录下每次模型调用的 token ID 和每次工具调用的时长，按时间跨度树推出调用之间的依赖，重放时按依赖发出调用、保持输入和输出长度不变。这样在不同的服务系统和配置上可以施加相同的负载，重放的端到端延迟误差在 3% 以内。

用它在八个应用上测出了几个现象：长尾来自停不下来的智能体；负载低时 decode 是瓶颈、高时排队是瓶颈；KV 缓存紧张时请求在工具调用期间的上下文被淘汰，导致命中率骤降和重复计算；提示开头放时间戳会让前缀缓存完全失效；多引擎的扩展效果取决于路由能否保住缓存局部性。

局限

局限与讨论

论文明确把运行应用逻辑和工具的主机排除在测量范围之外[[host]]，工具调用按录制时的时长睡眠，默认与服务负载无关；把工具参数也记下来、在主机上真实重放，是作者计划中的扩展。

本页说明：重放固定了执行图，这正是可复现的来源，也决定了它能评估什么。凡是会改变智能体行为本身的改动，例如换模型、改提示、调整上下文压缩策略，都会改变执行图，不能用旧轨迹评估，需要重新录制。反过来，由服务系统引起的行为变化（如延迟过长导致应用超时、改变后续动作）在重放中也不会出现。此外，实验平台是一到两台各带两张 H100 的服务器，多数结论在单引擎上得到；Fig. 15 的调度比较只用了一个应用。
