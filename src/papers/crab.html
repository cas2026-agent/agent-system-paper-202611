智能体沙箱为什么需要检查点

Claude Code、Codex 这类智能体在沙箱里编译项目、装依赖、起后台服务、反复改文件。它们的状态不只是对话记录，还包括内核能看到的一切：文件内容、长期运行的进程、装好的软件包[[os-actors]]。一旦沙箱崩溃，或者云上的抢占式实例被收回，这些状态就没了。长任务可能有上百轮，从头再来代价很大。

表中五种场景对检查点的时机和数量要求各不相同，但都离不开把沙箱完整状态快速存下来、再恢复出来的能力[[use-cases]]。其中树形强化学习从中间状态分叉出多条轨迹，推测执行先在复制的沙箱里试跑一个小模型猜的动作，主动回滚则把恢复作为一个工具交给智能体自己调用。

背景

基本概念

交互轮
智能体收到大模型回复、执行其中的工具调用、把结果发回大模型，这一来一回称为一轮。
两种部署方式
智能体在沙箱内：智能体进程本身跑在沙箱里（Claude Code、Codex）。智能体在沙箱外：智能体在外面通过命令接口操作沙箱（SWE-agent）。
检查点与恢复
把沙箱某一时刻的状态保存下来，之后能回到这个状态。
ZFS 快照
ZFS 文件系统的块级写时复制快照，只记录变化的块，实测每次约 12 到 22 毫秒。
CRIU 与 runc
CRIU 把运行中的进程连同内存完整写成镜像文件；runc 是容器运行时，负责管理容器生命周期并调用 CRIU。进程镜像的大小与进程占用的内存成正比。
eBPF
Linux 内核中可动态挂载的小程序，能低开销地观察系统调用等内核事件，不需要修改内核或被观察的程序。
cgroup 与软脏页
cgroup 把一组进程划为一个管理单元；软脏页是内核提供的页级标记，能查出某个进程自上次清零以来写过哪些内存页。
抢占式实例
云厂商的低价计算资源，随时可能被收回，通常提前几十秒到两分钟通知。
主线

问题、洞见、设计、效果

问题

只保存对话或文件的轻量恢复便宜但常常恢复错；每轮保存整个沙箱的做法正确但太贵，多个沙箱挤在一台机器上时更扛不住[[use-cases]]。

根源

智能体框架看得到工具调用，看不到它对操作系统的实际影响；操作系统看得到状态变化，却不知道哪一轮结束了、哪些变化值得保存[[gap]]。结果是超过 75% 的轮次其实什么都不用存[[sparsity]]。

设计

把智能体当黑盒，在每一轮结束时观察它在操作系统里留下的实际变化，据此决定这一轮存什么[[insight]]；存档与等待大模型回复并行；一台机器上所有沙箱的存档任务统一排队调度。

效果

恢复正确率从只保存对话时的 8% 提到 100%；最多 87% 的轮次完全跳过存档；每个任务注入一次崩溃，总耗时仍只比不出故障、不做存档时多 1.9% 以内。

问题

轻量恢复常常恢复错

Figure 1

实验从 Terminal-Bench 里挑出 50 个能顺利完成的任务，在每条运行轨迹的随机位置注入一次故障，比较四种做法：不出故障（基准）、从头重来、只恢复对话、恢复对话加文件。上排 (a) 按录好的轨迹重放，排除模型随机性；下排 (b) 接真实的大模型服务。每排左边是解题率，右边是每个任务耗时的累积分布，曲线越靠右越慢。

从头重来能做对，但所有已完成的工作都要重做，中位耗时变为 1.81 倍（重放）和 1.55 倍（真实模型）。只恢复对话几乎都失败，重放下只解出 6%：对话里记着“已经装好了依赖、已经起了服务”，沙箱里却什么都没有。恢复对话加文件好一些，重放下 48%，但丢了进程状态，后台服务、进程内存里的数据都不在了。真实模型下这一项反而降到 34%：恢复出的环境和原来不一致，模型发现东西不对，会动手“修”，修的过程进一步偏离了原来的轨迹[[diverge]]。轻量恢复本质上不完整，能保证正确的只有从头重做[[lightweight]]。

问题

每轮全量存档扩展不了

Figure 2存档请求来得有多密

左侧是每一轮耗时的累积分布，中位数 3.34 秒，一个任务平均 117 轮。右侧是一台 128 核机器上存档请求的到达速率：放 100 个沙箱、每轮都存档时，中位每秒 17 个请求，90 分位每秒 26 个[[burst]]。

Figure 3单次存档有多贵

左侧是 ZFS 快照的耗时，几种文件操作下在 11.8 到 21.8 毫秒之间，很便宜。右侧是 CRIU 进程存档，横轴是同时进行的存档数，纵轴是耗时（对数刻度），四条线对应进程内存 128 MB 到 1 GB。同时做 16 个 128 MB 的存档要 1.3 秒，64 个 1 GB 的存档要 47 秒[[criu-cost]]。

瓶颈在进程状态：它和内存大小成正比，并发起来会抢满磁盘带宽。智能体框架本身常驻约 185 MB，工具运行时可能涨到 4 GB 以上，把两张图合起来看，每轮全量存档在高密度部署下扛不住。

问题Figure 4

为什么光看工具调用判断不了

上条是 Terminal-Bench 记录里各类工具调用的占比，执行任意 shell 命令的 run_shell_command 占 60%。下条是这些 shell 命令里带有明显副作用语法的比例，70% 没有任何线索。

直觉上可以按工具类型判断要不要存档，比如读文件不用存、写文件要存。但最常用的工具是“执行一条命令”，python arbitrary_script.py 可能改文件、可能起常驻进程、也可能只打印输出，工具签名完全一样[[opaque]]。靠语法也推不出来：12,483 条命令里只有 5.3% 含重定向、1.0% 后台执行、16.2% 用管道[[syntax]]。把所有命令都当成有副作用，就退回了全量存档；按工具名或语法猜，就会恢复错误。

设计

架构：宿主机上的透明运行时

Figure 5

中间是三个沙箱，分别跑着 Claude Code、SWE-agent 和 Codex。黄色是 Crab 的组件：用户态的 Coordinator 架在智能体和LLM API 之间，所有 LLM request 和回复都经过它；内核里的 Inspector eBPF 程序观察每个沙箱的系统调用，用户态的 Inspector 守护进程汇总结果；右侧的 C/R Engine 包含调度器、执行存档的 Worker 和管理版本的 Manager，底层调用 CRIU 和 ZFS。智能体和 CRIU、ZFS 都不需要修改。

组件放在宿主机上有它的道理。如果每个沙箱配一个旁路进程，它只能看到自己的沙箱，无法协调整台机器上的存档流量；如果只在内核里做，能看到操作系统的变化，却不知道一轮何时结束、大模型何时在思考，也就没法把存档藏进等待时间[[kernel-only]]。只有宿主机上的运行时既能拿到轮次的语义（通过拦截 LLM request），又能看到所有沙箱的内核事件。

设计

一轮结束时发生了什么

Figure 6、§5.1

横轴是时间，每一行是一个参与者：智能体与沙箱、Coordinator、调度器、Worker、Manager、Inspector、大模型服务。第 i 轮的工具执行完，智能体向大模型发 LLM request，Coordinator 拦下（1）并立刻转发（2），这个 LLM request 的出现就标志着第 i 轮结束。随后它问 Inspector 这一轮改了什么（3），决定跳过还是存文件、存进程或两者都存，把任务交给 C/R Engine（4），调度器安排 Worker 去做（5）。这些都发生在大模型思考的那几秒里。

大模型的回复回来时，Coordinator 再次拦下（6）。如果第 i 轮的存档已经完成，回复立刻交给智能体，第 i+1 轮开始（7）；如果还没完成，就扣住回复，等存档做完再放行。这道闸门保证任何一轮开始前，上一轮的状态都已经安全落盘，同时把存档的等待只暴露在它超过大模型思考时间的那部分[[gate]]。若回复已到而存档未完成，Coordinator 还会把这个任务提升为高优先级，让调度器先处理已经卡住智能体的存档。

设计

Inspector：判断这一轮改了什么

Figure 7、§5.2

四行各是一个文件或进程从上次存档（灰色箭头）到本次查询（黄色箭头）的经历，橙色长条是它的存在期，斜线块是被修改的时段。第一行在上次存档后被创建，但查询前就消失了，判定为没变；后三行在查询时仍然存在、新建或被改过，判定为有变化。

这就是“净变化”的含义：只看从上次存档到现在，最后留下了什么[[netchange]]。shell 每执行一条命令都会派生短命的子进程，很多工具也会写临时文件再删掉，如果把这些都算作变化，几乎每一轮都得存档。文件方面，eBPF 挂在系统调用入口和出口，记录沙箱内进程的创建、删除、改名和写入，标准输出这类特殊句柄除外，守护进程据此计算净变化。进程方面，用 cgroup 判断沙箱里是否有进程新增或退出，对一直活着的进程，读它的软脏页标记看有没有写过内存。每次存档完成后把记录和标记清零，作为下次比较的起点。

设计

C/R Engine：调度、执行、版本

Figure 8、§5.3

左图横轴是轮次，FS 行和 Proc 行标出哪些轮存了文件、哪些轮存了进程。第 0 轮两者都存，得到恢复点 C0=(P0, F0)；第 1 轮只改了文件，新的恢复点是 C1=(P0, F1)，进程部分沿用第 0 轮的；第 2 轮什么都没改，不产生新恢复点。由于每次存档可能只覆盖一半状态，单个存档文件本身不能用来恢复，Manager 把“最近的进程镜像加最近的文件快照”组合成一个版本，形成类似 git 的版本历史[[manifest]]，可以回到其中任意一个。右图是一次存档的生命周期：排队、写入、组合版本、成功；任何一步出错或被打断就标为失败，绝不会被当作恢复点使用[[failed]]。

调度器用两个先进先出队列。新任务进普通队列，因为它的耗时还能被大模型思考时间盖住；一旦对应的回复已经回来，任务被提升到高优先级队列，Worker 总是先处理高优先级的。每个任务迟早会因回复到达而被提升，或者在此之前已经完成，不会饿死[[starvation]]。这样，有限的磁盘带宽优先用在已经让智能体等着的存档上。文件快照用 ZFS，进程存档用 runc 调用 CRIU，Worker 的数量设成刚好跑满磁盘带宽。

设计

两种部署方式下的恢复

Figure 9、§6

智能体在沙箱外时，沙箱可能在一条命令执行到一半时崩溃。存档只在轮次边界进行，恢复出来的沙箱里没有这条命令的痕迹，而外面的智能体正等着它的结果。Coordinator 在转发每条命令前先记日志，恢复后发现有未完成的命令就重新执行[[reissue]]，智能体只看到命令正常返回。

智能体在沙箱内时问题更微妙。智能体进程每一轮都会改自己的内存，如果把它当普通进程跟踪，几乎每轮都要做昂贵的进程存档[[exclude-agent]]，所以 Crab 不跟踪智能体进程本身。代价是恢复时智能体的内存可能比文件旧。图中最新的恢复点是 C4=(P2, F3)，智能体的记忆停在第 2 轮，文件已到第 3 轮。第 3 轮执行的是 echo "b" >> foo，如果让智能体照常继续，它会再追加一次，文件变成 “abb”。Coordinator 缓存了所有 LLM request 和回复，恢复后智能体重发第 3 轮的 LLM request时，Coordinator 认出这是重复的 LLM request，直接从缓存返回当时的回复，而不真正去执行动作[[fastforward]]，直到智能体的进度追上文件状态，foo 的内容保持正确的 “ab”。

结果

存档能藏多少，调度帮多少

纵轴都是累积分布，横轴是每个任务因等待存档而多花的时间占总时间的百分比。左图比较不同密度，四条曲线在 0 处就几乎升到顶，中位数在所有密度下都是 0，也就是至少一半的任务从未因存档等待过。95 分位在 16、32、64、96 个沙箱时分别是 0.00%、0.37%、0.44% 和 3.65%[[exposed]]。

右图是压力测试：96 个沙箱，并把大模型思考时间人为缩短到原来的 0.2、0.4、0.6 倍。思考时间变短，一方面能藏存档的窗口变小，另一方面每轮变快、存档请求来得更密。在这种情况下，按“是否已经卡住智能体”区分优先级的调度，比简单先来先做把等待时间的中位数降低最多 41.6%，95 分位降低最多 31.3%[[reactive]]。随着大模型推理越来越快，可用来掩藏存档的时间会缩短，调度的作用会越来越重要。

把回滚交给智能体

这个案例估算把回滚作为工具交给智能体能省多少。它在录好的轨迹上把清理片段替换成回滚调用计算得到，没有让智能体实际重新运行。每个案例上面是实际的执行过程，下面是假如有 rollback() 工具时的过程，绿色是有效推进，红色是手动收拾残局，橙色是卡住，蓝色是一次回滚（按实测 99 分位约 1 秒计算）。

结论

结论

智能体沙箱里积累的操作系统状态，现有的检查点机制要么抓不全，要么抓得太多。原因在于智能体框架和操作系统各自只掌握一半信息。Crab 的做法是站在两者之间：从LLM request 里得到“一轮结束了”的信号，从内核里得到“这一轮实际留下了什么”的信号，二者结合，只在需要时以需要的粒度存档，把存档藏进大模型思考的时间，并在整台机器的范围内调度存档流量。

结果是在 Terminal-Bench 和 SWE-bench 上恢复正确率从 8% 提到 100%，最多 87% 的轮次免于存档，每个任务崩溃一次时总耗时仍在理想情况的 1.9% 以内。更一般地，对一个看不透内部逻辑的程序，它在操作系统里留下的可见痕迹可以作为轻量的语义信号，同样的思路可用于沙箱的调度、资源隔离和安全审计[[conclusion]]。

局限

局限与讨论

实验按录好的轨迹确定性重放，并只挑选了能顺利完成的任务。这样做能干净地衡量存档本身的开销和正确性，但没有覆盖真实运行中模型随机性、任务失败等情况；主动回滚、推测执行两个案例也是在录好的轨迹上模拟出来的，智能体实际学会使用回滚工具后的效果还需要真实运行来验证。Inspector 的准确率是在 iFlow-cli 的 2,063 个轮次上人工标注得到的，其他智能体和任务类型上是否同样零漏报，没有单独报告。

Crab 判断的是“状态有没有变”，进程一旦变了仍要做完整的 CRIU 存档，这一部分的耗时（接近一秒）和内存大小成正比，也是长尾延迟的来源；大模型推理变快时，能掩藏它的时间会缩短。智能体在沙箱内时不跟踪智能体自身，恢复依赖缓存的大模型回复做快进，这要求智能体在相同输入下会重发相同的 LLM request。系统依赖宿主机上的 ZFS、CRIU 和 eBPF，实验只使用了 runc 容器，在 Firecracker 这类轻量虚拟机沙箱上的表现没有评估。
