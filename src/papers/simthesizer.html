Simthesizer: An Agent-Driven Simulation Framework for LLM Serving Systems

Wonung Kim、Hyunmin Choi、Minsu Kim、Jaehong Cho、Yeongwook Kim、Jongse Park，KAIST

arXiv 2608.24650v2，cs.AR，2026
计算机系统推理服务性能模拟器编码智能体
问题

模拟器跟不上推理服务的变化

Fig. 1Fig. 2§I、§II

系统级模拟器（如 Vidur、APEX、LLMServingSim、LLMServingSim 2.0）用来在不部署真实系统的情况下探索推理服务的设计空间。论文指出，它们都建立在两个前提上：推理服务演进得足够慢，人工可以跟上；服务行为可以装进一条固定的模拟流程[[premises]]。这两个前提正在失效。

(a) 演进快
智能体负载、投机解码的一代代变体、prefill 与 decode 分离、注意力与 FFN 分离，新一波出现时上一波还没成为标准做法。新机制出现的速度超过了人工开发模拟器的速度[[pace]]。
(b) 不再是单一流程
智能体请求把一个查询展开成多次推理、中间夹着工具调用和子智能体；分离部署、投机解码、跨层 KV 管理把原来自成一体的推理过程拆成多个相互配合的阶段。固定流程装不下的机制，每加一个都要侵入式地改写模拟器[[rewrite]]。
思路

两条设计原则

§II-C

两个困难归根结底是人力不够，所以让编码智能体来写扩展。但直接把智能体接到已有模拟器上不够：它继承了固定流程的耦合，每次扩展仍是大范围改写；而且能编译、能过功能测试的代码，模拟的可能是错误的系统[[wrong]]。由此提出两条原则。

原则一：可组合
用统一的表示描述所有阶段、依赖和状态转换，增加机制时只增加和组合部件，不改执行引擎。
原则二：有约束地让智能体实现
限定修改范围，加上模拟器专用的检查，并用与真实系统对比等方式验证模拟的语义是否正确。
系统

整体：模拟器加编码智能体

Fig. 3§III

(a) 用户用自然语言提出要加的功能，Synthesizer agent 把它变成规格、映射到模拟器的抽象上、实现缺少的部分，再与真实系统的测量或参考资料对比验证，最后交出扩展后的模拟器和设计、验证文档。(b) Simthesizer simulator 分两层：下层是统一的动态 DAG，上层是由调度器、路由器、模型等可替换部件组成的控制层。(c) Synthesizer agent 按 task-design、sim-mapping、sim-dev 三个阶段工作，然后做验证。

系统

执行层：把控制决策也变成图上的节点

Fig. 4§IV-A、§IV-B
节点表示什么延迟是否改状态
计算节点已排定的某个模型算子在某个设备上执行派发时确定否
通信节点设备之间的一次传输可能因链路争抢而改变否
逻辑节点请求到达、路由、组批、状态转换等控制决策固定是

已有的模拟器把计算和通信画成图，但路由、组批这些决策放在图之外的固定控制流里[[outside]]。Simthesizer 把决策也做成节点。服务过程是动态的，批的组成、放在哪里、请求要经过哪些阶段都取决于运行时状态，所以逻辑节点执行时可以通过一组 API 往图里加节点、改依赖。例如在分离部署中，决定 decode 放到另一台机器后，先断开 prefill 节点的出边，插入一个 KV 传输节点，再把 decode 接在它后面。所有节点由一个按时间排序的事件循环推进；通信节点的完成时间可以在资源状态变化时被撤销并重新安排，以此表达带宽争抢。

系统

控制层：接口固定，实现可换

Fig. 5§IV-C

如果所有决策都由一个处理函数来做，控制层上又会出现一条固定流程。所以按角色拆成部件，每个部件处理自己角色的逻辑节点、持有自己的策略状态。(a) 接口固定角色的操作，例如 Scheduler 负责接收子请求、给出下一批；(b) 具体实现封装策略和状态，例如带前缀缓存的分块 prefill 调度器；(c) 配置文件选择每个接口用哪个实现。已有的策略够用时，只改配置就能组装出目标系统[[config]]；缺一个时，只需在它的接口后实现这一个策略。内置部件覆盖单实例和多实例、prefill 与 decode 分离、专家并行的 MoE 等。

计算耗时默认用离线 profile 插值，每类层最多用两个键（例如注意力用已缓存的 KV 量和查询与上下文的交互数）；网络默认按流建模。两者都可以换成更精细的硬件或网络模拟器。

系统

Synthesizer agent：三个阶段、三份文档、两种验证

Fig. 6Fig. 7§V
阶段要满足的要求产出
task-design语义完整：决定模拟时间、资源争抢、状态生命周期、依赖结构的量和假设都要写清，近似要给出依据和适用范围面向模拟器的规格文档
sim-mapping结构对应：每个建模决定落到负责它的那个模拟器抽象上，避免散落在不相关的控制路径里实现映射表
sim-dev建模精度：按映射表改代码，根据编译、运行和测试结果迭代；检查未声明的近似、来路不明的常数和偏离映射表的改动代码与验证报告

规格中有影响性能的决定靠资料和模拟器上下文定不下来时，智能体会请人澄清，而不是悄悄选一个默认值[[human]]。验证分两种：有真实系统时做轨迹对比，在相同负载和配置下对齐队列长度、批组成、资源利用率等内部信号，把偏差追溯到具体的建模决定；没有可比的测量时（未发布的硬件、新机制）做参考对比，从参考实现和已发表的结果中推出性能标准。后者不能证明与目标系统一致，但给出了可追溯的依据并暴露剩余的不确定性[[reference]]。

示例

投机解码：一次验证找出的语义错误

Fig. 7Table II§V-D

以 EAGLE 式投机解码为例：小模型先起草几个 token，目标模型一次验证，只有被接受的 token 推进生成。task-design 从参考资料中推出四个变量：验证宽度 W、剩余输出长度 R、被接受的长度 A、请求已提交的进度 M。sim-mapping 把 W 和 M 放进已有的请求和调度机制，沿用通用的 DAG 执行路径，没有新增事件、节点类型或 API。第一版候选在验证轨迹上把吞吐高估了 13.4%[[overest]]：检查发现它只在最后一层用了宽度 W，其余层按起草数计算，低估了计算和通信。修正后，吞吐偏差降到 6.7%[[fixed]]。

实验

两张 RTX Pro 6000 Blackwell，真实系统为 vLLM v0.19.1。默认由 GPT-5.4（xhigh，通过 OpenAI Codex）充当 Synthesizer agent。对照是 LLMServingSim 2.0 和 Vidur：三个模拟器都没有原生支持的三个功能（FP8 KV 缓存量化、EAGLE3 投机解码、Mamba 混合模型），由相同的编码智能体、相同的 harness、相同的提示、资料、规格和 profile 数据分别加进去；harness 中不含 Simthesizer 专属的信息[[fair]]，每个任务独立重复多次、无人干预，取平均[[trials]]。

实验

扩展精度：底座决定扩展质量

Fig. 9Fig. 10§VI，Q2

KV 缓存量化只需要跟踪显存和量化开销，三个模拟器误差都低。投机解码和 Mamba 混合模型要同时改调度、模型结构和性能模型，Simthesizer 的误差明显最低，例如 Mamba 混合模型的平均 TTFT 误差约 11%，两个对照约 82%。由于智能体、harness、规格和 profile 数据都相同，论文认为差别来自底层模拟器[[isolate]]：模块化接口让扩展局限在一处，固定流程则要牵动多个耦合的部件。总体平均吞吐误差 2.51% 对 6.03%。

实验

模拟速度

Fig. 11§VI，Q4

ShareGPT 负载下，Simthesizer 平均比 LLMServingSim 2.0 快 164.9 倍、比 Vidur 快 6.65 倍[[speed]]。论文的解释是已有模拟器没有模块化的边界，扩展逻辑直接写进模拟流程，每个模拟迭代都多了开销[[overhead]]。Mamba 混合模型这一项 Simthesizer 用了约 23 秒，因为各层结构不同，它不能只模拟一层再复用，要逐层模拟。

本页说明：这里比较的是三个模拟器各自由智能体加入新功能之后的速度，不是原生版本之间的速度，差距中包含了“扩展写得好不好”。另外从图上看，Mamba 混合模型一项 Simthesizer 与 Vidur 都约 23 秒，在这项上并不更快。

结论

结论

Simthesizer 把模拟器的执行做成一张可以在运行时生长的 DAG，控制决策也是图上的节点；控制层按角色拆成接口固定、实现可换的部件。在此之上，Synthesizer agent 用三阶段、带文档和检查的流程把自然语言的功能需求变成局部的扩展，再用真实系统或参考资料验证。相同智能体和 harness 下，在它上面做的扩展比在已有模拟器上做的更准，吞吐误差 2.51% 对 6.03%，而且模拟更快。论文认为“可组合的模拟底座加智能体扩展”也可以用在其他系统领域的模拟器上。

局限

局限与讨论

本页说明：以下是本页的分析。第一，实验规模小：两张 RTX Pro 6000，负载每组 50 到 400 个请求，三个扩展任务；投机解码的修正需要人看验证报告后再跑一轮。第二，智能体负载的实验里工具调用耗时是事先测好再重放的，工作流也是 mini-SWE-bench 和 tau-bench 预先定义好的形式，没有涉及执行路径随模型输出变化的情形。第三，论文没有给出扩展任务的重复次数和各次的方差，只说取平均。第四，作者名单中 Hyunmin Choi、Jaehong Cho、Jongse Park 也是 LLMServingSim 2.0 的作者，代码同样发布在 casys-kaist 组织下；对照组之一是这个研究组此前的模拟器，论文正文没有说明这层关系。
