SpecBox: Speculative Sandbox Scheduling for Efficient LLM Agent Serving

SpecBox：为智能体服务投机地提前准备沙箱

Yihui Zhang、Tianyu Wo 等，北京航空航天大学、利兹大学、悉尼大学

arXiv 2607.23933v2，cs.DC，2026
计算机系统智能体运行时沙箱冷启动
背景

常驻还是按需：沙箱部署的两难

§1、§2.2

智能体越来越多地通过 MCP 调用隔离的外部沙箱来执行代码、操作网页、处理数据。在多租户的集群上有两种部署方式。常驻：给每个租户和工具保持预先启动好的容器，延迟最低，但工具成千上万时空闲容器占用的内存和 CPU 难以承受。按需：调用时才启动，资源利用率高，但每次都要拉镜像、建网络命名空间、挂文件系统、做应用层握手，秒级的冷启动在多轮任务里不断累加[[dilemma]]。

论文认为延迟的主因不在沙箱启动本身，而在 AgentScope、AutoGen、LangGraph 等运行时的串行模型[[serial]]：模型生成完、工具调用完全确定后，才开始准备沙箱。GPU 生成 token 时 CPU 闲着，沙箱启动时 GPU 又在等。

问题

串行执行与重叠执行

Fig. 1§1

思路是在请求到来之前，提前启动最可能被用到的沙箱，让准备工作与模型生成重叠。困难在于智能体的工具调用是随着流式 token 逐步显现的，在语义足够之前都不确定[[uncertain]]；而且多轮会话中下一步用什么取决于中间结果。服务器无关计算（serverless）里成熟的预热和预取技术通常假设执行目标或工作流图事先已知，不能直接搬过来。

测量

一步的时间构成与沙箱冷启动

Fig. 2§2.3

(a) 把一步拆成五段：处理上下文、生成 token（这两段属于模型推理）、准备沙箱环境、传输输入输出数据、在沙箱里执行。准备环境在 QPS 为 1 时占 22.3%，QPS 为 20 时占 28.1%；数据传输占 8% 到 11%。后三段是 SpecBox 能优化的范围，不改模型推理本身。

(b) MCPBench 的全部沙箱加上几种常用环境，共 32 种，多数 2 到 4 秒启动完，重型的接近 20 秒[[cold]]。

由此有三个观察：生成 token 期间，提示和已生成的部分往往已经透露了要用哪个沙箱，可以提前开始准备；相邻步骤之间有规律（检索论文之后常读文档，数据分析之后常画图），可以在当前步就准备下一步；多轮任务里常重复查询相同的内容，大文件和控制消息混在一起传，数据传输时间随文件大小增长。

问题

三个设计难点

§2.4
预测要早，但不能乱猜
早期的 token 很模糊，read、get 这类通用动词在许多 MCP 工具里都有；猜得早容易误启动，浪费资源。
跨步预取不能全都预热
下一步有多种可能，全部预热的开销就和常驻部署差不多了[[all]]；只预热一个，收益又有限。
复用和直传不能改变语义
严格相同才复用太保守，任意语义相似就复用可能返回不兼容的结果；大文件放在普通 RPC 里兼容但慢，换掉控制接口又会破坏现有工具。
系统

整体结构

Fig. 8§3、§4

SpecBox 是夹在智能体引擎和外部沙箱之间的一层运行时，基于 AgentScope 实现，不改工具接口。控制面订阅模型的 token 流、记录已完成的工具转移，做步内预热和跨步预取；数据面做结果缓存和大文件直传。

三项技术

步内：根据流式 token 推测意图，提前预热（§3.1）。跨步：根据历史转移，在当前步执行时准备下一步（§3.2）。数据：复用等价的结果，大文件走带外通道（§3.3）。

系统

步内：两个路由器的并集

Fig. 3Fig. 4§3.1
Keyword Router
拿 token 流与每个工具的keyword 表匹配，命中的工具专属 keyword达到阈值 γ 就给出候选，在出现一个有区分度的 token 后几微秒内就能触发。γ 取 2。
Semantic Router
拿当前上下文与工具意图的表示做相似度比较，能识别措辞与工具描述重合很少的请求，也能借助规划消除通用的词的歧义。代价是需要更长的前缀，单靠它常常来不及掩盖重型沙箱的冷启动。实现用的是 TF-IDF 加近邻的稀疏检索。
并集
两路各自控制自己的误报，谁先给出可信信号就开始准备[[union]]。显式的意图由Keyword Router早早触发，隐含的意图由Semantic Router补上。
系统

跨步：沙箱依赖图上的马尔可夫预取

Fig. 5Fig. 6§3.2

步内预热只能利用当前步剩下的生成时间，沙箱启动比这更久时就不够了。SpecBox 维护一张沙箱依赖图，记录相邻两步之间用了什么沙箱的转移次数，按一阶马尔可夫链估计下一步用各个沙箱的概率。当前步结束后，从候选里筛掉冷启动代价小的（低于 λ）和概率低的（低于 τ），再在每步的预算 B 内取概率最高的几个预热；实现中 λ=5、τ=0.6、B=1。每完成一次调用，就在后台补一条边、更新计数，不阻塞智能体。

系统

数据：语义缓存与带外传输

Fig. 7§3.3、§4
语义缓存
对确定性的调用保存规范化后的调用签名和结果。查找时先限定相同的工具，再比较规范化表示的相似度，超过阈值才复用[[cache-rule]]；未命中就正常执行并写入缓存。工具身份保证接口兼容，阈值限制只复用足够相似的调用。
带外传输
控制面照常传指令、完成通知、错误和小的元数据；大文件写进主机上的共享内存，控制面只传一个 64 位的引用，引擎直接从共享内存读。不需要改控制接口。

正确性边界。预热只把环境准备好，智能体确认调用之前不执行任何有副作用的操作，用不上的预热直接丢弃[[side-effect]]；缓存只用于确定性、相互兼容的调用；共享内存只在一台受信任的主机内使用。沙箱逃逸、恶意智能体和被攻破的基础设施不在威胁模型内[[threat]]。

实验

一台 16 核、256 GB 内存的服务器，沙箱是 Docker 容器，模型是通过阿里云 DashScope 生产 API 并发调用的 Qwen3.5-Max[[api]]。负载基于 MCPBench 的 32 个开源 MCP 工具服务器：先为每个工具生成 20 个单轮模板，再由一个大模型规划器逐步生成 1 到 10 步的会话，每一步都在真实的工具服务器上执行[[bench]]，共 200 条轨迹，平均每个会话 6.4 步、每步 2.96 个工具。对照是常驻（所有候选工具一直保持预热，代表延迟下界）和按需。

实验

每个会话累计的沙箱准备时间

Fig. 9§5.2.1

只统计每次工具调用前等沙箱准备好的时间，不含沙箱内的计算。按需的累计时间随步数增长，分布长尾明显；SpecBox 集中在一秒以内。相对按需降低到 1/4.53[[cum]]，与常驻相差 10.6%[[gap]]。

Fig. 11§5.3.2

结论

结论

SpecBox 把智能体运行时从“想好了再准备”改成边想边准备：生成过程中用 keyword 和语义两路推测要用的沙箱并提前启动；按历史转移在当前步就准备下一步；等价的调用直接复用结果，大文件绕开 RPC 走共享内存。实验中 P99 端到端延迟最多降到按需的 1/2.9，峰值内存比常驻低 45.9%，延迟接近常驻、内存接近按需。论文还认为同样的机制可以用于智能体强化学习的 rollout，掩盖环境初始化的开销。

局限

局限与讨论

论文承认的局限：一阶马尔可夫在开放的长程任务上准确率可能下降，但跨步预取落空时还有步内预热兜底；共享内存传输要求引擎和沙箱在一台主机内，计划用 RDMA 扩展到多机[[markov]]。

本页说明：负载是由大模型规划器生成的合成会话，长度均匀分布在 1 到 10 步，不是真实用户的轨迹；工具来自 MCPBench，冷启动多为几秒，重型沙箱（如带 GPU 的环境）较少。实验在一台 16 核机器上进行，模型走商业 API，生成速度随服务商负载变化，而步内预热能争取到的时间恰好取决于生成速度。文中系统名称（SpecBox、Laplace、PredBox）和若干数字前后不一致，读具体数字时需要留意。
