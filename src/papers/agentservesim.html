背景

领域定位

大模型推理服务引擎：vLLM（组批、KV 缓存管理、前缀缓存）
请求级服务模拟器：Vidur、APEX、LLMServingSim
有状态请求链、因果释放：Frontier
program 级、KV 保留与调度可编程：AgentServeSim

推理服务研究有两条线。一条是为智能体设计新的服务策略：InferCept 和 Continuum 研究工具调用间隙里 KV 缓存怎么留，Autellix 按 program 而不是按 request 排队，SMetric 按会话分配机器[[policies]]。另一条是模拟器：用真机上测出的算子耗时，在 CPU 上推算服务性能，省掉昂贵的 GPU 实验。两条线此前没有接上，现有模拟器表达不了前一条线里的那些策略。

AgentServeSim 建在 LLMServingSim 2.0 之上，加了一层 program 层，使这些智能体专用的策略能在模拟器里组合、比较。

背景

基本概念

program
一次智能体任务的完整执行：调用大模型、等工具、再调用大模型，如此交替。论文也把它叫 job，比如解决一个 SWE-bench 问题就是一个 program。
turn
program 中的一次大模型调用（论文也叫 call）。后一个 turn 的输入包含前面所有 turn 的内容。
tool gap
两个 turn 之间等待工具执行的时间。
KV 缓存
模型为已处理的每个 token 存下的中间结果，生成后续 token 时复用。它存在显存里，是推理服务最紧张的资源。
前缀缓存
新输入开头和已缓存的内容相同时，直接复用这部分 KV 缓存，跳过计算。
prefill 与 decode
prefill 一次性处理输入，计算量大；decode 逐个生成输出 token。KV 缓存被丢掉后，下一个 turn 要把整段上下文重新 prefill。
JCT
job completion time，一个 program 从到达到最后一个 turn 完成的总时长，是本文的主要指标。
TP
张量并行度，TP2 表示模型切分到 2 块 GPU 上运行。
主线

问题、抽象、验证、应用

问题

智能体的完成时间取决于推理引擎的三个决定：KV 缓存留不留、下一个 turn 派到哪台机器、和其他 program 谁先执行[[jct-depends]]。在真机上逐个试太贵[[gpu-hours]]，现有模拟器又以单个 request 为单位，表达不了它们[[request-level]]。

抽象

把 program 看作操作系统里的进程[[os-analogy]]：下一个 turn 何时出现由模拟本身算出来；三个决定做成可替换的策略代码。

验证

让模拟器和真实 vLLM 运行相同的策略和负载，比较完成时间。20 组对照的平均 JCT 误差，在 B200 上不超过 5.5%，在显存紧张的 RTX PRO 6000 上不超过 5.2%。

应用

每个模拟点约 1 个 CPU 核时，真机要占两块 GPU 跑 3 到 6 小时[[cost]]。于是可以大量比较策略组合，并让大模型自动改写策略代码。

问题

请求级模拟器为什么不够

§1、§2

请求级模拟

每个 request 的到达时间从记录里读出。request 结束时，KV 缓存立即释放，或按固定规则当普通缓存。

program 级模拟

下一个 turn 的到达时间由模拟算出。KV 缓存归 program 所有，去留由策略决定。

差别在到达时间。下面的例子说明为什么不能照抄录下的时间戳（数字是示意）。一个 turn 执行 2 秒，之后工具运行 5 秒：

策略排队等待完成时刻下一个 turn 到达时刻
录制轨迹时用的策略 A1 s3 s8 s
想评估的策略 B10 s12 s17 s

策略 B 下，下一个 turn 应该在第 17 秒到达，这又改变了那一刻的队列和 KV 池状态。如果按录下的第 8 秒重放，策略本该改变的东西就被固定死了，测不出换一种策略会怎样[[replay-fixed]]。KV 缓存也有类似问题：请求级模拟器在 request 结束时就决定了缓存的命运，而对智能体来说，tool gap 本身就是要做决定的时刻[[gap-decision]]。最接近的 Frontier 已经能按完成时间释放下一个 request，但把它固定派到上一个所在的实例，缓存保留也交给引擎自带的前缀缓存[[frontier]]，这两处都不能替换成别的策略。

系统

架构：在原模拟器上加一层 program 层

Figure 1

下方大框是 LLMServingSim 2.0 原来就有的部分：服务实例里的设备、性能模型、KV 缓存管理器、组批调度器和执行图生成器，由 ASTRA-sim 算出计算、通信和访存的耗时。它们模拟的是引擎机制。

上方是新增部分。Program Orchestrator 为每个 program 维护一个控制块（PCB），一个 turn 准备好时交给左边的 Dispatch Plane，决定派到哪个实例、优先级多少；完成时交给右边的 Retention Plane，决定缓存的价值和保护时间。这个结构借用了操作系统对进程的处理方式：一个 turn 相当于一段计算，工具调用相当于阻塞的系统调用，KV 缓存相当于跨越多次调度一直需要的工作集[[os-analogy]]。

§3 的三个定义：模拟器为什么需要它们

模拟器要回答的问题是“换一种策略，JCT 会怎样变”。这要求它做到三件事：算出下一个 turn 何时到达，让策略能看到跨 turn 的历史，并规定策略能决定什么。下面三个面板一一对应。

定义

到达时间由模拟算出

式 (2)
下一个 turn 的到达时刻 = 这个 turn 的完成时刻 + 这个 turn 之后的工具耗时

工具耗时、token 数这些属于任务本身的内容从记录里读取，所有策略相同。完成时刻包含排队和执行，随策略变化。两者相加，就把前面例子里的 8 秒和 17 秒都算对了。这个公式就是 program 层的动力来源，到达时间不再是输入，而是运行结果。

定义

控制块记录策略要用的历史

§3.2
PCB 记录谁需要它
累计被服务时间PLAS 排队
上次所在实例会话亲和路由
KV 是否还在、是否受保护回收和排队决定
正在等哪个工具按工具设置保护期

单个 request 结束后状态就没了，这些跨 turn 的信息需要一个地方存放。记录里还存着未来的信息，比如下一轮输出多少 token、工具要跑多久，这些在发生之前不进入 PCB[[causal-boundary]]，因此模拟器里表现好的策略不会依赖部署时拿不到的信息。

定义

策略只回答两个问题

式 (1)
时机策略返回
turn 到达πdispatch派到哪个实例，优先级多少
turn 完成πretain缓存的价值，保护到什么时候

两个函数的输入都是这个 program 的 PCB 和当前系统状态（各实例负载、KV 池占用率）。策略只说要什么，组批、抢占、回收内存、何时执行仍由引擎机制完成[[declarative]]。有了这条分界，换策略时不用改引擎模型，模拟和实测才能运行相同的决策逻辑。

系统

三处机制上各有哪些策略

§3.3、§3.4、附录 E

实例选择（routing）

机制：turn 必须落到某个实例；缓存只在这个实例的 KV 池里。

round-robin依次分配
least-loaded选负载最低的实例
session affinity回到上次的实例，过载时才换

队列排序（scheduling）

机制：实例内优先级数值小的 turn 先进入批次，数值相同时先到先执行。策略的差别在优先级取什么。

FCFS这个 turn 的到达时刻
Program-FCFS它所属 program 的到达时刻，早到的 program 一路优先
PLASprogram 累计被服务的时间，服务得少的优先，短任务不会被长任务堵住

缓存回收（retention）

机制：KV 池不够时，先回收过了保护期的缓存，再回收价值低的。策略的差别在保护期和价值怎么设。

立即释放不留，等同请求级模拟
固定 TTL一律保护 τ 秒（取 2 秒），假设间隙都差不多长
按工具 TTL取该工具历史间隙的 90 分位数
随压力调整 TTLKV 池占用从 70% 升到 90%，保护期从 τ 缩到 τ/2
LRU价值按最后访问时间，先回收最久未用的
min-waste比较留着占用的显存时间和丢掉后的重算代价，决定留或不留

回收规则还有一点值得注意：保护只是偏好[[preference]]。所有缓存都在保护期内时，价值最低的照样被回收，避免保护过多导致新 turn 无处安放。这样缓存能活多久成了可以编程的结果，而显存容量这条硬约束仍由内存管理器保证[[retention-summary]]。

模拟器和 vLLM“共用接口”是什么意思

§4、§5.3、附录 E、Listing 3
class EvolvedScheduling(SchedulingPolicy):
    engine_args = {"scheduling_policy": "priority"}

    def priority(self, pcb, now):
        # PLAS：累计服务时间越少，数值越小，越先执行
        return int(round(pcb.attained_service_s * 1000.0))

指实际的策略实现相同，语法结构相似还不足以描述它。一个策略是一个 Python 类，模拟器和 vLLM 执行相同的类[[same-impl]]，vLLM 一侧通过一层很薄的适配器接入。左边是论文给出的 PLAS 代码。

策略类型策略需要实现的方法返回
schedulingpriority(pcb, now)一个整数，小的先执行，和 vLLM 的优先级语义一致[[small-first]]
retentionon_turn_complete(pcb, now)、on_turn_arrival(pcb, now)protect(until)、release、evict 或 none
routingselect(pcb, inflight, now)实例编号

这些方法是 AgentServeSim 定义的策略接口，不是 vLLM 原生的 API，适配器负责把它接到 vLLM 上，论文没有详细描述适配器的内容。这样设计的好处有两点：比较模拟和实测时两边的决策来自相同的代码，误差才能归因于模拟器的时间模型；在模拟器里搜到的策略可以不改动地放到 vLLM 上运行[[unchanged]]。

实验的整体逻辑

全部实验分三步，目的不同，不要混在一起看。先证明模拟器算得准，再用它比较策略，最后用它自动搜索策略。

实验要回答的问题固定什么改变什么看什么指标在哪里跑
保真度验证模拟出的时间和真机对得上吗？策略（固定 TTL 加 PLAS）GPU、模型、负载、到达速率，共 20 组模拟相对真机的 JCT 误差模拟器和真机都跑
策略扫描哪种保留和排队的组合更好？硬件、模型、负载、速率保留策略、排队策略平均 JCT 相对基线的变化只在模拟器
策略搜索大模型能否写出比人更好的策略？硬件、模型、负载、速率策略代码本身平均 JCT 相对种子策略的降幅只在模拟器

保真度验证：模拟器和真机对得上吗

这组实验只评价模拟器，不评价策略好坏。TTL 加 PLAS 只是一种设置，选它是因为这时模拟器自己的决定会影响后续，比引擎默认设置下更难算准。

验证

怎样让两边可以比较

§4

相同的输入分别交给模拟器和真实的 vLLM 0.19：相同的 prompt、输出长度和工具耗时，相同的 program 到达时刻[[replay-same]]。排队顺序、缓存是否还在、下一个 turn 何时到达由两边各自算出。两边的差异就只来自服务系统的行为，智能体输出的随机性被排除。

模拟器的硬件参数按真机设置，这是它算得准的基础：先用 profiler 在每种 GPU 和模型组合上实际测出每个算子的耗时，多卡通信用实测带宽，KV 池大小用 vLLM 自己报告的数值。

GPU 和模型
B200（180 GB 显存，8B 用 1 卡、70B 用 2 卡）；RTX PRO 6000（96 GB 显存，70B 用 2 卡，显存紧张）
到达速率
每秒新到达几个 program（JPS）。五档从 0.02 到 0.10，即平均 50 秒到 10 秒来一个，用来改变系统负载。

每组只有一个服务实例，所以验证覆盖了保留和排队，没有覆盖 routing[[single-instance]]。

实验放在最能体现差异的显存紧张场景：RTX PRO 6000、70B、50 个 SWE-bench program、0.02 JPS。指标是平均 JCT 相对基线（LRU 加 FCFS，3726 秒）的变化，负值表示更快。结果是只换保留策略、排队仍用 FCFS 时，JCT 没有改善；换成 PLAS 才有明显改善；随压力调整 TTL 配 PLAS 最好，降低 5%。

两者的分工可以解释这一点：排队决定哪些 program 要等，保留决定它们回来时缓存还在不在[[who-waits]]。本页的推测是，FCFS 下 turn 回来后要排在大量 request 后面，等轮到它时被保护的缓存往往已经过期，保护白占了显存；PLAS 改变执行顺序后，被保护的缓存才更有机会用上。另一个结果是固定 TTL 配 PLAS 反而比 LRU 配 PLAS 差 0.9 个百分点，它对所有缓存一视同仁地保护，挤掉了 PLAS 接下来要用的 program 的缓存[[fixed-ttl]]。所以保留策略不能单独评价，要看它和调度是否配合。

式 (7)、式 (8)

保留策略

保护截止 = 完成时间 + max(0.5, 上下文长度 ÷ 20000) × 该工具的平均间隙 × max(0.3, 1 − KV 池占用率)

上下文越长保护越久，因为丢掉后重算更贵；KV 池越满保护越短。它只带来 0.5% 的改善，因为在这个设置下保护期很少真正决定回收哪块缓存，48 个候选里有 40 个彼此相差不到 0.5%[[plateau]]。

排队策略（数值小者先执行）

优先级 = 1000 × √(累计被服务秒数) + 0.03 × 上下文长度 − 0.10 × 上下文长度 × (缓存仍在 ? 1 : 0)

三项分别让已运行很久的 program 不至于被压得太靠后、让重算便宜的短上下文优先、让缓存还在的优先[[sched-terms]]。后两项在第一代就出现了，贡献了大部分收益。这条规则换到 0.02 JPS 下仍降低 2.3%。

结论

结论

AgentServeSim 把模拟的单位从 request 换成了 program，下一个 turn 何时到达、缓存在不在，都是模拟执行的结果，不再照抄录下的数据[[conclusion]]。它把 KV 回收、队列排序和实例选择做成可替换的策略，和 vLLM 执行相同的策略代码。20 组对照中平均 JCT 误差不超过 5.5%。

模拟器把评估一个策略的成本从数小时的双卡 GPU 时间降到约一个 CPU 核时，使系统地比较策略、让大模型自动搜索策略成为可能。比较的结果说明排队对 JCT 的影响大于保留，两者必须配合设计。

局限

局限与讨论

验证只用了一个服务实例，routing 尚未与真实系统对照；模型只有 Llama-3.1 的两个规模，负载两类，策略组合只验证了固定 TTL 加 PLAS 一种。换成混合专家模型、更长的上下文或 prefill 与 decode 分开部署的架构，准确度需要重新确认。演化出的策略针对特定的负载和硬件，本来就不追求通用[[deployment-specific]]。

策略扫描和搜索的结果都只来自模拟器，收益（0.5%、2.8%、5%）和拥堵时单个 program 7% 到 11% 的模拟误差在量级上接近，更适合看作模拟器能充当搜索评分器的可行性演示。长期价值更大的是那层接口，它让 InferCept、Continuum、Autellix 等系统中分散的策略可以放在一起组合比较。
