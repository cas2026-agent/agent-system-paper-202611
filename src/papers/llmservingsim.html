LLMServingSim 2.0: A Unified Simulator for Heterogeneous and Disaggregated LLM Serving Infrastructure

LLMServingSim 2.0：面向异构、拆分式大模型推理服务基础设施的统一模拟器

Jaehong Cho、Hyunmin Choi、Guseul Heo、Jongse Park，KAIST

arXiv 2602.23036v2，cs.DC，2026
计算机系统大模型推理服务性能模拟器异构与拆分部署
背景

领域定位

大模型推理服务的性能模拟
硬件级模拟器：LLMCompass、ADOR、ASTRA-sim
系统级模拟器：Vidur、APEX、TokenSim、LLMServingSim
请求级、异构硬件与拆分部署：LLMServingSim 2.0
program 级，建在它之上：AgentServeSim

新的推理服务硬件和部署方式在真机上很难逐个试：要有设备，要搭大规模环境，连粗略比较几种方案都要投入大量工程。模拟器因此成为早期探索的主要工具。现有的两类模拟器各缺一块。硬件级模拟器算得细，但只看固定的算子执行，没有 request 到达、组批变化和缓存复用[[hw-centric]]。系统级模拟器有服务层，但前缀缓存、prefill 与 decode 分开部署、异构设备这些近年的主流手段支持有限[[vidur]]。

LLMServingSim 2.0 的目标是把这两部分放进一个循环里模拟。它的上一版只支持单个实例，也没有混合专家模型和前缀缓存[[ls1]]，2.0 在此基础上扩展到多实例、异构设备和这些服务技术。

背景

基本概念

prefill 与 decode
prefill 一次处理全部输入，主要吃算力。decode 逐个生成 token，每步都要读 KV 缓存，主要受内存带宽、容量和缓存位置限制[[prefill-decode]]。两个阶段需要的硬件不同，这是后面拆分部署和 PIM 的出发点。
KV 缓存
模型为已处理的每个 token 存下的中间结果，随输出变长而增长，占显存。
前缀缓存
新 request 开头和已缓存内容相同时，复用这部分 KV 缓存，跳过 prefill。
混合专家模型（MoE）
每层有多个专家子网络，每个 token 只激活其中几个。相对地，每个 token 都走全部参数的模型叫 dense 模型。
PIM
processing-in-memory，内存芯片里带计算单元，数据不用搬到加速器上就能做部分运算。CXL 是一种可以外接大容量内存池的互连。
TTFT、TPOT、ITL、TPS
第一个 token 的等待时间；平均每个输出 token 的时间；相邻 token 的间隔；每秒生成的 token 数。前三个针对单个 request，TPS 针对整个系统。
TP、PP、DP、EP
四种把模型放到多个设备上的方式：张量并行切分每层的张量，流水线并行按层切分，数据并行多放几份副本各接各的 request，专家并行把 MoE 的专家分到不同设备。
主线

问题、方法、验证、用途

问题

服务系统的性能不再单独由硬件或软件决定，而取决于两者运行时的互相影响[[isolation]]。现有模拟器无法把异构硬件和拆分部署放在一个运行时框架里模拟[[abstract-gap]]。

方法

把服务决策和硬件行为放进一个循环[[abstract-loop]]：组批、放置、插入数据搬运，由 ASTRA-sim 算出耗时，结果再影响下一轮决策。硬件用算子级 profile 描述。

验证

和 RTX A6000、H100、TPU 上的真实 vLLM 对比吞吐、延迟、显存、功耗，摘要给出的平均误差是 0.95%，模拟耗时约 10 分钟[[abstract-err]]。

用途

评估手头没有的硬件和部署。案例是给 GPU 加上 PIM，只在模拟器中进行：decode 阶段吞吐提高到 1.43 倍，每 token 能耗降低 14.8%。

机制

模拟对象：一个 request 在服务系统里经历什么

§II、§III-A

模拟器要复现的是下面这条路径。多个 request 同时在路径上，每一步的资源都被别的 request 占着，所以一个 request 的耗时取决于当时系统里还有谁。

request 到达到达时刻来自负载配置
→
路由选一个服务实例
→
排队，进入 batch取决于内存放不放得下
→
prefill命中前缀缓存可跳过一部分
→
decode，反复执行KV 缓存增长，可能在内存层之间搬运
→
完成，释放资源队列里的 request 才能进来

只把每个算子的耗时加起来算不出这条路径的结果：batch 的组成不断变化，KV 缓存在哪一层决定访问多快，不同设备要互相等待，路由可能不均衡[[static]]。这些都要随时间逐步推演。下面这个例子是示意：一次 KV 搬运变慢，这个 request 晚一点结束，它占的显存也晚一点释放，下一个 batch 就放不下那么多 request，吞吐因此下降，排队又变长。论文所说的“交互”指的就是这种连锁反应。

近年的两个趋势让这条路径更复杂。一是异构：一个集群里可能有不同代的 GPU、TPU、NPU、PIM 和 CXL 设备，算力、带宽、容量和功耗各不相同。二是拆分：把原本放在一起的部分分开，每种分法都带来新的数据搬运。

拆分方式分开了什么，为什么要分模拟器必须多算的开销
prefill 与 decode 分离两个阶段放到不同的实例，prefill 不再打断 decode，各自可选合适的硬件KV 缓存从 prefill 实例传到 decode 实例，受网络拓扑和带宽限制
注意力卸载注意力算子放到 PIM 上，其余留在 GPU，因为注意力要大量读 KV 缓存中间结果和 KV 缓存在两种设备间来回传，还要互相同步
专家并行与卸载MoE 的专家分到多个设备，暂时不用的移到主机内存，省显存token 的路由、设备间全互联通信、加载被移走的专家
多层前缀缓存缓存放到显存、主机内存、CXL 内存池，容量更大，还能跨实例共享命中在下层时要把 KV 缓存逐层搬回显存，还会争抢带宽

系统：一个循环，三个组件

先看整体循环（Fig. 1），再看循环里做决策的 MSG（Fig. 2）和计算耗时的 System Simulator，最后看硬件数据从哪里来。

系统

输入、循环、输出

Fig. 1§IV-A、§IV-B
  1. 三份输入Workload 给出模型、request 内容和到达规律；Cluster Config 给出设备、内存、拓扑和服务策略；Profiles 给出每种设备上每个算子的耗时和功率。
  2. Execution Planner 只运行一次启动时按配置为每个模型建好 MSG，分配设备，装上策略，配好下面的模拟器。
  3. 红色箭头是循环Router 把 request 分给 MSG，MSG 为当前 batch 生成执行图，System Simulator 算出结果并推进下一轮，直到所有 request 完成[[loop]]。
  4. 两种输出运行时持续给出功率、内存、吞吐；结束后给出每个 request 的 TTFT、TPOT、排队时间、端到端延迟。

循环的设计决定了这个模拟器能看到什么。执行图每轮新生成，所以 batch 里有谁、KV 缓存在哪、要插入哪些搬运，都按上一轮结束时的状态决定。System Simulator 算完后把结果返回，才有下一轮[[iter]]。如果事先把配置和算子耗时算成一个固定结果，前面例子里的连锁反应就不会出现。

系统

MSG：决策发生的地方

Fig. 2§IV-C

一个 MSG 对应一个大模型服务实例[[msg-unit]]。上半部分是配置：模型、策略、设备池，以及内存、功耗、性能三个模拟子模型。下半部分是流水线，走一遍产生一张执行图。

Batch Scheduler
从队列挑 request 组 batch。它要先问内存模型放不放得下，同时考虑前缀缓存的驻留情况和回收代价[[batch]]。内存因此直接影响 batch 大小，进而影响吞吐。
Operation Mapper
按并行方式和卸载规则把每个算子分给设备，并从 profile 取出它的耗时和功率。
Operation Scheduler
排出依赖关系，组成有向无环图，并插入所需的通信和内存操作。回收和换入缓存的开销也在此变成图上的节点[[eviction]]。

论文的“策略”（policy）是用户配置的选择，比如路由方式、并行方式、回收规则和卸载规则。“模型”是模拟器算开销的方法。换策略不需要改模型，这使比较不同部署只要改配置。

系统

System Simulator 算耗时

§IV-D

它接收 MSG 生成的执行图，节点带有设备类型、耗时、内存、通信和功率信息，边是依赖关系。它根据集群拓扑算出同步开销、网络争抢、设备间通信和访存延迟。

底层是修改过的 ASTRA-sim 和 Chakra。这两个框架原本面向训练那种简单重复的通信模式，不足以表达推理服务的动态过程[[astra]]。论文为此补上异构计算结构、由算子驱动的执行图和专家并行，把内存层级扩展到显存、主机内存、存储和 CXL 内存，并增加了 PIM 上的运算操作[[pim-ops]]。

系统

硬件数据从 profile 来

§IV-A

每种硬件的算子耗时和功率要先测出来。对一组“模型、设备”，只需跑一个 decode block，一般在 2.1 小时内完成，例如 H100 上的 Llama 3.1-70B[[profile]]。结果存下来，之后的实验反复使用，不再需要这台设备。只测一个 block 就够，本页的理解是大模型由结构相同的 block 堆叠而成，其余可以推算。

这也是加入新硬件的方式。手头没有实物时，profile 可以来自外部的硬件模拟器，PIM 就是这样接入的[[ext-profile]]。代价是这种情况下结果的可信度取决于外部模拟器，后面 PIM 案例要带着这一点看。

功耗模型分七块

§IV-C
部件如何计算
加速器三种状态：idle、active、standby，随利用率切换[[power-7]]

互连在这里包括交换机，“其他”包括主板和散热。功耗并入模拟的目的是让性能和能耗能一起比较：一种部署更快，但多带一组设备，总能耗未必下降。Fig. 10 的 PIM 案例就比较了这种取舍。

用法：四种部署怎样配置

两张图展示 §V 的四种部署。它们有一个共同点：用户只写策略，通信、搬运和同步操作由模拟器自动插入执行图并计入耗时。

用法

单个 MSG 之内的两种部署

Fig. 3§V-A

(a) 异构设备：OPT-6.7B，1 块 H100 加 1 个 PIM

颜色表示算子在哪个设备上执行。卸载规则把 Op1、Op2（绿色）放到 PIM，其余留在 H100。Operation Scheduler 在图中加入 Mov 和 Sync：注意力执行前把中间结果和 KV 缓存传到 PIM，结束后再传回来[[attn]]。这些传输算进总时间，所以卸载是否划算要由模拟结果决定。

(b) 混合专家模型：Mixtral-8x7B，4 块 H100

Expert Router 模拟门控网络，逐 token 决定去哪个专家[[moe-router]]，可选随机、轮询、按比例均衡或自定义规则。图中专家 4 已被移出显存（虚线框），有 token 路由到它时，执行图就出现 Ld 加载节点。这个节点也由调度器自动生成[[moe-graph]]。token 的走向决定了加载和通信多少，因此每轮的执行图都不一样。

用法

多个 MSG 之间的两种部署

Fig. 4§V-B

(a) prefill 与 decode 分离：M 个 prefill，N 个 decode

Router 分发 request 时同时告知它之后由哪个 decode 实例接手。prefill 这一侧的调度器自动插入逐层传输 KV 缓存的操作[[pd]]，耗时由网络拓扑和带宽决定。图中两边的设备可以不同（H100 和 A100），M 和 N 的比例可调，因此能比较“用什么硬件做哪个阶段、配多少台”。

(b) 多层前缀缓存：显存、主机内存、CXL 内存池

图中从里到外是三种配置范围。只用显存时每个 MSG 有自己的基数树缓存；加上主机内存，相同节点上的 MSG 共享第二层；启用 CXL 内存池后，所有 MSG 共用一个全局缓存[[prefix-tiers]]。缓存范围越大，命中机会越多，但命中在下层时需要搬运，这部分开销同样进入执行图。

验证

吞吐和延迟：随时间的过程对得上吗

Fig. 5§VII-A

每张小图比较真实 vLLM 和模拟器在相同负载下每秒的吞吐。两行是两套 GPU：RTX A6000 上跑 Llama 3.1-8B 和 Phi-mini MoE，H100 上跑 Llama 3.1-70B 和 Mixtral 8×7B，后者张量并行度为 4。四列是四种部署：多个 dense 实例、单实例加前缀缓存、prefill 与 decode 分离、MoE。

结论是模拟器既能跟上过程，也能算准总量。逐时刻的吞吐误差在 RTX A6000 上是 5.14%，H100 上是 3.29%，论文归因于动态组批、到达波动和阶段切换[[ts-err]]。合计整段运行的吞吐和延迟后，误差降到 0.99% 和 1.54%[[agg-err]]。两组数字差几倍，本页的解释是逐时刻的偏差有正有负，合计时相互抵消。所以论文摘要的约 1% 代表总量，看某个时段的吞吐要按 3% 到 5% 估计。

曲线形状也和负载的设定吻合：300 个 request 按每秒 10 个到达，约 30 秒后不再有新 request，吞吐随后下降。RTX A6000 上的 MoE 明显更慢，跑到约 80 秒才结束，说明积压严重，这一格也是从图上看偏差最明显的。

验证

功率和能耗

Fig. 6§VII-A

这个实验要检验三状态功耗模型，所以负载特意做成脉冲：10 个 request 一组，每 60 秒发一次，共三次，中间留出空闲[[pulse]]。(a) 和 (b) 比较张量并行度 1 和 2 下的实测功率与模拟功率，总能耗平均误差 1.34%[[power-err]]。从图上估读，TP1 的三段功率约为 680、440、380 瓦，TP2 约为 930、510、400 瓦。TP2 多开一块 GPU，峰值更高，但执行更快，所以峰更窄。

假设分析

给 GPU 加 PIM 值得吗

Fig. 10§VII-C

这是模拟器的目标用法：评估没有实物的硬件。三种系统都跑 Llama 3.1-8B 和单块 RTX A6000，只有内存不同。两个 PIM 系统把主内存换成 256 个通道、每通道 1 GB 的 HBM2。负载也按 PIM 定制：256 个 request，正好一个通道一个，每个输入 128、输出 512 token[[pim-setup]]。SBI 是 NeuPIMs 提出的子 batch 交替执行。

这个实验没有真机对照，图中数字全部是模拟结果。

(a) 吞吐

前 25 秒以 prefill 为主，收益有限，因为 PIM 主要加速 decode。prefill 结束后，GPU+PIM 的吞吐是 GPU 的 1.43 倍[[pim-gain]]。1.43 倍只是 decode 段的值：从图上估读，全部 request 完成的时间从约 53 秒缩短到约 46 秒，整体只快约 15%。输出更短的负载，收益还会更小，这是本页的推断。

SBI 反而和纯 GPU 差不多。它把 batch 切开，提高了硬件利用率，却让 GPU 实际看到的 batch 变小。只有持续维持 256 以上的超大 batch 时才有效，也就是 26 到 35 秒那段[[pim-sbi]]。

(b) 能耗

GPU+PIM 总能耗最低，每 token 能耗降低 14.8%[[pim-energy]]。原因在于跑得更快：恒定功率的部件（CPU、其他）随时间缩短而少耗能，内存能耗只略有增加。SBI 没有提速，多出的 PIM 又要耗能，所以比纯 GPU 还略高。

折线可以用总能耗验算：约 37 kJ 除以 256×512 = 131072 个输出 token，约 0.28 J，和图一致。这说明指标只数输出 token。

这个案例说明模拟器能揭示单看硬件参数看不到的结果：提高硬件利用率的 SBI 没有带来收益，因为它和组批发生了相互作用。不过 PIM 的结论依赖两点假设。负载是配合 PIM 选的（decode 占比高，request 数等于通道数），PIM 的算子数据也没有和实物对过。所以 1.43 倍和 14.8% 应读作“这个设定下的模拟结果”，不宜读作 PIM 的一般收益。

关联

结论

结论

LLMServingSim 2.0 把服务决策和硬件行为放进一个循环：每轮按当前状态组 batch、放置算子、自动插入搬运和同步，再由改造过的 ASTRA-sim 算出耗时和资源，结果决定下一轮。硬件以算子级 profile 接入，因此可以覆盖 GPU、TPU，以及通过外部模拟器接入 PIM。

在 GPU 真机上，全程聚合的吞吐、延迟、显存和能耗误差都在 1.6% 以内，逐时刻吞吐误差 3% 到 5%。相比已有模拟器，它在更多部署上可以运行，且各项指标更均衡；代价是单次模拟要 5 到 10 分钟。它的主要贡献是提供一个公开的共同底座，AgentServeSim 就是一个现成的例子。

局限

局限与讨论

支持的范围明显大于验证过的范围。Table I 里打勾的功能，有几项没有和真机对比过：Fig. 5 每一行只有一种 GPU，所以 Fig. 4(a) 中 H100 配 A100 的异构分离没有验证；CXL 内存池和注意力卸载只有模拟；TPU 只验证了单实例 dense；功耗和显存只在 RTX A6000 上对比过。异构恰恰是这篇论文的主打，在真机上却只能分别验证每种硬件。

负载也比较温和：300 个聊天 request，几十秒跑完，前缀命中率最高约 26%。长上下文、显存持续紧张、智能体这种高度重合的请求，都不在实验范围内。换到这些场景时，误差需要重新确认。此外，模拟器的精度建立在 profile 上，每增加一种模型和设备的组合都要重新 profile 一次；没有实物时，结果的可信度只能和外部硬件模拟器一样。
