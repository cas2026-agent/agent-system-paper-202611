The Cost of Dynamic Reasoning: Demystifying AI Agents and Test-Time Scaling from an AI Infrastructure Perspective

动态推理的代价：从 AI 基础设施的角度看智能体和测试时扩展

Jiin Kim、Byeongjun Shin、Jinha Chung、Minsoo Rhu，KAIST

arXiv 2506.04301v2，cs.LG，2026
计算机体系结构AI 基础设施负载刻画智能体与测试时扩展
背景

从静态推理到动态推理

Fig. 1

三行是三种使用大模型的方式。(a) 普通用法，输入直接变成输出。(b) 静态推理，模型先在内部写出推理步骤再作答。(c) 动态推理，问“巴黎到纽约最便宜的航班”，模型想到需要查航班，调用搜索工具，读到结果，据此继续推理，直到给出答案。

近年提升大模型能力的重点，从扩大模型和数据转向在推理时多花计算，这叫测试时扩展：参数不变，回答问题时投入更多计算来换效果[[tts]]。这篇论文测 (c) 这类负载对硬件和基础设施意味着什么。它属于“负载刻画”研究：不提出新系统，而是把一类新负载的资源特征测清楚，为后续设计提供依据[[first]]。

基本概念

Fig. 2
request
交给智能体的一个完整任务，论文也称 query。一个 request 对应从 benchmark 里取出的一道题，比如一个 HotpotQA 问题，从提交到给出最终答案算一个 request。
LLM call
对大模型的一次推理调用。一个 request 内部有多次 LLM call，论文有时也称其为 LLM request。
QPS
每秒送入的 request 数。
prefill
一次性读入整段输入
decode
逐个生成输出 token，速度受显存带宽限制
KV 缓存
已处理内容的中间结果，占显存
前缀缓存
新输入开头与旧输入相同时复用 KV 缓存，跳过这部分 prefill
p95 延迟
95% 的 request 在此时间内完成

图是智能体的组成：大模型扮演执行者、规划者、反思模块等角色，记忆、计划和工具为其提供支持。整体上是“LLM 推理”和“使用工具”两个阶段交替进行[[two-phases]]。这一交替结构是后面所有测量结果的根源：推理阶段 GPU 在忙，工具阶段 GPU 可能在等，而每一次推理的输入都比上一次更长。

主线

动机、实验、发现、主张

动机

智能体完成一个 request 往往要调用几十次大模型[[dozens]]，但体系结构研究主要针对静态大模型[[gap]]，基础设施可能在为过时的负载而优化[[yesterday]]。

实验

五种智能体在四个 benchmark 上运行，以普通聊天作对照。依次测单个 request 的执行、并发服务、多花计算换来的准确率，最后外推到数据中心规模。

发现

多花计算能提高准确率，但收益迅速递减；延迟波动变大；GPU 在工具执行时闲置；基础设施成本难以持续[[findings]]。

主张

智能体设计应从堆计算转向考虑成本的推理，优化单位成本换来的准确率[[compute-aware]]。

实验组：单个 request 内部发生了什么

一次只处理一个 request，排除并发的影响，分别测调用次数、时间构成、GPU 使用和输入长度。比较对象是不用工具的 CoT 和普通聊天。

结果Fig. 4

一个 request 调用多少次大模型和工具

纵轴是每个 request 的平均调用次数，每个小图的刻度不同。CoT 只调用一次大模型，使用工具的智能体平均是它的 9.2 倍，LATS 平均达到 71 次[[lats-71]]，因为它扩展搜索树时要为每个子节点单独推理。调用次数是后面所有成本的第一个放大因素。

结果Fig. 5

时间花在推理还是工具上

柱子（左轴）是一个 request 总时间的构成，菱形（右轴）是它的总耗时。平均来看大模型推理占 69.4%，工具占 30.2%[[lat-split]]，但比例取决于工具快慢：WebShop 的工具很快，几乎全是红色；HotpotQA 的维基百科调用慢，黑色占比明显变大。

两部分难以同时进行，因为互相依赖：要有大模型的输出才知道调哪个工具[[dependency]]，下一次推理又要用到工具的结果。粉色是 LLMCompiler 把工具调用提前发出造成的重叠，也只占总时间的 18.2%[[overlap]]。

结果Fig. 6

GPU 是否闲着

柱子是 GPU 时间用在 prefill、decode 和空闲上的比例，菱形是平均 GPU 利用率。HotpotQA 和 MATH 的工具在 CPU 或外部服务上运行，GPU 空闲最多占 54.5%[[idle]]。WebShop 工具快，HumanEval 工具本身用 GPU，空闲就不明显。可见 GPU 是否闲置取决于工具在哪里运行、运行多久。

GPU 工作时，74.1% 的时间是 decode，只有 4.7% 是 prefill，而 decode 受显存带宽限制[[decode]]，计算单元同样用不满。一个 request 内部挤不出更多并行，提高利用率只能靠同时处理多个 request。这引出了后面的并发实验。

结果Fig. 7

每个 request 的耗时有多不确定

这是 request 总耗时的分布。普通聊天集中，95% 在 9.7 秒内完成；ReAct 在 HotpotQA 和 WebShop 上的 p95 分别是 20.7 秒和 50.8 秒，右侧拖着长尾。长尾来自步数的不确定，有的问题很快答出，有的要反复搜索，一个 request 要多久事先无法预估，这对需要承诺响应时间的服务很不友好。

结果Fig. 8

每次 LLM call 的输入有多长

纵轴是 token 数。灰色是任务说明和示范例子，黑色是用户问题，绿色是之前模型输出的累积，黄色是之前工具结果的累积，红色是本次输出。绿色和黄色就是智能体多出来的部分：每次调用都要带上之前的推理和工具结果。HotpotQA 一开始约 1000 token，会涨到 3 到 4 倍。问答和网购任务的工具返回内容长，黄色大；数学和编程任务模型自己写得多，绿色大。LATS 是例外，它只带从根节点到当前节点的路径。

输入变长的直接后果是显存：用工具的智能体每个 request 的 KV 缓存平均是 CoT 的 3 倍，最多 5.4 倍[[mem-3x]]。

结果Fig. 9

前缀缓存能省下多少时间

每种智能体的两根柱子比较前缀缓存关闭和开启时单次推理的延迟，下部红色是 prefill，上部是 decode。相邻两次调用的开头完全相同，正是前缀缓存擅长的情况。开启后 prefill 时间平均减少 60.1%[[prefill-60]]，单次推理总时间平均减少 15.7%，减得没那么多是因为 decode 不受直接影响。CoT 只调用一次，几乎不受益。LATS 同时评估的子节点开头相同，可以共用一份 KV 缓存，显存需求平均减少 64.8%。

实验组：同时服务很多 request

前面提出 GPU 的空闲只能靠并发利用。这组实验测一块 GPU 实际能撑多大流量，以及前缀缓存在并发时的作用。

实验Fig. 10

并发实验的系统

request 按泊松过程随机到达服务入口[[poisson]]，分给智能体工作进程。工作进程在需要推理时向 vLLM 发出 LLM call，多个进程的调用在 vLLM 里拼批；需要工具时调用外部工具。

结果Fig. 11

一块 GPU 能撑多少 QPS

横轴是每秒送入的 request 数，纵轴是 p95 延迟，曲线上翘的拐点就是可持续的最大吞吐[[knee]]。并发把 ReAct 的吞吐从 0.10 和 0.19 QPS 提高到 2.6 和 1.2 QPS，平均延迟只变为 2.1 倍[[concurrency]]，HotpotQA 工具慢、GPU 空闲多，提升也最多。即便如此，它们也只有普通聊天 6.4 QPS 的约四成和五分之一[[peak-qps]]。

实线和虚线比较前缀缓存的开关。聊天的吞吐只提高到 1.03 倍，ReAct 提高到 5.62 倍[[prefix-5x]]：没有前缀缓存时，长 prefill 占住 GPU，堵住同批其他 request 的 decode，智能体多次调用放大了这种阻塞。

结果Fig. 12

前缀缓存省下多少显存

纵轴是 KV 缓存占用的显存，W/o 是关闭前缀缓存，W/ 是开启，流量固定（HotpotQA 0.2 QPS，WebShop 0.1 QPS）。开启后平均和峰值占用分别下降 51.7% 和 63.5%[[kv-mem]]。单 request 实验中除 LATS 外看不到这个收益，并发时不同 request 之间才能共享前缀。

实验组：多花计算换来多少准确率

前面只看成本，这组把准确率也放进来。每种配置跑 50 道题[[fifty]]，准确率按各 benchmark 的官方方法计算，成本用 request 总耗时衡量。

结果Fig. 13

所有配置上的准确率和成本

每个点是一种配置（示范例子数、最大步数等不同）。上排纵轴是准确率，下排纵轴是准确率除以延迟，即性价比；横轴都是延迟，对数刻度。

所有智能体和任务上规律一致：计算越多准确率越高，但每多花一份计算换来的准确率越来越少[[diminishing]]。ReAct 延迟低、准确率中等；Reflexion 准确率略高、延迟明显增加；LATS 准确率更高、开销大得多；LLMCompiler 在 HotpotQA 上又快又准，在步骤前后依赖强的 WebShop 上会产生多余的工具调用，效率反而不如 ReAct。

结果Fig. 14

放宽最大步数值得吗

只改变 ReAct 允许的最大步数，横轴是这个上限。灰柱是平均延迟，黑柱是 p95 延迟，红线是准确率，蓝线是性价比。起初准确率上升，很快红线和灰柱都不再增长，黑柱却继续直线上升[[tail-linear]]。拉高尾部的是少数做不出来、把步数用光的任务，它们消耗大量计算，几乎不贡献准确率。蓝色菱形标出性价比最高的配置，它不在准确率最高处。

结果Fig. 15

增加示范例子值得吗

横轴换成提示中示范例子的个数，其余读法与 Fig. 14 相同。增加例子起初明显提高准确率，之后收益变小甚至下降。平均延迟反而随例子增多而下降[[fewshot]]，因为好的例子让智能体用更少的步数完成任务，省下的步数抵消了提示变长的代价。

结果Fig. 16

多想几轮，还是同时试几条路

这是两种增加计算的方式，都在 HotpotQA 上，横轴延迟、纵轴准确率，颜色越深扩展越多。(a)(b) 是顺序扩展，增加反思轮数；(c) 是并行扩展，增加 LATS 每次扩展的子节点数。

顺序扩展越往后越不划算：Reflexion 多换 4 个百分点准确率，从 16.9 秒的配置出发多花 8.7 秒，从 56.0 秒的配置出发要多花 269.5 秒，成本是前者的 31 倍[[31x]]。并行扩展的子节点从 1 增加到 16，准确率提高 14.4 个百分点，平均延迟反而减少 196.3 秒[[parallel]]，代价是同时发出更多 LLM call，显存压力更大。所以延迟敏感、资源充足时用并行扩展[[parallel-advice]]；资源紧张时用顺序扩展，峰值资源需求低，代价是延迟高。

结果Fig. 17

小模型配好策略能否接近大模型

上排 Reflexion，下排 LATS；三列的横轴分别是延迟、总 token 数和 GPU 能耗，纵轴都是准确率。70B 用更少的步数和 token 就能达到高准确率，8B 要多想很多步。LATS 这一排 8B 接近 70B 的准确率[[8b-70b]]，Reflexion 这一排则追不上。由于 8B 只用 1 块 A100、70B 用 8 块，8B 的总能耗反而更低。测试时策略能在一定程度上弥补模型规模的不足。

结论

结论

智能体的成本可以拆成三个相乘的因素：调用次数成倍增加，每次调用的输入随历史累积而变长，调用之间夹着让 GPU 空等的工具时间。前缀缓存和并发处理能缓解后两个因素。一块 GPU 能撑的 QPS 仍只有聊天的几分之一，而测试时扩展本身面临收益递减，继续堆计算换来的准确率越来越少。

据此，智能体设计应从堆计算转向考虑成本的推理[[compute-aware]]。可行的方向包括：量化、蒸馏，按角色混用大小模型；按任务难度动态分配计算；在推理系统上采用分层 KV 缓存与缓存压缩、利用智能体输出格式固定的特点做推测解码、把 prefill 和 decode 分开部署以减少互相干扰。

局限

局限与讨论

业界对智能体还没有公认的服务质量标准，分析没有、也难以针对某个具体的延迟目标[[no-sla]]，它描绘的是不同配置下准确率和成本的取舍。实验规模也不大：每种配置 50 道题，A100 40GB，vLLM 0.6.6，最大 70B 模型。

换成新的硬件、推理引擎和更大的模型，绝对数字会变，但准确率收益递减、尾部延迟上升、工具执行时 GPU 闲置、前缀缓存对智能体特别重要这些规律与具体硬件关系不大，参考价值更持久。
