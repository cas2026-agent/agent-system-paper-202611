Don’t Let AI Agents YOLO Your Files: Information and Control in Agent-Native Filesystems

别让 AI 智能体随手动你的文件：面向智能体的文件系统中的信息与控制

背景

本地智能体以用户的权限动文件

Fig. 2§1、§2

Claude Code、Codex、Cursor 这类编程智能体在用户本机上运行，一次会话可能执行几百个文件操作和 shell 命令，用的是用户自己的权限。已经有智能体清空整块磁盘、毁掉无法恢复的个人文档、悄悄把凭据泄露给攻击者[[harm]]。

现有的外壳（harness）有三种防护：对内置工具按路径设策略；对 shell 命令按字符串匹配规则过滤；把 shell 命令放进沙箱。多数外壳在执行前请用户批准，但频繁弹窗让智能体停下来等人，用户最后要么一律点同意，要么打开 “YOLO 模式” 让智能体不受检查地运行[[yolo]]。

用户
开了自动批准，因为否则一次会话要答几百个弹窗；弹窗只显示命令，不显示效果。
问题

弹窗看不出命令做了什么

Fig. 5§3.5

只是把 ../foo 里的 hello 换掉，Codex 生成了一段带错误处理和校验的复合命令请用户批准。“以后不再询问 sed -i” 这样的规则要么太宽（放行一切原地编辑），要么太窄（这条命令不会再出现）。

问题

信息缺口与控制缺口

Fig. 1§3.6、§4.1

智能体自己说不清也管不住自己对文件的影响，而文件系统能直接看到并拦截每次访问。论文因此主张把信息和控制交给文件系统，提出“面向智能体的文件系统”应提供三个原语[[primitives]]：

查看效果
一条命令实际读了、改了哪些文件。智能体据此发现自己的错误或恶意行为，用户据此审阅整个会话。
撤销修改
覆写和删除都能撤回。智能体不必事先请示，先执行、看效果、错了就撤销重来；任务结束后用户一次性审阅剩下的改动。
拦截访问
读过的密钥无法“没读过”，这类访问必须在发生前拦下。规则按路径而不是按命令，无论哪个命令访问这个路径都受约束。

另有四条要求：覆盖智能体能访问的所有文件且不能被绕过；策略能在运行中调整；不要求底层文件系统支持快照等非 POSIX 特性；开销要小。

问题

已有手段为什么不够

Table 2§4.3
版本控制（Git）
只跟踪仓库里被选中的文件，.gitignore 里的往往正是敏感文件和大文件；历史存在 .git 里，智能体自己就能删掉；扩展到所有文件要扫描整棵树、哈希并另存副本。
版本化文件系统（ZFS、Btrfs）
粒度对不上会话：整个文件系统回滚会连带丢掉用户的其他改动；还要求专用的磁盘格式，现有数据得迁移。
联合文件系统（OverlayFS）
重命名下层文件要先整份拷到上层[[rename]]；一个可写层只记录总的结果，要按命令撤销就得层层叠加，层数越多查找越慢，层数还有上限。
访问控制与隔离
Docker、Bubblewrap 启动时就定好可见路径；Landlock 只能加限制不能放宽；都只能按既定策略即时决定，没法把一次意料之外的访问留给用户决定。
系统

YoloFS 的三个机制

Fig. 6Fig. 7§5.1

YoloFS 由一个 Linux 内核可堆叠文件系统（2.7 千行 C）和一个用户态 CLI（8 千行 Rust）组成，叠在整个底层文件系统之上。CLI 在挂载命名空间里以 YoloFS 为根文件系统运行智能体的每条命令，所以智能体绕不过去。三个机制分别对应三个原语：暂存（staging）把所有修改留到用户提交为止；快照和回溯（travel）让智能体看每条命令的改动并退回之前的状态；渐进式授权（progressive permission）在运行中让用户逐步定规则。

例子。智能体对一个含恶意依赖的项目执行 cargo build，不需要事先批准命令。依赖的脚本想读 SSH 密钥时，YoloFS 拦下并把路径和操作告诉用户，用户拒绝。命令结束后自动快照，智能体看到被拒绝的访问和暂存的改动，识别出攻击，回溯到前一个快照，换一个依赖重试。会话结束时用户审阅剩下的改动再提交。

系统

暂存：内容和路径分开存

Fig. 8Fig. 9§5.2

联合文件系统的暂存目录要镜像底层的目录树，所以重命名要拷贝内容。YoloFS 认为暂存内容的存储布局不必镜像目录树，只有呈现给智能体的视图需要保持层次[[decouple]]。于是用三个结构：

平铺文件库
底层文件系统里的一个目录，存放改过和新建的文件内容，每个文件用递增编号标识。
覆盖树
内核里的内存结构，把每个路径映射到三种后端之一：文件库里的暂存文件、底层文件系统的某个位置、不存在。路径可以指向底层的另一个位置，所以重命名不拷贝。
会话日志
只追加的文件。每次改覆盖树就追加一条记录：S 暂存、D 删除、R 重命名。内核只写不读，由 CLI 重放来审阅和提交。

提交或放弃只能由用户做，智能体不能自己提交[[commit]]。放弃就清空覆盖树、文件库和日志，底层文件系统不受影响；提交时 CLI 按重建的覆盖树把每个路径落到最终位置，遇到 a、b 互换这种环会先移到临时路径。

系统

快照与回溯：历史放在日志里

Fig. 10§5.3

只有暂存的话，所有命令的改动混在一个状态里，没法单独看或单独撤销一条命令。联合文件系统要保留中间状态只能冻结当前层再叠一层，越叠越慢。YoloFS 内核只维护当前的覆盖树，历史放在日志里：快照只是日志里的一个 P 标记，默认每条命令后打一个；暂存文件按代（generation）做写时复制，旧版本留着供查看和回溯。所以快照再多，正常的文件操作也不变慢。

每条记录带上受影响路径之前的后端（pre 字段），一段日志单独就能算出这条命令的净改动，不用从头重放。回溯不截断日志，而是追加一个 T 标记；被放弃的历史仍然保留，智能体如果发现回溯本身错了还能“回到未来”。

系统

渐进式授权

§5.4、§5.5

有些访问撤销不了，只能事先拦。智能体需要访问什么取决于任务，没法一开始就写全，所以 YoloFS 让访问来推动规则的完善[[progressive]]。每个路径五种策略之一：ask（每次问）、allow、write-ask（读放行、写要问）、read-only、deny。规则组成一棵树，路径继承最近祖先的策略，更具体的规则覆盖继承的。

命中 ask 时，内核阻塞发起访问的线程，把路径、操作和进程名交给 CLI 问用户；用户回答的是一次具体的访问，而不是一条看不懂的命令。超时则拒绝。用户可以在弹窗里直接装一条规则（“拒绝且不再询问”），规则随时可改，下一次访问就生效，并按项目保存。规则和授权决定只接受来自用户的请求，内核通过检查调用进程的根文件系统来识别智能体一侧，拒绝它的这类操作。被拦的访问和规则变更也记进日志，审阅时一并显示。

已接入 Claude Code、Copilot 和 Gemini 的工具调用钩子，每条命令都经 yolo run 执行。

智能体评测

两个问题：YoloFS 能否防住隐藏的副作用、让智能体自己纠正；在日常任务上能否减少用户交互而不降低成功率。现有基准单独评模型或外壳并绕过了批准弹窗，所以论文写了一个交互式驱动：在伪终端里运行每个智能体，监视虚拟屏幕上的权限弹窗并按固定策略作答，每个任务从全新的目录开始，限时 3 分钟，结束后检查文件状态。对比 Claude Code 2.1.45（claude-sonnet-4-6）加不加 YoloFS，以及 Codex、Copilot CLI、Gemini CLI。

性能评测

CloudLab 上一台 16 核 AMD EPYC 7302P、128 GB 内存的机器，Linux 6.8，底层是 SATA SSD 上的 Ext4。对比 OverlayFS（用多个下层目录加后处理模拟 YoloFS 的功能）和 BranchFS（一个面向智能体探索的 FUSE 研究原型，支持暂存、提交和嵌套分支），两者都没有权限控制。

快照增多与真实开发负载

Fig. 12Fig. 13§7

反复覆写十个文件来累积快照。OverlayFS 到约 50 个快照就失败了，因为挂载参数超过内核的长度上限[[overlay50]]。OverlayFS 和 BranchFS 的新建和读取随快照增多变慢，YoloFS 不变。提交时间随快照数线性增长，但 YoloFS 只读一个日志文件，比逐个查询快。

按一组真实的内核补丁走一遍：建 git worktree、编译内核，然后对每个补丁搜索阅读、修改、增量编译、git 提交，最后把全部改动提交到底层。YoloFS 与 Ext4 相当，只是最后提交十万多个文件多花 3.5 秒；OverlayFS 比 YoloFS 慢 18%，因为每次快照都要重新挂载；BranchFS 有 bug，初次编译之后就跑不下去[[workload]]。

结论

结论

§8、§9

290 份事故报告显示，问题出在用户和智能体既不知道命令对文件做了什么，也管不住。YoloFS 把这件事交给文件系统：所有修改先暂存，每条命令后快照，智能体看到改动能自己回溯纠正，用户最后统一审阅；撤销不了的访问按路径在发生前拦下，规则随运行逐步完善。隐藏副作用的 11 个任务中智能体自己纠正了 8 个，其余 3 个仍可由用户拒绝；日常任务成功率不降、交互更少；I/O 开销可忽略，快照到几百个也不变慢。论文最后主张：随着智能体越来越自主，文件系统应当暴露智能体的影响、让修改可撤销、在敏感访问发生前控制住[[conclusion]]。

相关工作一节提到了面向智能体的快照与恢复系统，其中包括 Crab 和 DeltaBox，评价是它们让智能体的执行可以恢复，但不暴露单条命令对文件系统的影响，也不做细粒度的文件访问策略[[related]]。

局限

局限与讨论

论文把非文件系统的接口（数据库、网页应用、云服务）排除在外，认为这些是互补的问题，三个原语可能也适用于其他有状态的系统。

本页说明：11 个隐藏副作用任务的项目都只有 10 到 41 行，是有意让智能体容易查清；真实项目大得多时，智能体能否从改动摘要里看出异常没有验证。另外 3 个任务中智能体把有害改动当成正常结果接受了，这说明，YoloFS 能保证的是改动可见、可撤销，至于是否有害，最终仍要靠用户审阅。日常任务每个只做一次操作，0.4 次交互里主要是项目外路径的首次询问；多步任务中规则逐步积累后的交互次数没有测。只评测了 Claude Code 加 YoloFS 一种组合。暂存期间修改都不落到底层，这也意味着智能体会话之外的其他程序看不到改动，长会话或多个工具协作时这一点的影响论文没有讨论。
