Murakkab: Resource-Efficient Agentic Workflow Orchestration in Cloud Platforms

Murakkab：云平台上资源高效的智能体工作流编排

Gohar Irfan Chaudhry、Esha Choukse、Haoran Qiu、Rodrigo Fonseca、Adam Belay、Ricardo Bianchini，MIT CSAIL、Microsoft Azure

OSDI 2026
计算机系统云平台工作流编排资源调度
背景

问题：三层配置各管各的

§1、§2.3、§2.4

智能体工作流把多个模型和工具组合起来完成一个任务。今天的做法是开发者用 LangGraph、LlamaIndex 等框架命令式地写出每一步用哪个模型、什么参数、多少 CPU 和 GPU；云平台只把智能体发来的推理请求当作普通 API 调用来自动扩缩。工作流对平台来说是一串不透明的调用，应用逻辑和模型、硬件选择绑死在一起[[opaque]]。

工作流级
用哪些智能体、怎样连接，例如要不要语音转文字这一步。
智能体级
每个智能体用哪个模型、什么参数，例如抽多少帧、辩论几轮。
硬件级
GPU 型号和数量、并行方式，CPU 还是 GPU。

三层各自优化，系统就无法追求端到端的目标，例如在满足每个请求的准确率要求的前提下成本最低，或在延迟约束下吞吐最高[[silo]]。论文的主张是在云平台上加一个控制面，把整个工作流（模型调用、工具执行、数据依赖）当作一张可以整体优化的计算图[[control]]。

Fig. 1§2.2
(a) 视频问答
多模态：切分场景、抽帧、语音转文字（STT）、目标检测，最后由多模态大模型回答关于视频的问题。

仿照 Claude Code，每个请求的执行结构不同：并行生成若干候选、按公开测试排序，可选审阅者，由一个编排模型按题目选择写代码的风格和投入多少计算。

论文先用测量说明三点：工作流和智能体的设置决定准确率与开销（Fig. 2）；硬件设置决定延迟、吞吐和能耗（Fig. 3）；组合起来的配置空间大到无法手工选择（Fig. 4）。

测量

工作流和智能体设置：准确率与生成量

Fig. 2§2.5

(a)(b) 视频问答：帧数（工作流内部智能体的参数）和要不要 STT（工作流结构）都明显影响准确率。Gemma-3-27B 用 10 帧、开 STT 时准确率最高，为 66.2%，生成的 token 也最多[[gemma]]；不同请求的生成量从 250 到近 1000 token，长尾明显。(c)(d) 代码生成：准确率随辩论者数和轮数变化；推理模型 DeepSeek-Qwen-32B 准确率最高，但中位数生成约 2 万 token，Gemma-3-27B 在相同设置下约 2500[[tokens]]。生成越多，延迟、费用和 GPU 负载越高。

测量

配置空间：组合起来数不过来

Fig. 4§2.5

每个点是一个完整的端到端配置（模型、硬件、并行方式、工作流参数的组合），横轴分别是延迟、每请求费用、每请求能耗，纵轴是准确率，虚线是 Pareto 前沿。只调少数几个参数就已经有这么多点。配置空间随智能体个数和每个智能体的参数数目成倍增长，而用户目标各不相同，最优点还随流量、模型和资源的可用性变化，靠人工选择不现实。

设计：声明式描述、按画像优化、运行时调整

Murakkab 管理工作流的整个生命周期，分三个阶段（Fig. 5）：开发阶段把描述变成逻辑工作流，优化阶段把它变成具体的可执行工作流和部署计划，执行阶段按请求的 SLO 运行并动态调整。各决策的频率见 Table 1。

系统

开发：只写任务和数据流

§3.2

论文对比了两种写法。原来（Listing 1）每一步都写死实现、参数和资源：用 OpenCV 切场景、抽 15 帧、32 个 CPU、Whisper 占 50 个 PTU、Llama-3.2 用 8 张 H100。这些配置和工作流结构绑在一起，任何改动都要手工改代码、重新部署[[rigid]]。Murakkab 的写法（Listing 2）只用自然语言写出子任务（“给定视频列表，识别场景”“抽帧”“语音转文字”“回答问题”）和它们之间的数据流，请求时再附上 SLO，例如低延迟。开发者也可以写明偏好，作为约束交给优化器。

执行器库
执行器有三种：大模型（含特定提示或微调）、模型的组合结构（如自我反思、LLM Debate）、工具（帧提取、搜索、MCP 工具，以及传统 ML 模型）。每个都附有描述、接口和可调参数，例如帧提取暴露帧数 F 和核数，LLM Debate 暴露辩论者数 D、轮数 R 和模型。
编排器
一个会调用工具的大模型，拿到任务描述和可用执行器列表，为每个子任务选出执行器[[orch]]，生成逻辑工作流（只表达功能、不绑定模型和硬件的 DAG），并检查相邻节点的输入输出类型是否匹配，不匹配就带着错误重新生成。任务只能映射到库中已有的执行器，找不到就请开发者接入一个[[library]]。
系统

优化：两类画像加一个 MILP

Fig. 6§3.3
工作流画像
离线在基准数据集（VideoMME、HumanEval、Math）上跑各种工作流和执行器参数，记录准确率和每个执行器的负载（每次模型调用的输入输出 token 分布）。论文引用生产智能体的研究说，很多部署的工作流基本不变，画像的成本可以被大量调用摊薄[[static]]。
模型画像
每个模型在不同 GPU、并行方式、负载下的 TTFT、TPOT、能耗和费用。与工作流画像分开，模型更新或新硬件上线只需补测模型画像。

优化器写成一个混合整数线性规划（MILP）。输入是两类画像、下一个周期每个（工作流，SLO）组合的预计请求率、各型号 GPU 的可用数量；每个周期决定工作流参数、每个执行器用的模型或工具、每种模型配置开几个实例、负载按什么比例分到各实例。约束是 SLO 可行、容量足够、不超过 GPU 预算；目标三选一：能耗最低、费用最低、费用预算内准确率最高。实例数按预计峰值配，以保证 SLO；分流比例按平均负载优化，多个工作流共用实例以提高利用率[[peak-avg]]。调用闭源 API 的模型也可以作为一种没有 GPU 需求、按 token 计费、有速率限制的画像放进来。

系统

执行：SLO 分级、周期性重新优化、自动扩容

§3.4

SLO 分四档

准确率和端到端延迟各分 best、good、fair、basic 四档，分别对应所有配置中可达到的最好值、第 95、80、50 百分位[[tiers]]。用户也可以不指定工作流，只发自然语言问题和 SLO，由编排器临时用已有的执行器拼出工作流。

两种时间尺度的调整

优化器在后台每个周期重跑一次，论文设为 60 分钟[[epoch]]，用前几个周期的负载预测下一个周期。智能体的生成量难以预测，例如视频问答在一种配置下中位数 600 token、P99 为 1200 token，所以另有自动扩容器在秒到分钟的尺度上看每个模型实例的负载，超过画像给出的阈值就扩容；负载或资源明显偏离预期时提前触发重新优化。优化器可以设成保守（按尾部负载配资源）或乐观（按常见负载配，波动交给扩容器）。

实验：单工作流、多工作流、动态编程流水线、资源变化

平台为 Azure 上各带 8 张 A100 或 H100 的虚拟机，推理用 vLLM v0.9。论文找不到公开的智能体工作流生产轨迹，于是用 2024 年 5 月 Azure 推理服务 24 小时的聊天和编程请求到达时间作为近似，聊天请求映射到视频问答，编程请求映射到代码生成[[trace]]。所有策略都按画像的第 90 百分位生成量配资源[[p90]]。

实验

看得见工作流结构才能这样调度

Fig. 12§4.6

一个请求：从视频里看出学生写的代码并验证，延迟上限 30 秒。编排器把它拆成并行的两支：视频问答提取代码、代码生成写出参考答案。三种方案都用 4 张 A100 跑 Gemma-3-27B，区别在目标检测（OmDet）和语音转文字（Whisper）放在哪里。(a) 两者各占一张 GPU，共 6 张，满足 SLO，但这两张 GPU 利用率低、CPU 闲着。(b) 两者都放 CPU，只用 4 张 GPU，但 OmDet 占满所有 CPU 核，超时。(c) OmDet 用 1 张 GPU、Whisper 用 CPU，共 5 张，两支几乎同时完成，满足 SLO，被选为最省资源的方案[[sched]]。只有看得到工作流内部各阶段和它们的画像，才能做出这种分配。

实验

优化周期取多长

Fig. 13§4.7

假设开一个新实例（分配虚拟机、装软件、把模型放上 GPU）要 20 分钟[[prov]]，用指数加权移动平均预测负载，周期从 20 分钟试到 6 小时。(a) 10 到 60 分钟时切换太频繁，过渡期间要多配 GPU，利用率低；60 到 180 分钟时最划算，利用率在 60 分钟左右最高；180 分钟以上预测偏离实际，只能多配资源。(b) 需求被低估、没有扩容就会丢掉的请求比例随周期增长，约 240 分钟时最高，约 15%[[underpred]]。论文取 60 分钟作为折中。

实验

画像能否推广到没见过的输入

§4.8

整个方法依赖离线画像，所以画像必须对新输入成立。论文在数学多轮解题工作流上用 Math-500 做画像，用没参与画像的 MathEval 测试：各模型的准确率高低顺序在两者之间一致[[general]]，生成 token 的分布形状、分散程度和峰值也接近。据此认为对相近领域的新输入，优化器可以按准确率要求选模型并预估负载。

本页说明：这里验证的是在相近领域内换一个数据集。真实请求与画像所用基准的差别（如视频长度、代码题难度）可能更大，论文的结论也限定为来自相近领域的输入。

结论

结论

Murakkab 把智能体工作流的描述与执行配置分开：开发者只写子任务和数据流，用户给出 SLO，平台按离线的工作流画像和模型画像，用 MILP 同时选择工作流参数、模型、硬件和实例数，每个周期重新优化，自动扩容器处理短时波动。因为平台看得到整个工作流，能把多个工作流的负载合并到共用的实例上，也能按阶段决定放在 GPU 还是 CPU 上。

在用 Azure 推理轨迹近似的 24 小时负载上，相对人工设定的 LangGraph 部署，GPU、能耗和费用都降低到几分之一，且满足各请求的准确率和延迟要求。

局限

局限与讨论

本页说明：以下是本页的分析。第一，到达时间来自普通聊天和编程推理请求的轨迹，映射到视频问答和代码生成上，并不是智能体工作流的真实轨迹，论文对此有说明[[trace]]。第二，对照组是一个人工设定的固定配置，节省中有相当部分来自“允许按 SLO 换模型、降准确率”，与加了相同扩容策略的基线相比，费用的差距约为 2.4 倍。第三，SLO 档位是按配置空间的百分位定义的，档位的含义随候选配置的集合而变。第四，工作流的结构和执行器要预先接入并画像；对 Claude Code 这类每个请求执行路径都不同的智能体，论文只评估了配置前沿，没有端到端的系统结果。
