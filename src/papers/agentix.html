背景

agentic program：运行时才展开的 DAG

Fig. 1§1、§2

Fig. 1 画了四种智能体程序的执行流程，蓝框是一次模型调用，橙色圆角框是外部中断，即人的输入、工具调用或执行代码。(a) 聊天机器人：模型回复和用户输入轮流出现，直到用户结束。(b) ReAct 智能体：模型推理并决定调用哪个工具，工具返回后再交给模型，循环到模型决定结束。(c) Mixture of Agents，用于事实核查和摘要：先调用工具取材料，再并行交给多个 Map Agent 处理，由一个 Reduce Agent 汇总，可以重复多轮。(d) 蒙特卡洛树搜索：多个 Actor Agent 并行提出动作并调用工具，Critic Agent 评估，Reflect Agent 反思，执行 Python 后再展开下一层。

论文把这类应用统称为 agentic program：由一个或多个智能体的模型调用和外部中断组成的有向无环图。(a)(b) 是单线程程序，长度取决于用户输入，调用和中断的顺序取决于控制流；(c)(d) 是多线程程序，线程不断分叉和合并。图的形状只在运行时才显现，无法事先知道或预测[[runtime]]。

问题

两层排队阻塞

Fig. 2§1

Fig. 2 是一个手工构造的例子，用来说明调度策略的差别。(a) 的表列出四个在 0 时刻同时到达的程序：A 有 4 个调用，各需 4、3、1、1 步 decode；B 有 3 个调用，各需 3、3、4 步；C 有 2 个调用，各需 1、2 步；D 只有 1 个调用，需 4 步。一个程序内部的调用有先后依赖，前一个完成才能发出下一个。引擎的 batch 上限是 2，即同时只能跑两个调用。(b)(c)(d) 是三种调度下的甘特图：纵轴是两个 batch 槽位，横轴是 decode 步，每个色块是一次调用占用槽位的时段，统计的是所有调用排队等待的总步数。

现有推理引擎只看单个调用，忽略了调用之间、调用与程序之间的依赖[[ignore]]。(b) 先来先服务（FCFS，vLLM 的默认策略）：A、B 的长调用先占住引擎，C、D 要等到第 3、4 步才开始，这是调用级的队头阻塞，总等待 18 个单位。(c) 多级反馈队列（MLFQ）可以抢占长调用，让 C、D 先跑；但新到的调用都进最高优先级队列，A、B 后续的调用不断插到 D 前面，这是程序级的队头阻塞[[prog-hol]]，总等待仍是 18。(d) Agentix 的 PLAS 按程序已经消耗的服务时间排序，A、B 的后续调用排到后面，总等待降到 12。

动机实验：时间花在等待上，程序内部的缓存可以复用

单线程程序的端到端延迟由三部分组成：调用在引擎里排队的等待时间、调用实际计算的执行时间、等外部中断的时间。第三部分与推理服务无关，论文只处理前两部分[[scope]]。这一节的四张图是动机测量，负载取自后面实验用的三类程序：聊天（ShareGPT 的整段对话）、ReAct（BFCL 的工具调用任务）、蒙特卡洛树搜索（LATS 在 HotpotQA 上的搜索）。只有 Fig. 4 写明了模型和硬件：LLaMA-3.1-8B，一张 A100-80GB。

Fig. 5 分别跑聊天、ReAct、蒙特卡洛树搜索三类程序，系统负载设为 0.5 和 0.9 两档，把每个程序的时间拆成两部分：调用在引擎上实际计算的执行时间（蓝），和调用在引擎队列里排队的等待时间（橙），画出两者的占比。论文没有写明这里用的是哪种调度策略，以及负载是按什么基准换算的。

Fig. 4减少等待会提高吞吐

Fig. 4 用 LLaMA-3.1-8B 在一张 A100-80GB 上回放一小时的聊天轨迹，每个程序是 ShareGPT 中的一整段对话。横轴是时间，纵轴是引擎里同时存在的模型调用数，比较 vLLM 默认的先来先服务和 Agentix 两条曲线。

调用完成得快，程序就能更早发出下一个调用，引擎里同时存在的调用更多，组批的机会也更多。稳态中 Agentix 比 vLLM 平均多容纳 10 个并发调用[[plus10]]，减少等待本身就能提高吞吐。

测量

短调用、短程序等得最久；程序内部前缀几乎全能复用

Fig. 6Fig. 7§3.1、§3.2

Fig. 6等待时间与执行时间之比

Fig. 6 用聊天和蒙特卡洛树搜索两类程序，分别在先来先服务（FCFS）、多级反馈队列（MLFQ）和 Agentix 三种调度下运行，纵轴都是等待时间除以执行时间的比值，比值越高说明相对自身的计算量等得越久。(a)(c) 以单个调用为单位，横轴是这个调用的 decode 步数，即输出有多长；(b)(d) 以整个程序为单位，横轴是程序包含的调用数，即程序有多长。

按调用看，FCFS 下输出短的调用比值最高，长调用堵住了短调用，这是调用级的队头阻塞；MLFQ 能抢占长调用，压低了短调用的比值。按程序看，FCFS 和 MLFQ 下调用少的程序比值都高，短程序等得最久，MLFQ 没有解决程序级的阻塞，因为长程序新发出的调用都会进入最高优先级。Agentix 的曲线在四幅图里都最低。

Fig. 7程序内与程序间的前缀命中率

Fig. 7 测的是前缀缓存能复用多少。命中率定义为一个新调用的输入中，已经在引擎 KV 缓存里的 token 所占的比例。(a) 是单线程的聊天程序，(b) 是多线程的蒙特卡洛树搜索，横轴是调用的输入长度，两条曲线分别只拿本程序之前的调用、或只拿其他程序的调用作为可复用的缓存来源。

程序内部，各种输入长度下命中率都在 90% 以上[[locality]]；不同程序之间，命中率随输入变长按指数下降，因为它们只共享系统提示。这一点决定了后面多引擎时怎样分配调用：一个程序的调用最好留在它已经在用的引擎上。

设计：进程表、按程序已用服务时间排优先级、离散队列与防饿死、兼顾局部性的负载均衡

Agentix 是一层建在推理引擎上的服务系统，设计目标是降低程序的端到端延迟、提高 GPU 利用率，并用 P95、P99 衡量公平性。它不需要事先知道程序何时到达、执行图长什么样、负载如何分布[[nonclair]]。

系统

有状态的会话与全局进程表

Fig. 8§4.1、§4.2.1、§5

Fig. 8 是 Agentix 的架构。上方是在用户本地运行的程序（蒙特卡洛树搜索、ReAct、网页智能体等），每个程序开启一个会话，把模型调用发给后端；中间是全局进程表，每行以程序编号（PID）为键，记录服务时间和线程信息；进程表下面是负载均衡器，把调用分到某个推理引擎；引擎内部有调度器（按优先级函数排序）、内存管理器（管理 KV 缓存的交换）和模型执行器。

普通推理 API 是无状态的。Agentix 让程序在用户本地运行，导入它的库后自动开启一个会话，之后的每次模型调用都带上会话编号，程序结束时关闭会话。对开发者来说接口看起来仍是无状态的。

服务端维护一张进程表，每个程序一行：已获得的服务时间、累计等待时间、所在引擎、每个活跃调用（线程）的到达、等待和服务时间，以及最近一次调用到达和完成的时间（用来发现停滞的程序和长时间的外部中断）。调度器和负载均衡器都读这张表。

系统

PLAS 与 ATLAS：按已用服务时间排优先级

Fig. 9§4.2.1

为什么用已用服务时间。最短作业优先能使平均响应时间最小，但需要知道程序还要跑多久，这里做不到。不知道作业长度时的常用替代是最少已获服务优先（LAS）：已经跑了很久的，多半还要跑很久，先让新来的跑。

PLAS（单线程）
一个调用的优先级等于它所属程序之前所有已完成调用的运行时间之和，数值越大优先级越低。调用完成时更新进程表里的总服务时间。
ATLAS（多线程）
多线程程序的完成时间由critical path（最长的一串相互依赖的调用）决定。Fig. 9 左边是一个由 5 个调用组成的 DAG，标出了其中的critical path；右边是把这些调用放到引擎上的两种排法，横轴是时间：不按critical path排时完成时间是 14 个单位，优先排critical path上的调用时是 11。ATLAS 用“已观察到的最长critical path的执行时间”作为程序的服务时间[[atlas]]。每个程序只存这一个数：新调用以它作为优先级，调用完成时若自己这条路径更长就更新它，不需要记录调用之间的依赖[[atlas-simple]]。一个程序的并行调用拿到相同的优先级，会被一起调度，不会有某个线程被落下。
系统

离散队列、防饿死、内存交换、负载均衡

Fig. 10§4.2.2、§4.3

为什么要离散成队列

直接按连续的优先级抢占，最坏会退化成轮转调度，比 FCFS 还差，还会频繁在 CPU 和 GPU 之间换入换出 KV 缓存[[rr]]。所以把优先级分成 K 个队列：与 MLFQ 不同，新调用按所属程序的优先级进入对应的队列，不会一律进入最高队列；队列内先来先服务，用完时间片就降一级。

防饿死。简单地把等太久的调用提到最高队列，会让长程序的调用重新打断短程序，退化成普通 MLFQ[[starve]]。Agentix 改看程序级的比值：程序和调用的总等待时间除以总服务时间超过阈值 β，才把这个调用提到最高队列，提升后只清零这个调用自己的等待和运行时间。β 用来在平均响应时间和公平性之间取舍。

抢占带来的内存开销

抢占使引擎里同时存在的调用更多，KV 缓存频繁在 GPU 和 CPU 之间交换。两项处理：每 N 个 decode 步才调度一次，并预先多放一些排队的调用在 GPU 上，以便有调用提前结束时立刻补上；改写交换函数，vLLM 原来每个 KV 块单独发起一次异步拷贝，改为先汇集到一块连续的主机缓冲区再一次性传输。

多引擎的负载均衡

输入不超过 2048 token 的短调用，在任何引擎上都能靠共享的系统提示达到 75% 以上的命中率[[short]]，所以发往最空闲的引擎；长调用固定发往它所属程序已经在用的引擎，保住前缀缓存，偶尔排队也值得。这只需要程序编号，不需要维护全局的前缀树。

实现：约 5000 行 Python 和 CUDA/C++，基于 vLLM v0.6.1，只改了调度器和交换函数[[impl]]。

实验

单引擎：相同延迟下的吞吐

Fig. 12§6.3

Fig. 12 是单个推理引擎上的主实验。四行是四种负载（ShareGPT、BFCL、LATS、Mixed），三列是三种模型和卡数：LLaMA-3.1-8B 用 1 张 A100，LLaMA-3.1-70B 用 4 张，Falcon-180B 用 8 张。每幅小图比较 vLLM、vLLM-opt、MLFQ 和 Agentix 四个系统，横轴是每秒到达的程序数，纵轴是程序级每 token 延迟的平均值（秒/token）。曲线越靠右才上翘，说明在相同延迟下能承受的到达率越高，也就是吞吐越高。

vLLM 没有前缀缓存，要反复重算状态，最早上翘。ShareGPT 和 BFCL 上，FCFS 随到达率升高出现严重的队头阻塞；MLFQ 解决了调用级阻塞，吞吐是 vLLM-opt 的 1.5 倍；Agentix 同时处理两级阻塞，在高负载下达到 vLLM 的 8 倍、vLLM-opt 的 2 倍、MLFQ 的 1.5 倍[[single]]。LATS 上，MLFQ 一味追逐短调用，反而拖慢程序，Agentix 的 ATLAS 把程序的线程一起调度。Mixed 上差距最大，达到 vLLM 的 15 倍、MLFQ 的 5.5 倍、vLLM-opt 的 5 倍[[mixed]]。

本页说明：摘要中“4 到 15 倍”的对照是没开前缀缓存的 vLLM；与打开前缀缓存等优化的 vLLM-opt 相比，引言给出的是 2 到 5 倍，这是更公平的比较。

实验

多引擎：只用程序编号做负载均衡

Fig. 14Fig. 15§6.4

Fig. 14 测多引擎下的负载均衡。每个引擎内部的调度固定为 PLAS（单线程程序）或 ATLAS（多线程程序），只换负载均衡策略：轮转（Kubernetes 的默认做法）、发给当前调用数最少的引擎、Preble（维护全局前缀树，长前缀匹配的调用发往局部性最好的引擎，短的发往最空闲的引擎）和 Agentix（只看程序编号）。部署有两种：4 个 LLaMA-3.1-8B 副本，或 2 个 LLaMA-3.1-70B 副本；负载是 ShareGPT 和 LATS。四行对应四种模型和负载的组合，三列分别是平均、P95、P99 延迟，横轴是程序到达率。

Agentix 比轮转和最空闲优先吞吐最多高 1.4 倍，与 Preble 接近[[lb]]，但不用维护前缀树。ShareGPT 上优势更明显，因为对话历史的复用多；副本越多，随机分配撞上有缓存的那台引擎的机会越小，按程序固定引擎的好处就越明显。

Fig. 15 测扩展性：用 ShareGPT 负载和 LLaMA-3.1-8B，副本数取 1、2、4、8，延迟目标（SLO）取 0.3、0.5、1.0 秒/token 三档，纵轴是满足目标时 Agentix 能承受的最大程序到达率。三档目标下，最大到达率都随副本数线性增长，按程序做负载均衡不需要前缀树这类额外开销，可以直接横向扩展。

结论

结论

Agentix 把服务的对象从单个模型调用改为整个程序：用会话和进程表记录每个程序的累计服务时间，单线程程序用 PLAS、多线程程序用 ATLAS 排定优先级，离散成多级队列并按程序级的等待比例防止饿死；多引擎时短调用做负载均衡，长调用固定到程序所在的引擎以保留前缀缓存。不需要预先知道程序的结构和长度。

在聊天、ReAct 工具调用、蒙特卡洛树搜索和混合负载上，相同延迟下的程序吞吐比优化过的 vLLM 高 2 到 5 倍，尾延迟在多数场景下也更低。

局限与讨论

本页说明：以下是本页的分析。第一，论文把等待外部中断的时间排除在问题之外，实验部分也没有说明工具调用和人的等待时间怎样设置；ShareGPT 是把整段对话连续重放。而智能体在工具调用期间要不要保留 KV 缓存、长时间中断后程序还算不算“已用很多服务”，这些都没有涉及。第二，优先级只看已用的服务时间，没有区分程序的截止时间或用户的延迟要求。第三，按已用服务时间降级会系统性地延后长程序，平均延迟和尾延迟之间的取舍依赖阈值 β，论文没有给出 β 的敏感度分析。第四，基础引擎是 vLLM v0.6.1，与当时打开前缀缓存的 vLLM-opt 比较，没有与 SGLang 等已有的缓存感知调度直接比较。
