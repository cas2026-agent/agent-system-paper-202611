背景

agentic program：运行时才展开的 DAG

Fig. 1§1、§2

论文把智能体应用称为 agentic program：由一个或多个智能体的模型调用和外部中断（工具调用、代码执行、人的输入）组成的有向无环图。(a)(b) 是单线程程序，模型调用和中断交替，长度取决于用户输入和控制流；(c)(d) 是多线程程序，线程不断分叉和合并。图的形状只在运行时才显现，无法事先知道或预测[[runtime]]。

问题

两层排队阻塞

Fig. 2§1

现有推理引擎只看单个调用，忽略了调用之间、调用与程序之间的依赖[[ignore]]。例子：(a) 四个程序同时到达，A、B 长，C、D 短，引擎一次跑两个调用。(b) 先来先服务（FCFS，vLLM 的默认策略）：A、B 的长调用先占住引擎，C、D 要等到第 3、4 步才开始，这是调用级的队头阻塞，总等待 18 个单位。(c) 多级反馈队列（MLFQ）可以抢占长调用，让 C、D 先跑；但新到的调用都进最高优先级队列，A、B 后续的调用不断插到 D 前面，这是程序级的队头阻塞[[prog-hol]]，总等待仍是 18。(d) Agentix 的 PLAS 按程序已经消耗的服务时间排序，A、B 的后续调用排到后面，总等待降到 12。

动机实验：时间花在等待上，程序内部的缓存可以复用

单线程程序的端到端延迟由三部分组成：调用在引擎里排队的等待时间、调用实际计算的执行时间、等外部中断的时间。第三部分与推理服务无关，论文只处理前两部分[[scope]]。以下实验用 LLaMA-3.1-8B 和一张 A100。

设计：进程表、按程序已用服务时间排优先级、离散队列与防饿死、兼顾局部性的负载均衡

Agentix 是一层建在推理引擎上的服务系统，设计目标是降低程序的端到端延迟、提高 GPU 利用率，并用 P95、P99 衡量公平性。它不需要事先知道程序何时到达、执行图长什么样、负载如何分布[[nonclair]]。

系统

有状态的会话与全局进程表

Fig. 8§4.1、§4.2.1、§5

普通推理 API 是无状态的。Agentix 让程序在用户本地运行，导入它的库后自动开启一个会话，之后的每次模型调用都带上会话编号，程序结束时关闭会话。对开发者来说接口看起来仍是无状态的。

服务端维护一张进程表，每个程序一行：已获得的服务时间、累计等待时间、所在引擎、每个活跃调用（线程）的到达、等待和服务时间，以及最近一次调用到达和完成的时间（用来发现停滞的程序和长时间的外部中断）。调度器和负载均衡器都读这张表。

系统

PLAS 与 ATLAS：按已用服务时间排优先级

Fig. 9§4.2.1

为什么用已用服务时间。最短作业优先能使平均响应时间最小，但需要知道程序还要跑多久，这里做不到。不知道作业长度时的常用替代是最少已获服务优先（LAS）：已经跑了很久的，多半还要跑很久，先让新来的跑。

PLAS（单线程）
一个调用的优先级等于它所属程序之前所有已完成调用的运行时间之和，数值越大优先级越低。调用完成时更新进程表里的总服务时间。
ATLAS（多线程）
多线程程序的完成时间由critical path（最长的一串相互依赖的调用）决定。图中例子：不考虑critical path时完成时间是 14 个单位，考虑时是 11。ATLAS 用“已观察到的最长critical path的执行时间”作为程序的服务时间[[atlas]]。每个程序只存这一个数：新调用以它作为优先级，调用完成时若自己这条路径更长就更新它，不需要记录调用之间的依赖[[atlas-simple]]。一个程序的并行调用拿到相同的优先级，会被一起调度，不会有某个线程被落下。
系统

离散队列、防饿死、内存交换、负载均衡

Fig. 10§4.2.2、§4.3

为什么要离散成队列

直接按连续的优先级抢占，最坏会退化成轮转调度，比 FCFS 还差，还会频繁在 CPU 和 GPU 之间换入换出 KV 缓存[[rr]]。所以把优先级分成 K 个队列：与 MLFQ 不同，新调用按所属程序的优先级进入对应的队列，不会一律进入最高队列；队列内先来先服务，用完时间片就降一级。

防饿死。简单地把等太久的调用提到最高队列，会让长程序的调用重新打断短程序，退化成普通 MLFQ[[starve]]。Agentix 改看程序级的比值：程序和调用的总等待时间除以总服务时间超过阈值 β，才把这个调用提到最高队列，提升后只清零这个调用自己的等待和运行时间。β 用来在平均响应时间和公平性之间取舍。

抢占带来的内存开销

抢占使引擎里同时存在的调用更多，KV 缓存频繁在 GPU 和 CPU 之间交换。两项处理：每 N 个 decode 步才调度一次，并预先多放一些排队的调用在 GPU 上，以便有调用提前结束时立刻补上；改写交换函数，vLLM 原来每个 KV 块单独发起一次异步拷贝，改为先汇集到一块连续的主机缓冲区再一次性传输。

多引擎的负载均衡

输入不超过 2048 token 的短调用，在任何引擎上都能靠共享的系统提示达到 75% 以上的命中率[[short]]，所以发往最空闲的引擎；长调用固定发往它所属程序已经在用的引擎，保住前缀缓存，偶尔排队也值得。这只需要程序编号，不需要维护全局的前缀树。

实现：约 5000 行 Python 和 CUDA/C++，基于 vLLM v0.6.1，只改了调度器和交换函数[[impl]]。

实验

单引擎：相同延迟下的吞吐

Fig. 12§6.3

行是负载，列是模型，横轴是程序到达率，纵轴是延迟。曲线越靠右，说明在相同延迟下能承受的到达率越高。vLLM 没有前缀缓存，最早上翘。ShareGPT 和 BFCL 上，FCFS 随到达率升高出现严重的队头阻塞；MLFQ 解决了调用级阻塞，吞吐是 vLLM-opt 的 1.5 倍；Agentix 同时处理两级阻塞，在高负载下达到 vLLM 的 8 倍、vLLM-opt 的 2 倍、MLFQ 的 1.5 倍[[single]]。LATS 上，MLFQ 一味追逐短调用，反而拖慢程序，Agentix 的 ATLAS 把程序的线程一起调度。Mixed 上差距最大，达到 vLLM 的 15 倍、MLFQ 的 5.5 倍、vLLM-opt 的 5 倍[[mixed]]。

尾延迟

Fig. 13§6.3

抢占式调度能降低平均延迟，但可能饿死长程序、拉高尾延迟。ShareGPT 上 MLFQ 的平均延迟比 vLLM-opt 好很多，P95、P99 却很差[[mlfq-tail]]；BFCL 上 MLFQ 两项都更好。Agentix 在 8 个场景中有 7 个的尾延迟低于 MLFQ 和 vLLM-opt[[tail]]，在 P95、P99 下吞吐最多高 1.7 倍。防饿死机制在这里起作用。

结论

结论

Agentix 把服务的对象从单个模型调用改为整个程序：用会话和进程表记录每个程序的累计服务时间，单线程程序用 PLAS、多线程程序用 ATLAS 排定优先级，离散成多级队列并按程序级的等待比例防止饿死；多引擎时短调用做负载均衡，长调用固定到程序所在的引擎以保留前缀缓存。不需要预先知道程序的结构和长度。

在聊天、ReAct 工具调用、蒙特卡洛树搜索和混合负载上，相同延迟下的程序吞吐比优化过的 vLLM 高 2 到 5 倍，尾延迟在多数场景下也更低。

局限

局限与讨论

本页说明：以下是本页的分析。第一，论文把等待外部中断的时间排除在问题之外，实验部分也没有说明工具调用和人的等待时间怎样设置；ShareGPT 是把整段对话连续重放。而智能体在工具调用期间要不要保留 KV 缓存、长时间中断后程序还算不算“已用很多服务”，这些都没有涉及。第二，优先级只看已用的服务时间，没有区分程序的截止时间或用户的延迟要求。第三，按已用服务时间降级会系统性地延后长程序，平均延迟和尾延迟之间的取舍依赖阈值 β，论文没有给出 β 的敏感度分析。第四，基础引擎是 vLLM v0.6.1，与当时打开前缀缓存的 vLLM-opt 比较，没有与 SGLang 等已有的缓存感知调度直接比较。
